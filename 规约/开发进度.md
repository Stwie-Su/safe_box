- 新增 `app/hal/time/time_rtc.c`：走 **Linux RTC 子系统** `/dev/rtc<N>`，只用 `RTC_RD_TIME` / `RTC_SET_TIME`
  两个 ioctl；BCD 编解码与寄存器寻址交给内核 `ds1307` 驱动，**不手写 I2C**。
- 时间基准**一律 UTC**，转 Unix 秒用自算 civil-days 公式（不用 `timegm`：非标准 C 且受 `TZ` 影响），
  与 `settimeofday` 口径一致，TOTP 才对得上。
- 选择：`SAFE_TIME_BACKEND`（`sys`/`rtc`，默认 `sys`）；节点 `SAFE_RTC_DEV`（默认 `/dev/rtc1`）。
  **`/dev/rtc0` 是片上 SNVS，无备份电池**（板上实测 `date -u +%s` == uptime 秒数，即每次上电从 0 开始），
  不可作持久化时间源——这正是必须外接 DS3231 的原因。
- **优雅降级（硬要求，已实测）**：`SAFE_TIME_BACKEND=rtc` 但节点不存在 / 打不开 / ioctl 失败
  → 打一条 `[time]` 日志并回退 sys，**不崩不卡**。`hal_time_source()` 如实返回 `TIME_SRC_RTC` / `TIME_SRC_SYS`。
- **`/dev/rtcN` 独占打开（板上实测的坑）**：rtc-dev 用 `RTC_DEV_BUSY` 互斥，被异常占用的进程退出后该位
  **可能不复原**（实测：卡在 `read()` 的调试 `dd` 被 kill 后，连续 5 次 open 仍 `EBUSY`）。
  故改为**首次成功后常驻 fd 复用**；代价是 app 运行期间 `hwclock` 会 `EBUSY`——校时走 `hal_time_set`（RPC `sync_time`）。
  **禁止对 `/dev/rtcN` 执行 `dd`/`cat`/`head`**（`read()` 会等 RTC 中断，永久挂住并占死设备）。
- 验证：`build_pc` 0 error / 0 warning；`ctest` **7/7**；换算白盒（一次性 harness，不入库）
  20 万随机 + 边界穷举往返一致，`1700000000 → 2023-11-14 22:13:20`、`951782400 → 2000-02-29` 正确。
  PC 真机 ioctl（sudo 读 `/dev/rtc0`）：`src=1`，连续两次 `hal_time()` 均成功。
  板上（`build_board_test` 0 error/0 warning，rc=0 正常启动）：默认 → `[time] 后端 = sys`；
  `/dev/rtc1` 不存在 → `[time] … 不可用，降级 sys`；`/dev/rtc0` 被占 → 同降级。

## 8. 帧率优化（2026-09-12）：板上分段测量 → 定位瓶颈 → 显示像素数封顶

> 纪律：先测量后优化（规约 §4.2）。**全部数据在真机 i.MX6ULL（528MHz 单核 A7、无 GPU、

### 8.1 优化前的分段测量（板上，FACE 页，实时摄像头，稳态 45s）

| 分段 | 每帧耗时 | 占墙钟 | 说明 |
|---|---|---|---|
| 采集取帧 DQBUF | 49 us | 0.1% | V4L2 mmap 零拷贝，**不是瓶颈** |
| YUYV→RGB565 转换 | 20.8 ms | 26% | face 线程内，与主线程并行；查表实现，无浮点 |
| 帧拷贝（双帧缓冲） | 0.7~1.8 ms | ~1% | memcpy |
| 取帧 get（跨线程取最新帧） | 0.5~0.8 ms | <1% | |
| 缩放映射（320×240 → 显示矩形） | 15.6 ms | 13% | 查表最近邻，绘制期零除法 |
| **LVGL 渲染周期（合计）** | **120.9 ms** | **~100%** | **瓶颈** |
| └ flush（写帧缓冲） | 0.4 ms | 0.4% | 32bpp fb0 直写，flush 本身可忽略 |

**瓶颈 = LVGL 渲染（几乎等于整帧时间），而 LVGL 渲染耗时与「显示像素数」近似成正比**：
强制 1:1（画布 320×240 = 7.7 万像素）时渲染周期 131.9ms → 34.9ms；反向扫描显示尺寸得同一结论（§8.2）。
采集 / 格式转换 / 帧拷贝 / flush 都不是瓶颈 —— 这也否定了「先上 NEON 换帧率」的直觉。

### 8.2 显示尺寸扫描（同场景同摄像头，30s 稳态，取后 20s 平均）

| 显示矩形 | 像素数 | LVGL 渲染周期 | 视频 fps | UI fps |
|---|---|---|---|---|
| 546×409（优化前默认，1.7×） | 22.3 万 | 120.9 ms | 7.7 | 7.7 |
| 512×384（1.6×） | 19.6 万 | 89.1 ms | 7.4 | 7.6 |
| 480×360（1.5×） | 17.3 万 | 57.9 ms | 9.7 | 13.6 |

| 384×288（1.2×，未采用） | 11.1 万 | 19.9 ms | 10.6 | 27.4 |

同时逐项排除了其它嫌疑（各 20s，每次只开关一项）：
去掉预览面板圆角 121.9 → 107.6 ms（**小尺寸下该差异消失，故圆角最终保留**）；
隐藏底部半透明浮层 / 删除扫描光带动画 / 隐藏四角扫描框，三者各自 ≤5 ms，均非瓶颈；
画布改 ARGB8888（想让 LVGL 走 32 位直通）**反而变慢到 189 ms，已否决**，RGB565 画布保留。

### 8.3 最终落地的两项优化

1. **画布收缩到视频矩形**：v5 的画布满铺面板，每帧都要给「视频区之外」的留白刷一次底色
   （1008×410 面板下约 20~30 万像素/帧，纯浪费）。改为**画布尺寸 = 视频矩形 + 定位到居中位置**，
   留白交给 `s_preview` 的 panel 底色承担（只在尺寸 / 主题变化时刷一次）；
   画布缓冲同时从 ~827KB 降到 416×312×2 ≈ 259KB。
2. **显示放大倍数封顶 1.3×**（新增 `FACE_MAX_SCALE = 1300`，千分比整型运算）：
   `scale = min(面板等比自适应, 1300)`。采集固定 320×240，放大 1.3× 后**每个源像素仍被显示**
   （1.3 个显示像素 / 源像素），继续放大只是最近邻复制 —— 不增加任何细节，却线性地吃掉帧率。
   面板比 416×312 还小时按面板自适应，不会过度放大（PC 端同理）。

**这不是靠砍功能 / 砍画质换来的**：采集分辨率 320×240 不变、4:3 比例不变、不新增线程、无每帧堆分配，
`face_capture_once` 的分辨率校验与「只转最新帧」语义均未触碰；圆角 / 底栏 / 扫描动画 / 四角扫描框全部保留。
显示从「1.7× 放大」降到「1.3× 放大」，源的 7.68 万像素一个不少地全部显示，只是不再无意义地插值到 22 万像素。

### 10.2 SYSTEM 页折叠缺陷的根因与修法（值得记）

- **根因**：`st_panel` 面板**默认带 `LV_OBJ_FLAG_SCROLLABLE`**，内容超高即变成卡内滚动 → 「恢复出厂设置」被推到折叠线以下裁掉、点不到。旧代码靠注释里的"纵向撑满"补丁，缩放一变就失效（而缩放是分辨率自适应，必然变）。
- **结构性修法（不调数字）**：①左右面板一律 `lv_obj_set_scrollable(x,false)`；②主题列表放进**独立可滚动子容器**（溢出只滚它）；③危险区**移出面板**成为 root 的独立卡片，由 root column-flex + body `flex_grow` **结构性地**保证可见可点。

### 11.5 D20 的两项实测副产物（2026-09-16，QA 独立复核）

1. **「无法录入」是从属现象，不是独立缺陷**：看不到画面 → 无法把脸对准模组 → 模组回

   ⇒ 「首屏即人脸页」这条路径下 `进入前台` **从不被调用**，相机可用完全依赖 `app.c` 开机那次 `hal_camera_start()`。

   hidden→visible 边沿，故**当前不触发**。修法备选：`s_fg_ui` 初值改 `false`，或 `set_foreground(true)`
   时补检 `hal_camera_fd() < 0` 就重启。
3. **预览管线仍是两份重复实现**（架构债）：本轮只治了「常量分叉」，未治「管线分叉」，

### 11.6 预览默认旋转的判定与收口（2026-09-16，`631b530`）

**怎么确定是 270 而不是 90**（不靠穷举试错）：取用户截图里的预览帧，按 4 个方向逐一旋转比对
—— 顺时针 90° 得到**倒立的脸**；逆时针 90°（即本项目的 `270`）**人脸正立、天花灯位于画面顶部**。
代码侧再复核 `rotate_frame()` 的索引（`dst[x*sh + (sh-1-y)]` ⇒ 源 +x → 目标 +y）确认 `deg==90` 确为顺时针，
故映射为 `270`（`270` 的实现 `dst[(sw-1-x)*sh + y]` 即逆时针 90°，与注释一致）。

**同机位 A/B 实测**：`SAFE_CAMERA_ROT=0` → 人脸侧倒、天花板横躺；不设 env（新默认 270）→ 人脸正立、天花灯在顶部。
两页（识别 / 录入）共用同一默认值，PC 与板上一致。

**收口原则（与 D20 同一教训）**：设备固定的**预览几何**（默认旋转）与**性能上限**（放大倍数）都属于
「单一真源」，一律放 `app/ui/pages/preview_cfg.h`，**不允许再散落在启动器 env 或各页面里**——
D20 与 D21 都是这条原则被破坏的产物。重装 / 换向时用 `SAFE_CAMERA_ROT`（支持显式 0）覆盖即可，不必改代码。

### 14.5 新增两条环境/排错教训（已写进验收技能）

1. **版本串是 configure 期快照**：`cmake/SafeVersion.cmake` 用 `git describe` 但只在 **configure 阶段**求值 → `--clean-first` 重编**不会**更新它（本次真机日志一直打 `4af8e14-dirty`，差点误判成"跑的是旧二进制"）。**判二进制新鲜度要用 mtime + 符号**（如 `nm … | grep fm225_parse_userid_list`），要更新版本串必须重 configure（`rm -rf build_pc`）。
2. **启动命令天生非幂等**：`SSHConnection.execute()` 断线会自动重连重跑，叠加客户端重试曾一次起 **4 个实例**抢同一串口与同一日志。修法 = **幂等启动脚本**（`pgrep -x <prog>` 非 0 就跳过）+ 对启动命令**绝不重试**。另：常驻进程 stdout 重定向到文件是**块缓冲**，`printf` 不落盘会让日志"停在半截"，须 `stdbuf -oL -eL`。

### 15.3 帧率：先取证，再动刀（关键数字）

| 项 | 实测 / 现状 | 含义 |
|---|---|---|
| 色深 | 板端 `CONFIG_LV_COLOR_DEPTH 32` / PC 端 16 | 板端每帧像素字节数 2 倍；但 **fb0 实测就是 32bpp**，同色深使 flush 变纯 memcpy（这正是当初选 32 的理由，不能单向反悔） |

### 15.4 已落地的 4 项优化（均不依赖上板）

|---|---|---|---|---|

### 15.5 保留到上板后再定的项（本轮**没做**，需实测）

3. **板端帧率基线**：用 `SAFE_PERF_LOG=1` 取 `handler avg/max`，与 §8 的历史基线（UI 20.5fps）对齐后再决定是否需要进一步措施。
