## 20. 上板联调全通：OTA 期①闭环 + WiFi UI + 服务器双工程（2026-10-02，WorkBuddy 端）

**真机链路清单（全部实机验证）**：
- **ch341 内核外编模块**：板载内核 `CONFIG_USB_SERIAL_CH341` 未启用 → 拉板子 `/proc/config.gz` 全量重编内核取精确 `Module.symvers`（`MODVERSIONS=y` 必须同源）产出 `ch341.ko` → 固化 `/lib/modules/4.9.88/extra/`，wrapper 启动 insmod。FM225 USB 串口 `/dev/ttyUSB0`：自检 RESET→REPLY 通过，协议层模组清单「2 模板 201B 应答」。
- **相机**：UVC（ffff:ffff，非标）仅 MJPG → 软解路径；**开机竞态**（S05lvgl 早于 USB 枚举，首扫必空）加「人脸页打开时重扫 ≤3 次」自愈；**v4l2 快速恢复**（STREAMOFF 后直接 QBUF）在该 UVC 上返回 EINVAL → 失败自动退回完整重开路径（修「回来 0 帧」）。
- **显示与性能**：`SAFE_DISPLAY_ROT=180` 软件旋转（fbdev flush `lv_draw_sw_rotate`）；触摸**不镜像**——LVGL indev 核心随 rotation 自动变换，手动标定反转会双重抵消（D20）。PARTIAL 缓冲 60→240 行；切换动画 200/160→70/50ms；**板载构建切 Release**（-O0 曾致 stb 软解/旋转帧成本假性劣化，fps 数帧→十七帧的主因）。
- **OTA 期①（FR-29）**：系统页卡片 + `ota_check/apply.sh`（wget+sha256sum+tar，`mv` 原子替换）+ `ota_watchdog.sh` 回滚（`.ota_pending` 标记：应用 20s 健康确认清除，45s 未清自动恢复 `.old`）+ 分发双通道（HTTP 直连：WiFi→PC portproxy→VM；ADB 预推送 `/var/ota` 兜底）。
- **WiFi UI 配网**：禁 `S45network-manager`（抢 wlan0 的根因，韦东山流程）+ `S46wifi` 开机自连 + `wpa_cli -a` DHCP 事件联动（CONNECTED 起 udhcpc / DISCONNECTED 清 IP）+ `update_config=1` 持久化。backend_wpa（AF_UNIX ctrl_iface 自研 ~200 行）真机全通：扫描/连接/凭据库（AES+PBKDF2）。
- **服务器双工程**（Ubuntu 桌面，完整源码+cmake）：`mqtt-server`（自研单文件 broker：MQTT 3.1.1 子集 QoS0/1+retain+will+通配，标准 mosquitto 客户端回环验证 + 板端真实业务数据流经；**运行态用 mosquitto**，自研作协议栈作品）；`ota-server`（自研 HTTP：GET 白名单分发 + POST /report 上报落盘 + make_ota_pkg/vm_ota_push）。

**关键坑（D 台账候选）**：
- **D19 OTA 状态协议**：脚本「追加式」写状态 vs UI 取**首个**匹配 → 永远停在 CHECKING（「检查中…」卡死）；手动 cat/grep 全量查看掩盖根因，必须模拟读方解析逻辑验收。修复三件套：解析纯函数化取**最后**匹配（`core/support/ota_status.c` + `test_ota_status`，ctest 18→**19**）+ 脚本改「重写式」+ UI 30s 超时兜底。**教训固化为纪律：跨进程 IPC 的解析必须纯函数化进 ctest**。
- **D19b apply 错误无分支**：升级失败（ERR_DOWNLOAD/ERR_SHA/…）在 UI 无对应分支 → 永远「升级中…」。已补全 5 个错误分支 + 下载百分比实时进度（manifest 加 size 字段，wget 后台 + stat 轮询）。

### 23.1 FR-25 双向 TLS 闭环（此前「代码 90% 就位但未启用」→ 实机打通）

**链路**：板端（10.218.148.190）→ PC（10.218.148.51:8883）→ VM mosquitto（192.168.150.139:8883）。
broker 侧 `require_certificate true` + `use_identity_as_username true`，板端持 `device.crt`、
测试端持 `phone.crt`，同出自签 CA（`tools/tls/gen_certs.sh` 一键生成，ECDSA P-256；
broker 证书 SAN 覆盖 PC portproxy / VM / 回环三种连接地址 —— 缺 SAN 会 verify 失败）。

**实测结果**：
- 上行：`safe/status` 5s 心跳，握手日志 `[TLS] 握手完成：TLSv1.2 / TLS-ECDHE-ECDSA-WITH-AES-256-GCM-SHA384`；
- 下行：`safe/cmd`（phone 证书，QoS1）→ 板端 `safe/log` 回执，`req_id` 关联正确；
- 稳定性：修复后 **100s 观察 0 次断链**（修复前约 30s 一次）。

**代码改动**：
1. `tls_stream_pending()`（新）：mbedTLS 一次 `ssl_read` 只交付**一个 record 内**的数据，
   同一 record 剩余字节与后续 record 留在 SSL 层缓冲；此时底层 fd 已无待读字节，
   外层 `poll(fd)` 不再报 POLLIN → 残留数据被**饿死**（PINGRESP/PUBACK/SUBACK 永远取不到）。
   外层 poll 前查询 pending，为真时 timeout 置 0 并再读一轮。明文后端恒 false。
2. 断链原因可观测：`CLOSE_SOCKET` 打印 FSM 统计快照；读路径 EOF/错误、`tx_flush` 失败、
   mbedTLS 错误码均落日志 —— 「周期性重连」不再只能靠猜。

**★ 排查留档（诚实记录，避免后人重复踩）**：本轮观察到的「每 30s 断链一次」，
**根因在实验用 Windows 转发器，不在设备代码** —— `socket.create_connection(timeout=30)`
的 timeout 会被继承为 socket 超时，30s 后 `recv` 抛 `TimeoutError` 掐断长连接。
定位链：板端「读 EOF」→ broker 侧 `Client closed its connection` →
tcpdump 见 FIN 由 Windows 侧先发并带 RST → 转发器日志 `up->down TimeoutError`。
**教训：定位跨机问题时要先分清"设备"与"实验链路"，转发器也必须打日志。**
`pending` 修复是防御性加固（缺陷真实存在且必须修），但不是本次断链的根因。

**运维要点（必读）**：板端 8883 依赖 PC 侧端口转发。永久做法（管理员一次）：
`netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=8883 connectaddress=192.168.150.139 connectport=8883`
（现有 8080 / 1883 两条同款规则）。临时替代：用户态转发器需把 upstream socket
在建连后 `settimeout(None)`，否则复现上述 30s 断链。

### 23.2 FR-29 断点续传 + HMAC 来源验签

设计口径：**sha256 防「传输损坏」，hmac 防「来源伪造」，两者不可互替**（规约 §5.9）。
密钥 `ota_hmac.key`（打包机）与板端 `/etc/safe/ota.key` 为同一字节串。

1. `tools/ota_apply.sh` v4
   - 断点续传：`wget -c`（服务器须支持 Range/206），`-t 3 -T 30` 弱网宽容；
     **残片防御**：已有文件超过 manifest 的 `size` 判为「服务器换过包」→ 清掉重来
     （否则续传会把新旧包拼成混合体，要到 sha256 终验才发现，白费一次下载）。
   - HMAC 强校验：`hmac` 字段**强制** —— 缺失即拒（杜绝攻击者剥掉 hmac 字段把包
     降级成「无验签」形态），不符即拒并删除已下载数据。
2. `tools/ota_hmac.py`（新）：板端 HMAC-SHA256，仅用标准库
   （BusyBox 无 `hmacsum`，板载 python3.8.5 足够，零第三方依赖）。
3. OTA HTTP 服务（自研 `mini_ota_http.c`）：支持 `Range: bytes=N-` → 206 +
   `Content-Range`，越界 → 416，并补 `Accept-Ranges: bytes`；日志记录
   `Range=<off> size=<sz> -> <code>`，让「到底续传了没有」可被审计。

**实机验证（板端 i.MX6ULL）**：
| 项 | 方法 | 结果 |
|---|---|---|
| 断点续传 | 制造 512000 字节残片后 apply | 从该偏移继续（512000→1508708，**未回零**）；服务器日志 `Range=512000 size=2211840 -> 206` |
| 正向全流程 | 续传完成后 sha256+HMAC | 通过 → 解包 / 原子替换 / 重启；版本 **1.0.4 → 1.0.5**，新进程单实例、exe 非 deleted |
| 负向①：hmac 不符 | manifest hmac 改全 0 | `STATE=ERR_HMAC`，**已下载包被删除** |
| 负向②：剥 hmac 字段 | manifest 去掉 hmac | `STATE=ERR_HMAC`，**已下载包被删除** |

**已知边界（登记不改）**：manifest 字段提取用 `grep`，对 JSON 缩进/空格敏感 ——
打包端格式固定故可用；若 manifest 被写成 `"file": "..."`（带空格）会落到 `ERR_ARGS`
—— **仍是拒绝，安全方向正确**，仅错误码不够精确。若要更稳可改用板载 python3 解析
（`ota_hmac.py` 已证明板端 python 可用）。

## 25. 认证路径零同步落盘（2026-10-08，WorkBuddy 端）

### 25.1 背景：门禁里唯一的整文件豁免

`tools/check_main_thread_store.sh` 的白名单中，`app/core/auth/auth_fsm.c::*` 是唯一
按**文件**豁免的条目（其余 8 条都是「文件::函数」精确登记）。它对应技术路线规约
§3.1 明文的并发纪律「认证路径零同步落盘」——该条自 v1.3 立项起一直未落地。

**为什么拖到现在才做**：认证路径的落盘不是单纯的「写」，而是「读→改→写」三步
（失败计数 +1、达阈值置 `lock_until`；临时用户 `used_count++` 用尽即删；TOTP 防重放
计数器回写）。直接套用「主线程算好新值 → worker 去写」会**丢失更新**，详见 25.2。

### 25.2 核心取舍：为什么必须整段下沉

| 方案 | 做法 | 问题 |
|---|---|---|
| A 主线程算、worker 写 | 主线程读快照 `failed_attempts` → +1 → 投作业落盘 | **丢失更新**：人脸连续出帧时一帧内可能调多次，每次都基于同一份快照算 +1，最终只落盘 +1 → `max_failed` 永远打不满，失败锁定形同虚设 |
| B 整段下沉（**采用**） | worker 内 `find_by_name` → 改 → `user_update` 一口气做完 | 主线程拿不到「改完的值」，FSM 只能等回调 |

选 B 之后，**顺序保证从哪来**是整个方案的成立前提：worker 是单线程 FIFO 队列。
前一个「失败计数落盘」作业完成后，后一个 PIN 校验作业（`backend_verify_pin` 走
`user_load_all` 读**真实文件**）才开始 ⇒ 「已锁定」不会被异步化撕开窗口。
**这条依赖必须记住**：一旦将来把 worker 改成多 worker 线程池，本方案的安全前提就没了。

### 25.3 落地内容

| 层 | 改动 |
|---|---|
| `store_cache` | 补 `find_by_name` / `find_by_face`（此前只有 `find_by_id`）——主线程查用户的唯一合法通道 |
| `async_store` | 新增 `astore_auth_side(op, user, detail, cb)`：四类副作用（失败计数锁定 / 开锁清零与临时用户计数 / FR-21 凭据失效 / FR-9 授权撤销）**共用一个作业类型 + op 分派**，而不是四个独立作业——输入都是「一个用户名」、形态都是同一套读改写，分开写只会复制四遍样板 |
| `auth_fsm` | 12 处同步 store 调用全部替换：读 → 快照；写 → `astore_auth_side`；`log_append` → `astore_append_log` |
| 动态码通道 | `submit_otp` 下沉 worker（**世代号覆盖，不单飞**；校验期间仍停 WAIT_OTP，不新增状态） |
| UI | 新增 `page_otp_on_fsm` 结果回填（与 `page_keypad_on_fsm` 同款），删掉「提交后立刻读 `auth_fsm_state()`」的同步判定 |
| 门禁 | 摘掉 `auth_fsm.c::*` 整文件豁免；`unlock_backend.c` 纳入扫描并登记调用方纪律 |

**两个刻意与 PIN 通道不同的设计**（避免后人"对齐"回去）：
1. **世代号覆盖而非单飞**：单飞要求「离开 WAIT_OTP 的每一条路径都复位标志」才不卡死
   （tick 超时 / 手动取消 / WAIT_OTP 期间刷脸放行……）太散、太易漏；世代号覆盖天然不会卡死，
   且 FIFO 下旧作业先派发、被丢弃。
2. **不新增 FSM 状态**：校验期间停在 WAIT_OTP，UI 与 `auth_fsm_state_name` 零改动。

### 25.4 顺带修掉的盲区：门禁看不见 unlock_backend

本次把 `unlock_backend.c` 纳入门禁扫描后**立刻暴露一处真实违规**：`temp_revoke`
（static 辅助）不被 `backend_*` 前缀覆盖。更早在评估阶段就发现——`backend_verify_totp`
内部有 `user_find_by_name` + `user_update`（读盘 + 整表写盘），而它曾被主线程经
`auth_fsm_submit_otp` **同步调用**，门禁原先完全看不见这个文件。

处置：以白名单形式登记（`backend_*` 前缀 + `temp_revoke` 单独登记），并在脚本注释里
写明成立前提 —— **这些函数只允许在 worker 线程调用**。
**教训：门禁的扫描范围是会被"想当然"缩小的。** 一个"存储层判定封装"因为看起来
只在后台用，就被排除在扫描之外，结果它恰恰是主线程同步落盘的藏身处。
