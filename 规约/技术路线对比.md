## 1. 时间源：片上 SNVS RTC（/dev/rtc0） vs 外部 DS3231（等 /dev/rtc1）

| | 片上 SNVS（已采用） | 外部 DS3231（原计划） |
|---|---|---|
| 依赖 | 仅需装后备电池（已完成） | 等 I2C 模组到货 + 设备树挂载 |
| 精度 | 秒级（内部 RC/LSE） | ±2ppm 温补（更准） |
| 断电保持 | ✅ 实测成立 | ✅ |
| 代码改动 | **0 行**（time_rtc.c 早已写好，换环境变量即切） | 0 行（同一份 time_rtc.c） |

**实测证据（2026-10-10）**：
- `date -s "2020-01-01"` 把系统时钟改错后，app 走 rtc 后端**仍显示真实时间** `2026-10-11 00:01`（截图为证）；
- 同一时刻 **MQTT 断线**——系统时间错误 → mbedTLS 证书有效期校验失败。反向证实了立项理由：「证书校验依赖可信时间源」。

**决策**：先用 SNVS。DS3231 到货后只需 `SAFE_RTC_DEV=/dev/rtc1`，代码零改动——这正是 HAL 抽象的回报。

**为什么默认节点仍保留 /dev/rtc1**：改默认值会静默改变未装电池设备的行为（同 OTA D35 教训：改默认=改别人设备的行为）。

**一句话讲法**：*"我的时间后端是编译期预留、运行期选择的——同一份代码，装电池前走 sys、装电池后一个环境变量切到硬件 RTC，证书校验和审计日志的时间可信性随之闭环。我还实测了系统时间被篡改时 TLS 会因证书校验失败而断线，这反过来证明了时间源为什么必须可信。"*

## 2. epoll vs poll vs select（已实测，2026-10-11）

**结论先行：本项目现状（2~4 个 fd）下 epoll 无可测优势，保留 `poll`；拐点实测在 n≈16，n≥64 后 epoll 才拉开差距。**

### 实测方法

`tools/io_bench.c` —— 用 pipe 构造 N 个监听 fd（其中 active 个有数据），计时单次 wait 循环（含注入与排空），
对比 select / poll / epoll-LT / epoll-ET。交叉编译后在**板端 i.MX6ULL（ARM Cortex-A7）**运行，iters=3000。

```
cd <工程> && arm-buildroot-linux-gnueabihf-gcc -O2 -o io_bench tools/io_bench.c
adb push io_bench /usr/share/lvgl/ && adb shell "ulimit -n 8192; /usr/share/lvgl/io_bench 3000"
```

### 实测数据（板端 ARM，单次 wait 循环，ns/次；越小越好）

| n_fd | active | select | poll | epoll_LT | epoll_ET | epoll 相对 poll |
|---|---|---|---|---|---|---|
| 2 | 1 | 17115 | 12207 | 12324 | 12267 | **+0%（噪声内）** |
| 4 | 1 | 15511 | 12497 | 13905 | 12761 | +11%（噪声内） |
| 8 | 1 | 16564 | 13618 | 12197 | 12886 | −10%（噪声内） |
| 16 | 2 | 26255 | 23531 | **21298** | **21145** | −10%（开始稳定领先） |
| 64 | 4 | 82620 | 51935 | **38843** | **38252** | **−25%** |
| 256 | 8 | 193057 | 163829 | **70467** | 101193 | **−57%** |
| 1024 | 16 | **n/a** | 1083498 | **140210** | 171128 | **−87%（快 7.7 倍）** |

### 三条实测发现

1. **小集合下 epoll 并不更快**。n≤8 时两者都在 12–17µs 量级，差异落在噪声里（同一场景多次跑会互有胜负）。
   原因不难理解：epoll 省的是"每次调用都要把 fd 集合从用户态拷进内核 + 内核线性扫描"的开销，
   fd 少时这点开销本就微不足道，而 `epoll_ctl` 的建树成本反而是额外支出。
2. **拐点在 n≈16，n≥64 后差距才真正拉开**（−25% → −57% → −87%）。
   这正是 epoll O(1) 就绪队列 vs poll O(n) 线性扫描的经典曲线，只不过是**在本项目目标板上实测出来的**。
3. **select 在 n=1024 直接不可用**：不是"慢"，是**崩溃**。
   `fd_set` 是**按 fd 号索引的位图**，不是按监听个数；当 fd 号 ≥ `FD_SETSIZE`(1024) 时 `FD_SET` 会**越界写**，
   实测直接 Segmentation fault（bench 早期版本就死在这里，后加显式防护才输出 `n/a`）。
   这条是"为什么不用 select"最硬的实证——不是教科书结论，是我踩出来的。

### 决策（按"有提升才保留"）

- **现有 `face_thread`（2 个 fd：FM225 UART + 相机）保留 `poll`**：换成 epoll 无可测收益，
  而它每 200ms 才等一次，12µs vs 14µs 的差异占比 0.001%，**属于为技术正确性付出重构风险却换不来收益**。
- **未来若要建"统一事件总线"收编 MQTT socket + 串口 + 相机 + 门磁/传感器（fd 数会到 10~几十），则新总线用 epoll**：
  那时收益是 25%~57% 的真金白银。
- 换句话说：**不是"epoll 更高级所以要用"，而是"到什么规模才值得用"——这条曲线就是答案。**

### 一句话讲法

> *"我给项目做过一次 IO 多路复用的实测选型：在板子上用 pipe 构造不同 fd 规模，对比了 select/poll/epoll-LT/ET。
> 结果是 2~8 个 fd 时 epoll 和 poll 没有可测差异——所以我的人脸线程保留了 poll，没有为了用 epoll 而重构；
> 拐点在 16 个 fd 左右，到 1024 个 fd 时 epoll 快 7.7 倍。另外 select 在高 fd 号下会 segfault，
> 因为 fd_set 是按 fd 号索引的位图，FD_SET 越界写——这个坑我是真的踩到了，不是背的。"*
