## 1. 架构总览

### 1.1 分层与依赖方向

```
ui/          表现层：页面、主题、控件、字体
   ↓ 单向依赖
core/        业务层：auth（认证） / store（存储） / remote（远程） / support（支撑）
   ↓ 单向依赖
hal/         硬件抽象层：face / actuator / camera / time / net
   ↓
platform/    平台适配：SDL(PC) / FBDEV(目标板)
```

硬约束：

- 依赖**严格单向向下**。`ui` 不得直接调 `hal`；`core` 不得感知具体后端实现；`hal` 不得引用上层。
- `core` 不出现平台头文件（不含 LVGL、不含 SDL/fbdev），保证可移植与可单测。
- 硬件差异全部收敛在 `hal` 的后端注册机制内。
- **`ui` 不得直接调系统接口**（v1.4 明文）：需要系统信息时在 `hal` 开接口，例如存储占用 → `hal_storage_used_pct()`。`check_layers.sh` 只查包含关系，抓不到"在 ui 层 `#include <sys/statvfs.h>` 自己算"这类穿透（历史遗留：`page_monitor.c` 曾如此），要靠评审兜住。

### 1.2 设计原则

| 原则 | 落地方式 |
|---|---|
| 后端可替换 | HAL 以函数指针表注册，构建期选后端，业务零改动 |
| 配置集中 | 阈值与地址集中在 `app/core/config.c`，支持环境变量覆盖，禁止散落魔法数 |
| 错误码统一 | 除认证域语义外统一 `safe_err_t`，禁止各模块自造返回码 |
| 主题 token 化 | UI 取色走 `theme_color()` 与全局样式，禁止硬编码颜色值 |
| 异步不阻塞 | 阻塞任务（PBKDF2、文件 IO）下沉后台线程，主线程只做渲染与分发 |
| 事件解耦 | 跨模块通知走 `event_bus`，发布方与订阅方互不知情 |

## 3. 线程与并发模型

### 3.1 现状（Sprint1 已实现）

| 线程 | 职责 | 节拍 |
|---|---|---|
| 主线程（LVGL） | 渲染、状态机心跳、结果泵、事件派发、指令分发 | 20ms / 100ms / 5s 三级节拍 |
| worker 后台线程 ×1 | PBKDF2 校验、文件 IO、网络凭据读写 | 由 `worker_post` 投递 |
| MQTT 网络线程 | 自研客户端的 poll 循环：连接 / 收发 / 重连退避；消息只入线程安全队列，不触碰 UI | 由 `rpc` 层启动 |

主线程节拍分工：

| 函数 | 周期 | 内容 |
|---|---|---|
| `app_tick_fast()` | 20ms | `worker_poll()` → `event_bus_pump()` → `rpc_poll()` → `hal_face_tick()` |
| `app_tick_slow()` | 100ms | `auth_fsm_tick()`（轮询人脸结果、状态超时推进） |
| `app_tick_periodic()` | 5s | `rpc_publish_status_now()` |

并发约定（**必须遵守**）：

- LVGL **非线程安全**，所有 UI 操作只能在主线程。
- 后台线程完成回调通过 `worker_post(fn, arg, done)` 的 `done` 在主线程 `worker_poll()` 执行。
- 跨线程事件用 `event_bus_post()`，主线程 `event_bus_pump()` 派发；主线程可直接 `event_bus_publish()` 同步派发。
- MQTT 线程只入队，主线程 `rpc_poll()` 消费，网络线程不得触碰 UI 对象。
- **不持锁调回调**（v1.3 明文）：任何临界区内不得调用外部回调 / `event_bus_publish` / LVGL API——先取出数据、解锁、再回调（worker 与 event_bus 现有实现即如此，防止回调内再入队导致死锁）。
- **认证路径零同步落盘**（v1.3 明文）：`auth_fsm` 回调与判定路径内禁止直接调 `user_update` / `log_append` 等同步文件 IO（当前 keypad→FSM→backend 全链在主线程做 PBKDF2 + 全量读写盘，见 §10），一律经 worker（`astore_*` / `worker_post`）异步完成。

  ★ **2026-10-08 已落地**：
    - 主线程查用户一律走 `store_cache` 只读快照（`find_by_id` / `find_by_name` / `find_by_face`）；
    - 用户表改动一律经 `astore_auth_side(op, user, detail, cb)` 在 worker 内**整段读改写**，审计走 `astore_append_log`；
    - 动态码通道 `auth_fsm_submit_otp` 下沉 worker（世代号覆盖，不新增 FSM 状态）。
  ⚠ **本条成立的前提**：worker 是**单线程 FIFO**。顺序保证来自它——前一个落盘作业完成后，后一个校验作业（`auth_verify_pin` 读真实文件）才执行，因此「已锁定」不会被异步化撕开窗口。**将来若改成多 worker 线程池，本方案的安全前提即失效，必须重新设计。**

### 3.2 退出与信号（v1.3 新增）

进程必须可优雅退出，防数据半写与线程悬挂：

| 步骤 | 动作 |
|---|---|
| 1 | 注册 `SIGTERM` / `SIGINT` 处理：**只置 `g_quit` 标志**（信号处理函数内不做任何 IO / 分配） |
| 2 | 主循环检测 `g_quit` 跳出，`lv_timer` 停止 |
| 3 | `app_shutdown()`：`hal_face_deinit` → `mqtt_stop` → **`worker_shutdown()`（置退出标志 + `pthread_join`）** → store 缓存脏数据 flush 落盘 → `platform_shutdown()` |
| 4 | `main` 返回，进程退出 |

> 现状缺口（2026-09-08 审计）：`app_shutdown` 缺 worker join 与 `platform_shutdown` 调用，`main` 无信号处理、主循环无退出路径——列为重构项（§10），接口见 §5.7 `worker_shutdown()`。

### 3.3 线程数封顶（v1.3 新增）

**口径（必须先明确，否则数字没有意义）**：本节约束的是**应用自建常驻线程**，不含第三方库内部线程；
第三方线程须在下表**显式登记**，新增时同步本节。

| 类别 | 线程 | PC(SDL) | 板子(FBDEV) | 说明 |
|---|---|---|---|---|
| 应用自建 | 主线程（LVGL） | 1 | 1 | `main.c` |
| 应用自建 | worker | 1 | 1 | `worker.c` |
| 应用自建 | face 线程 | 1 | 1 | `face_thread.c`（步骤 3b 新增） |
| 应用自建 | MQTT 网络线程 | 0 | 0 | 当前用 Paho；R9 自研后为 1 |
| **应用自建小计** | | **3** | **3** | **≤4 ✅（尚余 1 条）** |
| 第三方 | LVGL swdraw 渲染 | 1 | 1 | `render_thread_cb @ lv_draw_sw.c`；`DRAW_UNIT_CNT=1` 时仍存在 |
| 第三方 | Paho MQTTAsync | 2 | 2 | 收发线程 + 回调线程；R9 替换后消失 |
| 第三方 | Mesa / llvmpipe | 17 | **0** | 仅 PC 软件 GL；FBDEV 后端不存在 |
| **进程内合计** | | **23** | **约 6** | |

实测依据（2026-09-10，步骤 3b，QA 独立验证）：`gdb -p <pid> -batch "thread apply all bt"` **逐线程取栈**
判定来源——应用 3 条栈顶分别为 `main`(main.c:58) / `worker`(worker.c:62 cond_wait) / `face`(face_thread.c:127 poll)。

**结论与收敛路径**：
- 应用自建 3 ≤ 4，本节预算成立；3b 只新增 face 1 条，符合设计。
- **但**：§3.1 四角色模型把 MQTT 计为 1 条，而 Paho 实占 2 条；叠加 LVGL swdraw 1 条后进程内为 5~6 条。
  故 **R9（自研单线程 MQTT 客户端替换 Paho）是把进程内线程收敛到四角色模型（4 条）的必要条件**。
- R9 完成后：应用自建 = 主 + worker + MQTT + face = **4**（正好用满预算）；第三方仅余 LVGL swdraw 1 条。
- **新增线程必须先修订本节**，并说明为何不能用「worker 投递」或「合并进既有线程 `poll` 多 fd」收敛。
  单核 A7 上每多一条线程只是多一份上下文切换与同步面。
- ⚠️ **上板评估注意**：FBDEV 后端下 Mesa 的 17 条**不存在**，板子进程内线程数远低于 PC——
  评估板子资源占用时**不要用 PC 的 23 作依据**（板子上约 6 条）。

**实测（2026-09-10 步骤 3b，Ubuntu/Xvfb + SDL）**：应用侧**逻辑线程 = 主线程 + worker + MQTT + face = 4**；步骤 3b 相对 3a 只 **+1**（face），已用「临时屏蔽 face_thread_start」对照实测（无 face=22/20，有 face=23/21，mqtt on/off 各一组，恒定）。两点须说明，均非本工程新增线程：① 现网 MQTT 走 paho `MQTTAsync`，其内部另起 **2** 条 OS 线程（§3.1 原设计为自研单线程 poll 客户端，实现选了 paho），故 OS 层面应用线程为 5；② Xvfb 下 SDL 经 Mesa llvmpipe 软件 GL 渲染，另有约 **18** 条运行时线程（`llvmpipe-*` 等，上板 FBDEV 无此项）。故 `ls /proc/<pid>/task | wc -l` 裸计数在本环境为 **23**，不能等同应用线程预算——预算口径按「本工程自建的常驻线程」计 4。

### 3.4 Sprint3 目标模型（v1.3 修订：合并 face 线程）

~~采集线程 + 识别线程分立~~ **合并为一个 face 线程**：V4L2 取帧（连续流）与 FM225 串口（事件驱动）节拍不同，但均为可 poll 的 fd，单线程 `poll()` 双 fd 收敛——线程总数 5→4，且命中 IO 复用（poll/epoll）考点。

| 线程 | 职责 | 交接方式 |
|---|---|---|
| face 线程 | `poll()` 双 fd：V4L2 取帧 + 格式转换（**只转最新帧**，旧帧丢弃）；FM225 串口协议状态机解析，产出识别结果（含失败原因码） | 识别结果 `event_bus_post(EV_FACE_EVENT)` 交主线程；预览帧写环形/双帧缓冲，满则丢最旧，绝不阻塞采集 |
| 主线程 | LVGL 渲染 + 既有节拍 | 消费者 |

约束：

- 临界区内不做格式转换等重计算。
- 识别结果只能通过 `event_bus_post` 交给主线程，禁止跨线程操作 LVGL 对象。
- 单核上绘制仍为单绘制单元（多线程绘制为负优化）。
- **代价与缓解**：格式转换重时会延迟串口响应——以「只转最新帧」缓解；若将来预览要求高帧率且识别阻塞变长，再拆回两线程（须回改本节）。
- **为什么 poll 不用 epoll**：epoll 的优势在大量连接的 O(1) 就绪通知（服务器场景）；设备端仅 2 个 fd，poll 足够且更可移植——能说清适用边界比硬上 epoll 更显判断力。
- **落地模块/接口（3b）**：线程在 `app/hal/face/face_thread.[ch]`（§5.19）；相机 fd 经 `hal_camera_fd()`（§5.13）借用（fd 仍归 camera 模块）；主线程经 `face_thread_get_preview()` 取最新预览帧；`hal_face_tick` 保留在主线程作后端驱动（理由见 `face_thread.c` 头注释）。

## 5. 接口规约

> 格式：签名 → 参数 → 返回值 → 功能 → 调用关系（谁调它 / 它调谁）

### 5.1 应用编排 `app/app.h`

- **参数**：无。
- **返回值**：无。
- **功能**：`app_main` 按依赖顺序初始化存储 → worker → 执行器 → 配置 → 界面 → 状态机 → 远程通道；三个 tick 分别为异步结果泵 / 状态机心跳 / 周期上报。
- **调用关系**：`main.c` 调 `app_main`，并用 LVGL 定时器挂三个 tick；`app_main` 内调 `store_init` → `worker_init` → `hal_actuator_init` → `app_config_init` → UI 初始化 → `auth_fsm_init` → `rpc_init`。

### 5.2 认证状态机 `app/core/auth/auth_fsm.h`

- **参数**：`submit_face(face_id, reason)` 为一次人脸结果（**无分数**，按失败原因分流；`face_reason_t` 定义见 §5.11 `hal_face.h`，core 依赖 hal 为架构允许方向）；`submit_pin`/`submit_otp` 为凭据字符串；`note_unlock(user)` 为成功用户名；`note_failure(detail)` 为失败描述。
- **返回值**：状态查询类返回状态 / 最近失败原因 / 剩余秒数；其余无返回值，结果通过 UI 钩子和事件回调通知。
- **功能**：**按失败原因分流**（成功→开锁；未匹配→计数，连续达 `face_otp_after` 强制转动态码，再达 `max_failed` 锁定；活体失败→拒绝 + 防伪告警并入 FR-10；超时 / 无人脸→不计数）、失败计数与设备级锁定、动态码等待与超时、状态展示时长控制。本模块不 `#include` LVGL，与 UI 通过钩子解耦。
- **调用关系**：
  - 被调：`app_tick_slow` → `auth_fsm_tick`；人脸事件订阅者 → `auth_fsm_submit_face`；PIN 键盘 → `submit_pin`；动态码页与 RPC `submit_otp` → `submit_otp`；RPC `remote_unlock` → `note_unlock`。
  - 它调：`auth_verify_totp` / `auth_verify_pin`（判定），`hal_actuator_pulse`（开锁脉冲），`log_append` 与 `event_bus_publish`（记录与通知），UI 钩子与事件回调。

### 5.3 认证判定 `app/core/auth/auth_verify.h`

- **参数**：`pin` 明文 PIN；`out_user`/`user_cap` 为成功时回填用户名与缓冲容量；`code` 为 6 位动态码。
- **返回值**：见枚举。`AUTH_REPLAY` 表示该码已用；`AUTH_CHANNEL_OFF` 表示通道未启用；`AUTH_EXPIRED` 为临时授权过期或次数耗尽。
- **功能**：PIN / 动态码 / 管理员二次确认三条校验路径的统一入口，内含 ±1 窗口、防重放、失败计数与通道开关判定。
- **调用关系**：UI 与 RPC 只调本接口，不持有判定逻辑；`auth_verify_totp` 内部调 `totp_verify`；管理员二次确认被「改管理员密码」「删除用户」「RPC 敏感指令」调用。

### 5.4 动态码 `app/core/auth/totp.h`

- **参数**：`b32` Base32 密钥；`counter` 时间片序号；`now` 当前 Unix 秒（用 `hal_time()`）；`last_counter` 上次成功使用的时间片（0 = 从未使用）；`used_counter` 成功时回填本次时间片。
- **返回值**：`totp_verify` 返回 `0` 通过、`-1` 码错、`-2` 重放、`-3` 参数或密钥非法；其余函数 `0` 成功。
- **功能**：RFC6238（HMAC-SHA1、30s 步长、6 位），±1 窗口容忍，**严格递增计数器防重放**。只做密码学，不碰用户表、不落盘。
- **调用关系**：`auth_verify` 调 `totp_verify`；时间源用 `hal_time()` 便于切换 RTC；UI 用 `totp_remaining` 画倒计时。

### 5.5 存储抽象 `app/core/store/store.h`

- **`user_face_set(user_id, face_id)`（2026-09-11 UI 现代化 ui3 新增）**：人脸录入/删除完成后把模组分配的模板号写回用户记录的单字段便捷接口，`face_id < 0` 表示清除绑定。实现为「读整表 → 定位该用户 → 写 `face_id` → 整表原子落盘」；当 `face_id >= 0` 时会先把其它用户身上相同的 `face_id` 清成 -1（防御性去重，保证 `user_find_by_face` 的唯一映射）。之所以不直接用 `user_update`：那是整记录覆盖，「查→改→写回」三步在并发写场景有丢失更新风险，这里把读改写收进 store 内部一处。同步落盘、内部有锁，可从 worker 线程调用。
  **不变式（v1.4 补充）**：`face_id < 0` ⟹ `face_enable == false`（无绑定必然不可用）。
  所以本接口在 `face_id >= 0` 时**顺带置 `face_enable = true`**（语义「重新录入即重新授权」）——
  否则被 FR-21 两条防线标失效、或被管理员关过通道的用户，重新录入人脸后仍会被 `auth_fsm` 以
  「人脸通道未启用」**永久拒绝**；在把别的用户身上的同名模板清成 -1 时，**同时把那个用户的
  `face_enable` 也置 false**（否则该用户处于「通道已启用但无绑定」的状态：刷脸会被判「未注册
  人脸」并记失败，界面也会误导管理员）。反向状态（`face_enable=false` 且 `face_id>=0`）是
  **合法**的，表示「有绑定但被停用」，保留。
  **加载边界也要归一化（v1.4 补充，QA 二轮/三轮发现）**：`store.c` 的 `parse_user_obj` 反序列化时，`face_id`
  与 `face_enable` 是**各自独立**从 JSON 读的 —— 必须在读完后再归一化一次（`if (u->face_id < 0) u->face_enable = false;`）。
  **不信任磁盘数据**：该不变式确立之前的旧版本可能已经写出 `face_id=-1 & face_enable=true` 的 users.json，
  而加载后任何 `user_update` 都会把它**原样回写**，让不一致态自我延续；只防「新增」不修「存量」是半个修法。
  （注意区分两种情况：**字段缺失** → 缺省 false 已天然一致；**字段存在且不一致** → 才需要归一化。）
- **参数**：用户结构整体传入/传出；`log_query` 的 `evt_filter` 为 `NULL` 不过滤、`res_filter < 0` 不过滤。
- **返回值**：多数返回 `0` 成功；`user_verify_pin` 返回 `0` 通过 / `1` 错误 / `2` 已锁定 / `-1` 无此用户；`*list` 需 `user_list_free` 释放，`*out` 需 `free`。
- **功能**：业务代码只调本层，不关心落 JSON 还是将来的 SQLite/独立分区。PIN 走 PBKDF2-SHA256 加盐哈希，明文不落盘。
- **调用关系**：上层通过 `async_store` 异步包装调用，避免 PBKDF2 阻塞主线程；策略阈值被 `config.c` 读取生成配置快照。

### 5.6 异步存储 `app/core/support/async_store.h`

- **参数**：回调均为主线程执行；`list` 在回调返回后由框架释放，回调内不得保留其指针。
- **返回值**：无（结果通过回调给出）。
- **功能**：把 PBKDF2 与文件 IO 下沉后台线程，回调回主线程后可安全操作 LVGL。
- **调用关系**：UI 调 `astore_*` → 内部 `worker_post` → 后台执行 `store_*` → `done` 回主线程执行回调。

### 5.7 后台 worker `app/core/support/worker.h`

- **参数**：`arg` 必须堆分配，提交后主线程不得再读写，由 `done` 负责释放（`done` 为 `NULL` 时框架释放）。
- **返回值**：无。
- **功能**：单后台线程 + 结果泵模型；`worker_shutdown()` 置内部退出标志、唤醒 worker 并 `pthread_join`，由退出流程调用（§3.2），保证不丢在途作业。
- **调用关系**：`app_main` 调 `worker_init`；`app_tick_fast` 调 `worker_poll`；`app_shutdown` 调 `worker_shutdown`；`fn` 内**禁止**调用任何 LVGL API，且**不持锁执行**（作业函数在锁外运行）。

### 5.8 事件总线 `app/core/event_bus.h`

- **参数**：`payload` 按主题约定类型（如 `EV_MQTT_STATE` 为 `const bool *`），总线不接管其内存，发布方保证生命周期覆盖本次派发；**结构体 payload 一律 POD（定长数组，禁指针成员）**——`post` 走 `memcpy` 按值拷贝（上限 `PAYLOAD_MAX_BYTES` 128B，`ev_auth_result_t` 116B / `ev_face_event_t` 100B 均含，头文件以 `_Static_assert` 拘束），跨线程投递不悬空。
- **返回值**：`subscribe` 返回 `SAFE_OK` / `SAFE_ERR_NOMEM` / `SAFE_ERR_PARAM`；`post` 返回 `SAFE_OK` 或错误码。
- **功能**：替代散落各模块的回调字段；主线程 `publish` 同步派发，其它线程必须 `post`（入队，主线程 `pump` 派发）。接线（v1.3 / 步骤 3a 落地，3b 调整）：`hal_face_emit` → `post(EV_FACE_EVENT)`（3b 起改用 `post`——脸结果可能来自 face 线程，主线程调用亦安全、仅延迟一拍）；`auth_fsm_init` 订阅 `EV_FACE_EVENT`；`app.c on_auth_event` → `publish(EV_AUTH_RESULT)`（主线程同步）。
- **调用关系**：状态变化、主题切换、MQTT 连接变化等统一经此广播；`app_tick_fast` 调 `event_bus_pump`。

### 5.9 配置 `app/core/config.h`

- **参数**：无（从环境变量 / 存储策略 / 编译默认三处聚合）。
- **返回值**：`app_config_init` 返回 `safe_err_t`；`app_config()` 返回内部静态快照指针（未初始化时返回默认值快照）。
- **功能**：只读配置快照。来源优先级：**环境变量 > 存储层策略 > 编译期默认值**（如 `SAFE_MQTT_HOST` / `SAFE_MQTT_PORT` / `SAFE_MQTT_TLS` / `SAFE_TLS_CA` / `SAFE_TLS_CERT` / `SAFE_TLS_KEY` 可覆盖）。
- **调用关系**：须在 `store_init()` 之后调用；策略变更后调 `app_config_reload_policy()`；`app_main` 读取 `mqtt_host/port` 传给 `rpc_init`。
- **校验**：`app_config_init()` 末尾调用 `app_config_validate()`（见 §5.24），
  FATAL 拒绝启动、WARN 钳制后继续。

### 5.10 远程通道 `app/core/remote/`

- **参数**：`host` 为 broker 地址字符串、`port` 端口；`mqtt_take` 需提供主题与负载缓冲及其容量；`rpc_take_local_otp` 回填待处理的本地动态码请求 ID。
- **返回值**：`mqtt_start` / `mqtt_publish` 返回 `0` 成功（断线时 `publish` 返回 `-1`）；`mqtt_take` 返回 `1` 表示取到一条；`rpc_take_local_otp` 返回是否有待处理请求。
- **功能**：`mqtt_client` 为**自研精简 MQTT 3.1.1 客户端**——socket 非阻塞 + poll 驱动；CONNECT/CONNACK、PUBLISH/PUBACK（QoS1 超时重发）、SUBSCRIBE/SUBACK、PINGREQ/PINGRESP 状态机；断线指数退避重连；**LWT 遗嘱**（异常掉线时 broker 代发离线状态，配合 R-1 在线状态）；消息先入线程安全队列。传输层统一经 `tls_stream` 可插拔加密层（见 §7.5），**加密与否对客户端逻辑零感知**。`rpc` 做指令解析、权限门控（req_id 去重 + 序号窗口防重放）、回执。
- **调用关系**：`app_main` → `rpc_init(cfg->mqtt_host, cfg->mqtt_port)` → `mqtt_start`（回调传 `NULL`，消息走内部队列）；`app_tick_fast` → `rpc_poll` → `mqtt_take`；回执与事件 → `mqtt_publish("safe/log", ...)`；`app_tick_periodic` → `rpc_publish_status_now` → `mqtt_publish("safe/status", ...)`。

#### 5.10.1 R9 自研 MQTT 客户端 —— 模块分解（v1.5 新增）

**设计主线：把「协议逻辑」与「IO / 线程」彻底切开。** 纯逻辑层不碰 socket、不碰线程、不自己取时间，
因此重传时序、退避曲线、keepalive、半包/粘包全部可以在 PC 上做**确定性单测**（喂字节 + 喂时间戳 → 断言输出）。
这条切分是本设计最重要的决定：否则「状态机单独出单元测试」只能靠真 broker 碰运气。

**范围界定**：自研的是**客户端**（client）。broker 继续用板子上已有的 mosquitto
（`/etc/init.d/S50mosquitto`）—— 自研客户端是硬约束驱动（ARM 无交叉编译好的 `libpaho-mqtt3a`，
构建时探测失败即 OFF → 编入 `mqtt_stub.c` → 设备上「MQTT 断线」为永久状态）；
自研 broker 无真实需求，且订阅树/会话持久化属服务端方向，与设备端岗位目标错位。

| 文件 | 职责 | 层次 |
|---|---|---|
| `mqtt_codec.[ch]` | MQTT 3.1.1 报文编解码：变长剩余长度（1~4 字节，防第 4 字节仍带续位的畸形输入）、CONNECT / PUBLISH / PUBACK / SUBSCRIBE / PINGREQ / DISCONNECT 组包，CONNACK / PUBLISH / PUBACK / SUBACK / PINGRESP / UNSUBACK 解析。**纯函数：不 malloc、不做 IO、不取时间、不打印**；非法输入（NULL / 超长 / 截断 / 超 268435455）返回明确错误码 | 纯逻辑 |
| `mqtt_inflight.[ch]` | 未确认报文队列（in-flight）：packet_id 分配与 1~65535 回绕、入队 / 出队 / 按 id 查找、超时扫描、DUP 位置位、重传次数与队列满策略。**存「已组好的字节」而非上层指针** —— 上层 `rpc.c` 会在 publish 后立刻 `free()` 掉 JSON，存指针必悬垂 | 纯逻辑 |
| `mqtt_fsm.[ch]` | 状态迁移 + 收包分发 + 定时器（keepalive / PING 超时 / 重传 / 指数退避含抖动）。**不建 socket、不起线程、不调 `hal_time_ms()`** —— 时间由调用方按参数注入 | 纯逻辑 |
| `tls_stream.[ch]` | 可插拔传输层（§7.5 已定稿的 4 函数签名）：后端 A 恒等（默认，直接透传 socket）；后端 B mbedTLS 用 `#if SAFE_FEATURE_TLS` 隔离 | 传输抽象 |
| `mqtt_client.c` | **IO 与线程**：单线程 `poll()` 循环、非阻塞 connect、self-pipe 唤醒、入队消息队列、对外 API 实现 | IO / 线程 |
| `mqtt_stub.c` | `SAFE_FEATURE_MQTT=OFF`（或板子无网）时的同一套 `mqtt_client.h` 的另一实现，二选一由 CMake 决定 | fallback |

**接口纪律**：§5.10 已定的对外签名**保持不变**（`rpc.c` / `ui.c` / `app.c` 零改动），
仅新增 `mqtt_set_will()` / `mqtt_state_str()` / `mqtt_stats()` / `mqtt_queued()`。

**分层验证策略**：T01~T03（编解码 / 队列 / 状态机）为纯逻辑，PC 单测即可全绿；
T04 接入后额外用 VM 上已装的 mosquitto 做真 broker 端到端（订阅 `safe/#`、杀 broker 验重连、
`kill -9` 验 LWT 广播、与 `mosquitto_pub/sub` 对拍）。

**下行背压的定性（重要，防止误读）**：QoS1 下行采用「入队成功才发 PUBACK，队列满则不 ACK 让 broker 重投」，
但这是**缓解**而非修复 —— 它只降低主线程被压的频率，不消除「主线程同步跑重活」的根因，
故 **QA-20（rpc dispatch 下沉 worker）与 QA-21（rpc_poll 节流）是 T04 的前置依赖，不得因有背压而降级**。
另一条实现红线：**背压绝不能靠「停止读 socket」实现** —— 那会关死 TCP 窗口 → PINGRESP 读不出来 →
keepalive 超时 → 断连 → 会话丢失 + 重连风暴，背压的收益被它自己制造的重连抵消。

**明确不实现的部分（取舍记录）**：QoS2（仅解析识别报文类型，不实现 PUBREC / PUBREL / PUBCOMP 状态机）、
MQTT 5.0（用 3.1.1）、双向 TLS 的 PKI 配发体系（只做可插拔传输层与单向校验，见 §7.5）、broker 侧任何逻辑。

**行为保证边界（不做过度承诺）**：下行 at-least-once 到「入队」为止，重启会丢在途报文；
上行事件掉电即丢，靠 5s 周期状态快照补齐 —— 安全事件的权威记录是本地 `safe.log`，不是 MQTT 通道。

### 5.11 人脸服务 `app/hal/hal_face.h`

- **参数**：`backend_name` 为 `"fake"` / `"fm225"` / `"none"`，传 `NULL` 时用**构建期默认名的单一来源**（`app_config()->face_backend`，它已合并环境变量与编译期默认），**不得在查找表里默认取首项**——否则 `SAFE_FACE_BACKEND=none` 的构建会静默启用人脸，属安全相关的反面默认（D2）。
- **`tick(now_ms)` 接口约定（v1.4 钉死）**：`now_ms` 必须与 `hal_time_ms()` **同源**（单调毫秒）。后端内部一律用 `hal_time_ms()` 记时刻，与传入的 `now_ms` 相减才是真实等待时长；跨时钟基（如主循环自增计数 vs 绝对毫秒）做无符号相减会回绕成巨值 → 超时判定恒真 → 无退避重发刷屏（D1）。**后端对 `now_ms` 只许做差值运算**。
- **返回值**：`safe_err_t`；不支持的操作返回 `SAFE_ERR_UNSUP`。
- **功能**：业务层唯一可见的人脸接口，事件驱动（不轮询硬件），后端经函数表替换。业务层只认 `{face_id, reason}` 数据接口约定（**无分数**）；多方向交互录入的实时引导与已录方向进度由本层事件驱动（FR-19）。
- **调用关系**：`app_main` → `hal_face_init`（后端选择：环境变量 `SAFE_FACE_BACKEND` → 参数 → 构建期默认）；`app_tick_fast` → `hal_face_tick`；后端事件 → `hal_face_emit` → `event_bus_publish(EV_FACE_EVENT)`（ev_face_event_t POD payload）→ 订阅者 auth_fsm 的 `on_face_event` → `handle_face_result`；UI 与 RPC `inject_face` → `hal_face_inject`（仅 fake 后端可用）。
- **并发（步骤 3c 补）**：`hal_face_emit` 与 `hal_face_last_result` / `hal_face_poll_compat` 读写 `s_last` / `s_seq` / `s_has_last` **须持同一把内部互斥锁**——emit 可能来自 face 线程（fm225 后端在 face 线程解析出识别结果），last_result 在主线程被 UI/RPC 调用，二者并发。锁只覆盖字段读写（不含 `event_bus_post`，遵守 §3.1「不持锁调回调」）；配套并发用例见 tests/test_event_bus.c（face 线程高频 emit + 主线程 last_result 竞争）。

- **格式锁定 `MJPG`（v1.6 变更，2026-10-14）**：~~优先 `YUYV`、协商失败降级 `MJPG`~~ → **直接请求 `MJPG`** + `stb_image` 软解。

  实测数据（cam_probe，2026-10-14）：MJPG 320×240 → 实测 17.8 fps、帧均 20732 B、带宽约 360 KB/s；480×320 → 12.4 fps；驱动对 30fps 请求一律收敛到 **15.000 fps**（离散单值 0.067s），故 `PREVIEW_MS = 50ms`（20fps 拉帧）有余量。
  **保留项及理由**（同为疤痕但有真实需求，删除会引入回归，逐条见 `backend_v4l2.c` 删除记录）：多节点扫描（实测 video1 是同设备的 Metadata Capture 节点，无 `VIDEO_CAPTURE`）、STREAMOFF 后「快速恢复 / 完整重开」两条路径（这颗非标 UVC `ffff:ffff` 的 QBUF 静默 EINVAL）、MJPG 坏帧丢弃不停流（USB 抖动出截断帧）、S_FMT 后校验驱动是否照做（UVC 驱动会静默改写 pixelformat）。
  实现约束不变：软解必须放**独立翻译单元**（`stb_image_impl.c`，以 `-w` 编入，见 §8），且必须定义 `STBI_NO_HDR` / `STBI_NO_LINEAR`——HDR 路径引用 libm `pow`，会让所有链 `safe_thirdparty` 的单测链接失败。**只解最新帧、坏帧丢弃不停流**。
- **硬件能力探测工具（v1.6 新增）**：`tools/cam_probe.c`（自研，`cc -O2 -o cam_probe tools/cam_probe.c`，可交叉编译上板）。输出 `QUERYCAP` 能力位逐位解释 + `ENUM_FMT` / `ENUM_FRAMESIZES` / `ENUM_FRAMEINTERVALS` 全量枚举 + 指定格式的实测帧率与帧字节。**纪律：新增/更换摄像头后先跑它，把结论回写本规约，再决定代码里写死什么**；不要再用「协商失败再降级」的方式替代码猜硬件。`v4l2-ctl --list-formats-ext` 可作交叉对照，但板子上没有该工具。
- **冷启动延迟重扫（v1.4 目标项 T4，未实现）**：UVC 枚举完成晚于应用启动（板上实测开机 **7.43s**，晚于自启脚本），启动瞬间 `/dev/videoN` 不存在会让相机**永久降级 null**，须人工重启才有画面。修法=**应用层延迟重扫**：挂到主线程已有定时器（**不新增线程**），启动后窗口内每 2s 重扫一次，成功即平滑切换并停止重扫，始终无摄像头时不改变现有降级行为。验收：真实 reboot 两次，不人工干预自动出画面。
- **调用关系**：face 线程 `poll(hal_camera_fd())` → `hal_camera_frame()`（后端内部 DQBUF 只转最新帧）→ 拷进双帧缓冲 → 主线程 `page_face` 渲染；**必须** `hal_camera_release_frame()`，否则后端停更。

### 5.17 虚位密码实现方案（FR-18）

虚位匹配在 PIN 校验层实现，对调用方透明：

实现要点：

- **滑动窗口**：对输入串的每个起始位置取 `pin_len` 长度子串做定值比对。输入上限 20 位、PIN 4–8 位，最多 17 次比对，开销可忽略。
- **不解密、不反推**：虚位是对**输入**做切分后逐段走 PBKDF2 校验，不是把存储的哈希还原成明文——存储侧仍是 PBKDF2 加盐哈希，**安全性不变**。
- **适用边界**：开锁 PIN 走 `exact=false`；管理员二次确认与动态码走 `exact=true`（依据需求规约 5.5）。
- **开关**：由策略项 `virtual_pin_enable` 控制，默认开启，纳入 `safe_policy_t` 与配置快照。

> 安全权衡：虚位会削弱暴力破解难度（一次 20 位输入相当于同时试多个候选）。对冲手段是 FR-4 的失败锁定，以及禁止在管理员二次确认中使用虚位。这是该特性的固有代价，须在设计与面试表述中明确承认，而非回避。

### 5.18 worker 与 event_bus 职责边界（v1.3 新增）

两者底层机制同源（非主线程产出 → 线程安全队列 → 主线程派发），但接口约定不同、**不得互相替代**：

| | worker（§5.7） | event_bus（§5.8） |
|---|---|---|
| 模型 | 请求-响应：1 个作业 → 1 个 `done` 回调 | 广播：1 个事件 → N 个订阅者 |
| 携带 | 函数指针 + 堆参数（arg 生命周期有约） | POD 定长 payload（按值拷贝） |
| 解决 | **计算下沉**：PBKDF2 / 文件 IO 等阻塞任务 | **状态广播**：模块间解耦通知 |
| 典型 | 用户增删改、策略落盘、网络凭据读写 | 认证状态/结果、人脸事件、MQTT 状态、主题切换 |

使用纪律：

- **不要**用 event_bus 替代 worker 的 `done` 回调——会丢失按作业续体的类型与 arg 生命周期管理；
- **不要**在 worker 的 `fn` 里直接发业务事件替代返回值——结果统一经 `done` 回主线程后，再由主线程决定是否 `publish`；
- 全工程通知/派发机制**只保留这两套**，禁止模块再自建订阅数组或回调链（face_service 自有订阅数组与 `auth_ui_hook` 按接线计划拆除，见 §5.8）。

### 5.19 face 线程 `app/hal/face/face_thread.h`（v1.3 / 步骤 3b 新增）

- **参数**：`dst` 容量须 ≥ `FACE_THREAD_PREVIEW_W * FACE_THREAD_PREVIEW_H * 2` 字节（RGB565）。
- **返回值**：`face_thread_start` 返回 `safe_err_t`；`get_preview` 有比上次更新的帧时拷贝并返回 `true`，否则 `false`（不阻塞）。
- **功能**：单线程 `poll()` 复用 V4L2 video fd 与 FM225 UART fd（§3.4，IO 复用）。相机可读 → 取帧并**只转最新帧** → 写双帧缓冲（新帧覆盖旧帧、满则丢最旧、绝不阻塞采集）；UART 可读 → 读字节喂协议状态机（3c）。产出预览帧供主线程取用，识别结果走 `event_bus_post(EV_FACE_EVENT)`（§5.8）。全程不碰 LVGL。
- **退出**：按 §3.2 / b5 顺序——`request_stop()`（置退出标志 + `STREAMOFF` + 静默在途采集）→ `hal_camera_deinit()`（close fd）→ `face_thread_join()`。线程内 `io` 锁保证关 fd 前无在途采集读到 mmap 缓冲。
- **调用关系**：`app_main` → `face_thread_start`；`app_shutdown` → `request_stop`/`deinit`/`join`；`page_face`（主线程）→ `face_thread_get_preview`。线程计入 §3.3 封顶（第 4 条）。
- **UART fd 接线（步骤 3c 落地）**：`hal_face_init("fm225")` → 后端 `init` 打开串口（`SAFE_FACE_DEV`，默认 `/tmp/fm225_host`，真机 `/dev/ttyUSB0`）并 `termios` 配 115200 8N1 → `hal_face_start` → 后端 `start` 经 `fm225_uart_fd()` 把 fd 交给 `face_thread_set_uart_fd()`（**start 前调用**，face 线程尚未起，无竞争）。fd 归 fm225 后端所有，face 线程只借用读；`app_shutdown` 中 `hal_face_deinit`（后端 close fd）发生在 `face_thread_join` **之后**，保证线程先停再关 fd。UART 可读 → 读字节 → `fm225_proto_feed()`（§5.20）→ 解析出识别结果 → `hal_face_emit`（§5.11 加锁）→ `event_bus_post` 交主线程。

### 5.20 FM225 协议解析器 `app/hal/face/fm225_proto.h`（步骤 3c 新增）

- **设计**：纯状态机——`feed(ctx, buf, n)` 不碰 fd / 串口 / 全局，输入字节流输出帧事件，单测可脱离串口运行（c1）。ctx 由调用方分配（face 线程一个静态 ctx 即可），解析器内部零动态分配，帧缓冲定长（`FM225_MAX_DATA 128`，超长帧按坏帧丢弃重同步）。
- **状态机**：`WAIT_SYNC0 → WAIT_SYNC1 → WAIT_MSGID → WAIT_SIZE_H → WAIT_SIZE_L → WAIT_DATA → WAIT_XOR`。逐字节推进；帧头错位/坏校验时**丢弃已累计字节、从缓冲里重新搜 0xEF 0xAA 重同步**（粘包处理：一次 feed 产出多帧，回调可能连续多次触发）。
- **超时**：帧内任意两字节间隔 > `FM225_INTER_BYTE_TIMEOUT_MS`（默认 200ms，115200 波特率下一字节约 87µs，200ms 已是 2000+ 字节余量）即作废当前半帧回 WAIT_SYNC0——`proto_tick(now_ms)` 由 backend tick（主线程）驱动；feed 时也用调用方传入时间无（face 线程无时钟参数，feed 不含时间，超时判定统一在 tick）。
- **调用关系**：face 线程 `face_uart_drain` → `fm225_proto_feed`；backend_fm225 注册帧回调：REPLY(VERIFY) → `hal_face_emit(FACE_EV_DETECT)`（按 MR_* 码映射 face_reason_t，见下表）；REPLY(ENROLL) → `FACE_EV_ENROLL_DONE`；REPLY(DELUSER) → `FACE_EV_DELETE_DONE`；NOTE(NID_READY) → 心跳（刷新在线时间戳）；其余帧忽略。
- **MR_* → face_reason_t 映射**（手册 REPLY result 码 → 业务原因码）：`MR_SUCCESS(0)` → `FACE_RES_OK`；`MR_FAILED4_LIVENESSCHECK(12)` → `FACE_RES_LIVENESS_FAIL`；`MR_FAILED4_TIMEOUT(13)` → `FACE_RES_TIMEOUT`；verify 的未匹配（MR_FAILED4_UNKNOWNUSER=8 或无匹配用户）→ `FACE_RES_NO_MATCH`；其余错误 → `FACE_RES_ERROR`。
- **单测**：`tests/test_fm225_proto.c` 覆盖手册示例帧（`EF AA 00 00 05 13 00 00 03 1F 0A`）、半包（逐字节喂）、粘包（多帧一次喂）、坏 XOR（重同步后后续帧仍可解）、超时（tick 推进作废半帧）、NOTE READY 帧。

**H>>M 命令字与应答（v1.4 补全，依据手册 V1.7 §六）**：

| 命令 | 字 | 载荷 | 应答 | 超时档 |
|---|---|---|---|---|
| RESET | 0x10 | 无 | REPLY(0x10) | 即时 800ms |
| GET_STATUS | 0x11 | 无 | REPLY(0x11) + 业务数据（模板计数等） | 即时 800ms |
| VERIFY | 0x12 | `pd_rightaway(1B) + timeout(1B)` | **会话**：过程回 NOTE(FACE_STATE)，结束回 REPLY 带 `user_id + user_name[32] + admin + unlockStatus` | **会话档** timeout+2s |
| ENROLL | 0x13 | `admin(1B) + user_name[32] + face_dir(1B) + timeout(1B)` | **会话**：结束回 REPLY 带 `user_id` | **会话档** timeout+2s |
| DELETE_USER / DELETE_ALL | 0x20 / 0x21 | `user_id_heb + user_id_leb` / 无 | REPLY | 即时 800ms |
| FACE RESET | 0x23 | 无 | 清除**录入**状态 | 即时 800ms |

> 术语纪律：**0x10 RESET 与 0x23 FACE RESET 不是一回事**（后者的语义是"清除录入状态"），代码注释不得混用（曾出现注释把 0x10 称作 FACE RESET）。

- **超时分型（D17，真机实测确立）**：`pd_rightaway=0`（解锁成功不断电，电源由应用掌控）；**会话型命令的 pending 超时必须 ≥ 模组 timeout 参数 + 余量**，否则真模组永远被判"无应答"——模拟器秒回应答会掩盖这个语义差异，**只有真模组能暴露**。配套：重发上限 3 次 → 报 `FACE_EV_ERROR` 放弃；轮间再开退避 2s；重发日志**只在"进入重发"这一次状态变化时打一条**（D1③）。
- **应答解析（v1.4 目标项 N1）**：VERIFY 成功应答的 `user_name[32]` 必须解析并向上传递——它是 FR-21 第 1 条防线「验证成功后核对模组返回用户名」的**唯一数据源**（当前只取了 uid 两字节，该防线实际无法实现）。
- **启动对账（v1.4 目标项 N2 → FR-21 防线 3）**：手册提供 `MID_GET_ALL_USERID(0x24)`（取已注册用户数量与 ID 列表）与 `GET USER INFO(0x22)`（按 ID 取详情），用于「模组用户清单 ↔ 本地凭据」对账；孤儿凭据（本地有、模组无）标失效且不用于放行。亦可复用为 FR-23「启动自检」通道。
- **原因码不得坍缩（v1.4 目标项 N3）**：ENROLL / DELETE 的 `MR_*` 必须向上传递，至少能区分 `FACEENROLLED(10)` / `MAXUSER(9)` / `INVALIDPARAM(6)` / `TIMEOUT(13)`——否则 UI 只能报"失败"，且 FR-22「同一张人脸只能绑定一个用户」无从判定。

- **对账清单解析 `fm225_parse_userid_list()`（v1.4 新增，纯函数）**：`GET_ALL_USERID(0x24)` 应答的
  业务 Data 布局是 `user_counts(1B) + users_id[N×2]`（每个 ID 高字节在前，手册 §MID_GET_ALL_USERID）。
  **入参必须是「已剥掉 REPLY 的 mid/result 前缀」的那一段**（即 `fm225_frame_t.data` / `data_len`）——
  把前缀也算进去就会整体错位 2 字节。本工程曾因此把 `user_counts` 读成 `data[2]`：**空模组（载荷全 0）
  恰好掩盖了它**（读错的也是 0），而真机一旦有模板，就会漏掉第一个 uid、把合法凭据误判成孤儿。
  故抽成纯函数并**单测固化边界**：真机形状（201B / counts=2 / uid={1,300}）、空清单、声明量>实际时截断、
  输出缓冲上限、`data=NULL` / `data_len<1`、奇数尾字节（半个 uid 自然忽略）。

### 5.21 网络 `app/hal/hal_net.h`（v1.4 新增）

- **后端选择**：`SAFE_NET_BACKEND` = `iw`（默认，`popen + iw dev <if> scan` 解析）/ `mock` / `netlink`。
- **mock 必须显式 opt-in**，且**界面上要标明是示例数据**——历史事故（D10）：硬编码的假 AP 列表被误判成"扫描到了真实 AP"，违反"UI 只显示真实数据"的项目纪律。**"界面上出现恰好等于源码字面量的取值"是第一反查信号。**
- **不新增线程**（§3.3 封顶）：扫描是阻塞操作，必须经 worker 下沉（§5.7），回调回主线程后再刷 UI。
- **权限**：走 cfg80211/nl80211 的路径需要 `CAP_NET_ADMIN`(+`CAP_NET_RAW`)。PC 验证两条路：`mac80211_hwsim` 造真实 `wlan0`（走真实内核路径而非 mock 数据），或对二进制 `setcap cap_net_admin,cap_net_raw+eip`（**每次重链接后失效，须重执行**）。板级只能写"Buildroot defconfig 已声明含 `iw`，运行时未验证"——**不要把配置声明当作已验证事实**。
- **netlink 第二后端**（同接口的另一个实现，做透档）：价值不在功能而在"同一接口约定两个可互换实现"的 A/B 证据，是分层抽象最有力的展示（见 §9）。

### 5.23 日志上限与滚动语义（v1.4 新增）

- **上限唯一真源**：`APP_CFG_LOG_MAX_DEFAULT`（`config.h`），运行期可用 `SAFE_LOG_MAX` 覆盖；`store.c` **不得再自持一份编译期上限**。历史事故（D6）：一处写 5000、另一处实际生效 500，同一语义两个默认值。
- **滚动语义**：超过上限时"保留**最近 N 条**"，且必须**恰好 N 条**——截断后不得残留空行、不得只剩 N-1 条（差一错误由单测暴露过）。
- **开销目标（D7，未完成）**：当前 `log_append` 每次追加都要 `fgetc` 全量遍历计数（O(文件)，且**就在认证路径上**）；文件饱和后每次追加还会触发 tmp→rename 全量重写（实测 cap=500、追加 158 次 → 259 次 rename / 10.04MB 写，放大约 500×）。目标：①计数改**内存维护**（init 扫一次 + 增量），消除每次追加的全量读；②引入迟滞 `lines > cap + SLACK` 才滚动，把重写摊还到 SLACK 次（摊还 O(1)/次）。**在该优化落地前不得放大 cap**（500→5000 会让单次重写 38.5KB→385KB、洪峰 6MB→60MB）。
- 记一条与规约无关但常被误判的事实：**日志文件路径本身没有 fsync**（fsync 只在用户/策略的原子替换写路径上），因此刷屏的代价是页缓存回写与 rename 抖动 + CPU，**不是**同步 flash 磨损。
- **语义**：日志条数是"记录条数"，不等于"认证尝试次数"（一次活体失败会同时落 `ALARM` 与 `DENY` 两条，语义与读者不同，**保留双记**）；因此 UI 用"今日记录"而非"今日尝试"。日志类型字符串的**大小写在读写两侧必须完全一致**（大写 `UNLOCK` 曾与查询侧小写 `unlock` 失配，导致"最后开启"恒为空）。

3. 订阅 `safe/#`；
4. 向 `safe/cmd` 发 `{"cmd":"query_status","req_id":"t1"}`；
5. 约 20ms 内 `safe/log` 收到回执，其中连接在线字段为 1 即端到端通。

### 7.5 加密与身份层（FR-25 双向 TLS，需求 v1.6 定案）

**可插拔加密层 `tls_stream`（明文进 / 明文出，上层无感知）**：

```c
/* tls_stream.h —— 接口恒定，后端构建期二选一 */
int  tls_stream_connect(const char *host, int port, const tls_conf_t *cfg); /* cfg=NULL 走明文恒等后端 */
int  tls_stream_write(const uint8_t *buf, size_t len);                      /* 明文进 */
int  tls_stream_read(uint8_t *buf, size_t cap, int timeout_ms);             /* 明文出 */
void tls_stream_close(void);
```

- **后端 A（默认，恒等）**：直接透传 socket，行为与明文完全一致——加密关闭即此态，业务代码与数据零改动。
- **后端 B（mbedTLS）**：双向 TLS。校验 broker 证书（自签 CA + ECDSA + SAN 含 broker IP），同时出示设备客户端证书；任一校验失败**拒绝连接**。

**证书体系与生命周期（自签 CA，全流程项目内完成）**：

| 环节 | 方案 |
|---|---|
| 签发 | 离线生成自签 CA；broker 与手机各持 CA 签发的 **ECDSA** 证书（broker 证书 SAN 必须含 broker IP；不用 RSA2048——A7 握手慢一个量级） |
| 预置 | 设备与手机预置同一信任根 CA；客户端证书经本地管理员授权下发（安全预置流程） |
| 续期 | 证书带有效期，到期前重签并预置（演示期可配长有效期降低频次） |
| 吊销 | 移出 broker 信任列表即吊销，**立即生效**；已吊销证书的连入必须被拒（§10 验收） |

**与 FR-24 的关系（互补不互替）**：双向 TLS 解决「链路加密 + 端点身份」（**谁可以连**）；FR-24 应用层凭据 + 主题 ACL + 动态码分级解决「用户授权」（**连上后能干什么、接管操作要不要动态码**）。两者均保留，缺一不可。

**防重放**：req_id 去重 + 接收序号窗口为主；RTC 就位后叠加时间戳 ±5s 辅助校验（不单独依赖绝对时钟）。

**构建**：mbedTLS 交叉编译进 `third_party/`；`SAFE_FEATURE_TLS` 开关（关 = 恒等后端，业务与既有数据无感，§10 验收「加密开关与业务无感」）。

## 11. 运行期守护：独立 supervisor + 看门狗（v1.6 新增）

### 11.1 决策摘要（ADR-WATCHDOG-01）

| 项 | 内容 |
|---|---|
| 场景 | 设备长期无人值守运行；进程崩溃、卡死或被杀后设备「变砖」、不可自恢复 |
| 决策 | **独立 supervisor 进程**（fork/exec + waitpid + 滑动窗口限速 + 安全态）+ **应用主循环心跳喂狗**（硬件看门狗） |
| 理由 | 应用崩溃时自身状态已不可信（堆损坏/死锁），自救不可靠；父进程只依赖内核的 fork/waitpid 语义，能在子进程任何死法下拿到通知。喂狗放在主循环，是因为只有主循环知道「业务还活着」——卡死即停喂，硬件在超时后复位设备 |
| 代价 | 多一个进程与一个 HAL 模块要维护；PC 无 /dev/watchdog 时走 null 后端（无复位能力，仅验证调用链与节流逻辑） |
| 未选方案 | ① S05 守护循环 / inittab respawn：几行搞定，但无重启限速、无安全态；② systemd：单应用设备过重 |
| 状态 | 代码已落地并通过 PC/交叉编译 + 三组行为测试；**板上真狗待验**（板子未接入） |

### 11.2 看门狗接口 `app/hal/hal_watchdog.h`

五个接口：`init(timeout_ms)` / `start` / `kick` / `stop` / `deinit`，外加 `kick_count`（可观测）。

约定要点：

1. `init` 只打开设备、设定超时，**不开始喂狗**；`start` 之后才要求周期性 `kick`；
2. `kick` 由主循环按心跳调用，分发层按 `SAFE_WATCHDOG_KICK_MS`（默认 1000ms）节流——主循环 20ms 一拍也不会把系统调用打满，卡死检测粒度仍为 1 秒，远小于默认 15 秒超时；
3. **正常退出前必须 `stop`**（向驱动写魔法字符 `V` 停表），否则关机或重启应用时会被硬件误复位；
4. 后端三个：`backend_linux.c`（/dev/watchdog 真狗）、`backend_file.c`（软狗：写心跳文件）、
   `backend_none.c`（PC / 无权限占位）。未指定 `SAFE_WATCHDOG_BACKEND` 时按
   **linux → file → null** 自动降级；指定时只试该后端，失败降级 null——与相机/时间模块同构。
5. **软狗不是硬件狗的等价替代**（v1.8 补）：软狗覆盖「进程活着但主循环卡死」
   （心跳停 → supervisor 判超时 → 杀掉重启）；**不覆盖**内核 panic、整机死机、
   supervisor 自身死亡、断电。要补这一层只能开 SoC 内置 WDOG（i.MX6ULL 有 WDOG1/2，
   需内核 `CONFIG_IMX2_WDT` + 设备树使能）或加外置看门狗芯片。
   本项目板子当前没有 `/dev/watchdog`，实际走 file 后端。

调用顺序（`main.c`）：`platform_init_io` → **watchdog init+start** → `app_main` → 主循环每拍 `hal_watchdog_kick()` → `app_shutdown` → **watchdog stop+deinit**。watchdog 排在 `app_main` 之前，是为了让后续初始化卡死也能被复位。

### 11.3 supervisor `tools/supervisor/safe_supervisor.c`（v1.8 补齐）

- 独立进程，**不链接任何应用代码**；手工编译：
  `cc -O2 -Wall -Wextra -o safe_supervisor safe_supervisor.c`
- 行为：
  - 正常退出（code 0，或被 SIGTERM/SIGINT 停止）→ 不重启；异常（非 0、或 SIGSEGV/SIGABRT 等）→ 重启；
  - 滑动窗口（默认 5 次/60s）超限 → **进入安全态**：执行 `/etc/safe/safe_state.sh`
    （真锁接入后指向「拉低 GPIO、保持锁闭」），然后**接管 `/dev/watchdog` 持续喂狗**，
    保持设备运行且锁闭，直到收到 SIGTERM；
  - 指数退避：连续崩溃时重启间隔按 2 倍递增，上限为 `--restart-delay` 的 8 倍；
  - supervisor 收到 SIGTERM/SIGINT → 转发给应用，宽限 `--grace` 秒仍未退出则 SIGKILL；
  - 软狗：`--heartbeat` 每 1s 检查心跳文件 mtime，超过 `--heartbeat-timeout`（默认 5s）
    未更新 → SIGTERM，宽限后 SIGKILL，并按异常重启；启动后 `--heartbeat-startup`
    （默认 20s）内文件未出现不判死；文件内容为 `stopped` 时不重启。
  - 单实例：`flock` 锁文件，重复启动退出码 3（避免两个 supervisor 抢应用与看门狗）。
- 参数：`--app` `--max-restarts` `--window` `--grace` `--restart-delay` `--safe-cmd`
  `--watchdog` `--log` `--log-max` `--app-log` `--status` `--pidfile` `--daemon`
  `--heartbeat` `--heartbeat-timeout` `--heartbeat-startup`，`--` 之后为应用参数。
- 退出码：0 正常退出（未重启）；1 参数或启动错误；2 进入安全态；3 已有实例。
- 可观测：`--status` 原子写 key=value（pid/state/restarts/last_exit）；`--log` 按大小轮转
  （默认 1MB）；`--app-log` 单独接应用 stdout/stderr（`--daemon` 下 stdio 是 /dev/null，
  不接就丢日志）。
- 测试：`tests/test_supervisor.sh`（8 组进程级用例，随 ctest 跑）。

### 11.5 两层保护的分工（v1.8 新增）

| 层 | 覆盖的故障 | 不覆盖 |
|---|---|---|
| supervisor | 进程崩溃、非 0 退出、配置错误导致启动中止 | 进程存活但卡死 |
| 硬件看门狗 | 主循环卡死、死锁、调度饥饿（停喂 → 复位整机） | 崩溃后拉起 |

**为什么安全态必须由 supervisor 接管看门狗**：应用崩溃后 fd 关闭，但驱动仍在计时；
15s 后整机复位 → init 重新拉起 supervisor → 再次崩溃，形成整机级重启循环。
接管后设备保持运行、锁闭、日志可查，等人来修——这才是安全设备应有的失效方向。
