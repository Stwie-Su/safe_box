## 一、活文档（每次任务按需改）

| 文件 | 回答什么 | 什么时候**必须**改 |
|---|---|---|
| `需求规约.md` | **做什么**（FR-x / NFR-x，带优先级与验收口径） | 需求变更、增删功能、改验收口径 |
| `技术路线规约.md` | **怎么做**（分层、线程模型、接口签名、并发纪律） | 接口签名变更、架构调整、并发纪律变化 |
| `开发进度.md` | **做到哪**（唯一进度真源；§0 是机器可读当前步） | 每完成一个任务新增一节 |
| `Bug台账.md` | **踩过什么坑**（按分层一行一条） | **每次任务后必更新**（含自己引入的回归） |
| `README.md` | 本导航 | 目录结构变化时 |

**改动顺序是硬约束**：需求规约 → 技术路线规约 → 代码。
先改代码再补文档，是本项目反复吃亏的根源（补的时候需求已经变形，文档变成事后追认）。

### 改文档前先做的两件事（都栽过）

1. `grep -n '^## ' 开发进度.md` 查下一个可用编号 —— 撞号撞过两次。
2. `grep -rn '^| D' Bug台账.md | tail -20` 查下一个 D 编号 —— 同样别凭记忆。

## 五、每次任务收尾前逐条过

1. `开发进度.md` 新增一节（先查编号）；
2. `Bug台账.md` 有缺陷就加一行 —— **包括自己这次引入的回归**；
3. 需求 / 接口变了 → 先回改需求规约 / 技术路线规约，再动代码；
4. `git status --short | grep '^??'` 查孤儿未跟踪文件（本项目反复出现的坑）；
5. `ctest` 全绿 + 交叉构建通过后再提交；
6. 可复现性：CMakeLists / `safe_add_test` 引用的 `.c` 必须都在 `git ls-files` 里
   （`ctest` 全绿**证明不了**仓库可复现 —— 曾有多个 `.c` 被构建引用却从未 `git add`）。
