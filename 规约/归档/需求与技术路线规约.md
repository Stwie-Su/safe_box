## 1. 规约定位与范围

### 1.1 规约目标

本项目**首要服务于秋招简历**（目标岗位：嵌入式 Linux 应用 / BSP，华为成研所、中科创达等）。因此规约的取舍标准是：

- **技术深度优先**：核心模块要能讲清设计动机、权衡过程与边界条件，而非堆砌功能数量。
- **证据可复现**：每条亮点都能对应到代码、测试或实测数据（验收记录、帧率数据、日志）。
- **范围克制**：不承诺无法闭环验证的功能；硬件不在手上的部分保持 HAL 抽象占位。

## 2. 项目定位与场景

多用户共享保险柜系统，面向民宿/短租、小型办公室、多成员家庭等「多人共用同一柜体」场景。

核心链路：**FM225 双目人脸识别 + TOTP 动态密码双因子**认证，配套 LVGL 本地界面、MQTT 远程监控与 RPC 远程指令。

关键约束：

- **离线优先**：认证链路不依赖外网，断网仍可正常开锁。
- **局域网远程**：仅局域网内可通过 MQTT 客户端查看状态、下发开锁与管理指令。
- **硬件受限**：单核 Cortex-A7，一切性能设计以此为前提。

## 3. 架构原则（可维护性与易扩展性）

本节是全项目的**硬约束**，任何新增代码必须遵守。用户明确要求把可维护性与易扩展性作为贯穿要求。

### 3.1 分层与依赖方向

```
ui/          表现层：页面、主题、控件
   ↓ 依赖（单向）
core/        业务层：auth / store / remote / support
   ↓ 依赖（单向）
hal/         硬件抽象层：face / actuator / camera / time
   ↓
platform/    平台适配：SDL(PC) / FBDEV(板子)
```

依赖方向**严格单向向下**，禁止反向依赖与跨层直连：

- `ui` 不得直接调用 `hal`，只能通过 `core` 暴露的业务接口。
- `core` 不得感知具体硬件后端实现，只面向 HAL 接口编程。
- `hal` 不得引用 `ui` 或 `core` 的内部状态。

### 3.2 HAL 后端注册机制

所有硬件能力通过**函数指针表（后端注册）**接入，业务层在初始化时选择具体实现：

| 能力 | 已有后端 | 规划后端 |
|---|---|---|
| face（人脸比对） | `fake` / `none` | `fm225` |
| actuator（开锁执行器） | `mock` | `gpio`（硬件占位中不实现） |
| camera（图像采集） | `null` | `uvc`（FM225 视频流） |
| time（时间源） | `sys` | `rtc` |

**扩展方式**：新增硬件 = 新增一个 `.c` 实现 HAL 接口并注册，**不修改任何业务层代码**。这是易扩展性的核心落点，也是面试重点。

### 3.3 配置与外观集中化

- **配置集中**：所有可调参数收敛在 `config.c`，支持环境变量覆盖（`SAFE_MQTT_HOST` / `SAFE_MQTT_PORT` 等）。禁止在业务代码中散落魔法数字。
- **主题 token 化**：全部 UI 控件通过 `theme_color()` 与全局 `lv_style_t` 取色，**禁止硬编码 hex**；换主题无需重建页面。默认主题为「月白」（index 1）。
- **错误码集中**：RPC 错误码、认证返回码统一定义，禁止各模块自造。

### 3.4 模块与测试约束

- 新增 `core` 逻辑必须配套单元测试（`tests/`，ctest）。
- 新增远程指令必须配套 headless MQTT 验收用例。
- 构建产物与运行时数据不得入库（`.gitignore` 已覆盖 `build/` `data/`）。

## 4. 角色与认证模型

| 角色 | 说明 | 关键权限 |
|---|---|---|
| 管理员 admin | 柜体 owner / 运维 | 用户增删改、策略调整、设置中枢二次验证、远程开锁 |
| 长期用户 user | 家庭成员 / 员工 | 人脸 + PIN/OTP 正常开锁 |
| 临时用户 temp | 房客 / 访客 | 限时限次开锁，到期/用量耗尽自动失效（FR-9，规划中） |

认证方式：纯数字 **PIN（4–8 位）**，`auth_method` 字段预留 `"otp"`。

人脸置信度三档策略（默认 `score_high=85`、`score_mid=60`）：

| 置信度 | 结果 | 说明 |
|---|---|---|
| ≥ `score_high` | UNLOCK | 直接开锁 |
| ≥ `score_mid` | WAIT_OTP | 进入动态码二次确认态 |
| < `score_mid` | DENY | 拒绝 |

敏感操作二次确认规则（FR-14）：

- **仅当修改「管理员」密码时**，保存前强制弹动态码（TOTP）键盘校验（`backend_admin_verify_totp`）。
- 普通用户改密不要求动态码，仅校验旧 PIN。
- 删除用户走管理员 PIN 二次验证。

## 6. 技术路线与里程碑

### 6.1 总体节奏

```
Sprint1（已完成）  PC/SDL 验证：状态机 · TOTP · 存储 · UI · MQTT/RPC
      ↓
Sprint2            上板打通：交叉构建 + FBDEV + 部署（硬件仍 mock/null）
      ↓
Sprint3            FM225 视频 + 多线程重构
                   ├─ 先在 Ubuntu（PC）环境验证流水线与线程模型
                   └─ 验证通过后再移植上板接真 FM225
      ↓
Sprint4            收尾打磨：可靠性四项 + 文档 + 简历材料
```

排布理由：先取得「程序在板子上真跑起来」这一硬证据，再攻含金量最高但风险也最高的视频与多线程；多线程部分坚持**先在 Ubuntu 环境验证再上板**，把硬件不确定性隔离在外，符合用户明确的节奏要求。

### 6.2 Sprint2：上板打通

目标：同一份 `app/` 源码在 i.MX6ULL 上以 FBDEV 后端运行，硬件后端保持占位。

| 要点 | 方案 |
|---|---|
| 工具链 | Buildroot 自带 `arm-linux-gnueabihf`，经 `cmake/user_cross_compile_setup.cmake` 配置 |
| 构建 | `build_board` 目录，defconfig 复用 `configs/get_started.defconfig` |
| 显示 | FBDEV 后端；`CONFIG_LV_COLOR_DEPTH_32=y` 对齐 fb0 实际 32bpp |
| 绘制 | `CONFIG_LV_DRAW_SW_DRAW_UNIT_CNT=1`（单核多线程为负优化） |
| 触摸 | Goodix 上报已是屏幕像素，标定用恒等 `(0,0,1023,599)`，支持 `LV_TOUCH_CAL_*` 覆盖 |
| 中文 | `CONFIG_LV_USE_FREETYPE=y` + `/usr/share/fonts/opentype/noto/NotoSansCJK-Regular.ttc` |
| 息屏 | 内核 `consoleblank=600` 只读，应用层用 `KDSETMODE` + `FBIOBLANK` 轮询保活 |
| 部署 | ADB 推送替换 `/usr/share/lvgl/lvglsim`，`killall` 重启（板子无 `pkill`） |

**部署验证四查**：PID 已变化、`/proc/<pid>/exe` 非 `(deleted)`、日志有新打印、配置打印核对。

### 6.3 Sprint3：FM225 视频与多线程

#### 6.3.1 FM225 双通道对接

选定方案：**UVC 取流做预览 + 串口拿识别结果**，两条独立数据通路。

| 通道 | 用途 | 技术栈 | 产出 |
|---|---|---|---|
| USB UVC（视频） | LVGL 小窗实时预览 | V4L2 `mmap` 采集 | 480×272 图像帧 |
| 串口（控制） | 获取识别结果与人脸分数 | termios + 协议解析 | 注入 `face_service_inject` |

识别算法在模块内部完成，主控只取结果——单核 A7 不具备本地跑人脸检测/活体的算力，**不在主控做算法**。

硬件规格待核实清单（上板前必须确认）：

- USB VID/PID，是否标准 UVC（决定能否用通用 V4L2 路径）
- 视频流格式（YUYV / MJPEG）与原生分辨率、帧率
- 串口波特率、帧格式（帧头 / 长度 / 校验）与识别结果报文定义

#### 6.3.2 视频流水线与性能预算

```
V4L2 采集 → 格式转换(YUYV→RGB565) → 缩放/裁剪 → LVGL 小窗渲染
                ↑ 主要 CPU 热点          ↑ 目标 480×272
```

目标指标：**小窗预览 480×272 @ ≥20fps**（单核 A7 现实可行，且保留 UI 余量）。

| 环节 | 预算（每帧 50ms） | 优化手段 |
|---|---|---|
| V4L2 采集 | 低 | `mmap` 零拷贝，避免 `read()` 内存复制 |
| 格式转换 | 主要热点 | 查表法 / NEON 加速，避免逐像素浮点运算 |
| 缩放 | 中 | 整数倍缩放优先，必要时最近邻 |
| LVGL 渲染 | 中 | 仅刷新脏区域，双缓冲避免撕裂 |

调优先测量：用 `perf` / `gprof` 定位热点后再优化，禁止凭猜测改代码。

#### 6.3.3 线程模型

选定：**采集线程 + 识别线程 + UI 主线程**。

| 线程 | 职责 | 关键点 |
|---|---|---|
| 采集线程 | V4L2 阻塞取帧，写入环形缓冲 | 生产者；缓冲满时丢弃最旧帧，绝不阻塞采集 |
| 识别线程 | 串口协议解析 / 帧处理，产出分数与事件 | 消费者；结果经队列交给业务层 |
| UI 主线程 | LVGL 渲染 + `rpc_poll` 20ms 泵 | 只做渲染与轻量分发，不做重计算 |

同步约束：

- 帧缓冲用**双帧或环形缓冲**，配互斥量 + 条件变量；临界区内不做格式转换。
- 识别结果通过队列交给 UI，**不在识别线程直接操作 LVGL 对象**（LVGL 非线程安全）。
- UI 线程保持轻载，任何耗时操作下沉到工作线程。

#### 6.3.4 先在 Ubuntu 验证再上板

在 VM/PC 上先验证整条流水线与线程模型：

1. 用普通 UVC 摄像头，或 `v4l2loopback` 虚拟设备构造可控视频源。
2. 串口侧可用伪终端（`socat` 建立虚拟串口对）模拟 FM225 协议报文。
3. 验证帧率、CPU 占用、线程同步正确性后，再接真 FM225 上板。

这样把「线程 bug」「性能瓶颈」「硬件协议不确定」三类风险分离，上板阶段只面对硬件差异。

## 8. 关键接口约定

### 8.1 HAL 后端注册

能力以函数指针表注册，业务层面向接口编程，新增后端不改业务代码（见 3.2）。

### 8.2 认证状态机

状态：`IDLE` → `DETECTING` → `UNLOCKED` / `WAIT_OTP` / `DENY` / `LOCKOUT`。

关键约定：

- 连续失败 `max_failed=5` 进入 `LOCKOUT`，持续 `lock_seconds`。
- **锁定期间一律拒绝开锁**，包括管理员远程指令（返回 `3001`）——先拦截再校验 OTP，避免「锁定期间仅凭动态码即可远程开锁」的越权路径。
- `WAIT_OTP` 支持升级路径：同待确认用户的高置信度帧可直接开锁，不消耗 OTP。

### 8.3 TOTP 双因子

- 遵循 RFC6238，校验窗口 ±1。
- **严格递增计数器**：`c <= last_counter` 即判重放，实现一码一用。
- 注意：同一 30s 窗口内重复用同一码会判重放，这是设计行为而非缺陷（测试脚本需按窗口构造用例）。

### 8.4 MQTT / RPC 通道

Broker：VM 上 mosquitto 常驻，`listener 1883 0.0.0.0`，`allow_anonymous true`。

| 方向 | Topic | QoS | 内容 |
|---|---|---|---|
| 下行 | `safe/cmd` | 1 | 手机/客户端下发的 RPC 指令 |
| 上行 | `safe/log` | 1 | 指令回执 + 事件上报 |
| 上行 | `safe/status` | 0 | 状态快照 |

报文结构：`{"cmd": "...", "req_id": "...", "params": {...}}`

| 指令 | 是否需管理员 OTP | 说明 |
|---|---|---|
| `query_status` | 否 | 立即回状态快照 |
| `remote_unlock` | 带 `params.otp` 直接开；不带回 `2001` 触发板端弹码 | 锁定态返回 `3001` |
| `add_user` / `del_user` / `set_face_enable` / `set_threshold` | 是 | 敏感操作，缺失或不合法回 `2001` / `2002` |
| `sync_time` | 否 | `params.ts` 为 Unix 秒 |
| `submit_otp`（调试） | 否 | 受 `WAIT_OTP` 门控，非该态调用被忽略 |
| `inject_score`（调试） | 否 | 注入人脸分数，用于 headless 验收 |

错误码分段：`1xxx` 参数与解析、`2xxx` 认证与权限、`3xxx` 状态冲突。

线程模型：RPC 不注册回调，消息进入内部队列，由主线程 `rpc_poll()`（20ms 泵）取走分发。

### 8.5 存储层

- JSON 文件 + 统一抽象层（`astore_*`）。
- PIN 用 PBKDF2-SHA256 哈希，每用户随机盐，明文不落盘。
- 写入必须走原子写（第 7 节）。

## 10. 验收标准

分层验收，每层可独立复现。

| 层级 | 手段 | 当前状态 | 目标 |
|---|---|---|---|
| 单元 | `ctest` | 4/4 全绿（totp / auth_fsm / store / layers） | 新增 `core` 逻辑必须配套 |

| 上板 | FBDEV 实跑 + 四查 | 未开始（Sprint2） | 板端可交互、日志正常 |
| 视频 | 帧率与 CPU 实测 | 未开始（Sprint3） | 480×272 @≥20fps，UI 不卡 |
| 手机端 | MQTTX 订阅 `safe/#` + 发 `safe/cmd` | 通道已通（需 app 运行） | 指令回执可验证 |

**手机验证最小闭环**（不依赖专用 App）：

1. VM 起应用：`xvfb-run -a ./build_pc/bin/lvglsim &`
2. 手机 MQTTX 连接 `192.168.150.139:1883`（匿名）
3. 订阅 `safe/#`
4. 发布到 `safe/cmd`：`{"cmd":"query_status","req_id":"t1"}`
5. 约 20ms 内 `safe/log` 收到状态回执（`mqtt_online:1` 即端到端通）

前提：手机与 VM 同网段可达；应用需处于运行状态（顶栏 MQTT 小圆点为绿）。

## 11. 技术亮点与面试展开话术

每个亮点给出定位、追问预判与回答要点，供简历深挖与面试复习使用。

### 11.1 分层架构与 HAL 后端注册

- **一句话定位**：把硬件差异收敛在函数指针表后面，业务层只面向接口编程，同一份源码跑 PC 与板子。
- **会被追问**：新增一种摄像头要改多少代码？PC 和板子差异怎么隔离？
- **回答要点**：新增后端只加一个 `.c` 实现 HAL 接口并注册，业务层零改动；平台差异由 `platform/` 与构建矩阵吸收（`build_pc` 用 SDL、`build_board` 用 FBDEV）。
- **本项目证据**：face / actuator / camera / time 四类后端已可插拔；分层重构已入库。

### 11.2 多线程并发架构

- **一句话定位**：采集、识别、UI 三线程解耦，环形缓冲交接帧数据，识别与网络不阻塞渲染。
- **会被追问**：为什么这么分线程？线程安全怎么保证？LVGL 线程安全吗？
- **回答要点**：按「阻塞源」划分——V4L2 取帧与串口读写会阻塞，必须独立；LVGL **非线程安全**，所有 UI 操作收敛到主线程，工作线程只通过队列投递结果；临界区内不做重计算。
- **本项目证据**：当前为单线程 + 20ms 轮询泵，Sprint3 重构的目标形态即为本模型。

### 11.3 视频流水线与单核性能调优

- **一句话定位**：在单核 A7 上把 V4L2 采集到 LVGL 渲染的整条链路压进每帧 50ms 预算。
- **会被追问**：帧率上不去怎么定位？为什么不用多线程加速？格式转换怎么优化？
- **回答要点**：**先测量后优化**（`perf` / `gprof` 找热点），主要开销在 YUYV→RGB565 转换，用查表 / NEON 消除逐像素浮点；采集走 `mmap` 零拷贝；单核上多绘制线程是负优化，故 `DRAW_UNIT_CNT=1`，优化方向是减少每像素开销而非加线程。
- **本项目证据**：目标指标 480×272@≥20fps；Sprint3 先在 Ubuntu 用 v4l2loopback 验证再上板。

### 11.4 认证状态机与防暴力锁定

- **一句话定位**：三档置信度驱动的状态机，配连续失败锁定，且锁定优先级高于一切开箱请求。
- **会被追问**：锁定期间管理员远程开锁能不能开？为什么？中置信度为什么还要动态码？
- **回答要点**：**不能，且这是刻意的**——先判 `LOCKOUT` 再校验 OTP，否则会留下「锁定期间仅凭动态码即可远程开锁」的越权路径；中置信度进入 `WAIT_OTP` 是双因子补强，同时保留高置信度帧的升级路径避免误伤。
- **本项目证据**：`LOCKOUT` 返回 `3001`；21/21 headless 验收覆盖锁定拦截。

### 11.5 TOTP 双因子与防重放

- **一句话定位**：RFC6238 动态码 + 严格递增计数器，做到一码一用。
- **会被追问**：±1 窗口是什么？怎么防重放？时钟不准怎么办？
- **回答要点**：±1 窗口容忍设备时钟偏差；防重放靠**严格递增计数器**（`c <= last_counter` 即拒），而非单纯比时间；时间源 `rtc`/`sys` 可切换，`sync_time` 指令支持对时。
- **本项目证据**：验收 T6 覆盖当前窗口码、同码重放、`+1` 窗口三类用例。

### 11.6 MQTT/RPC 远程通道与手机管理

- **一句话定位**：局域网内用 MQTT 做双向通道，敏感指令强制 OTP 门控，回执带错误码可追溯。
- **会被追问**：QoS 怎么选？断线怎么办？敏感指令怎么防滥用？
- **回答要点**：指令 QoS 1 保证至少一次；状态快照 QoS 0（丢了下次还有）；断线用指数退避自管重连（`automaticReconnect=0`），离线事件缓存待恢复补传；敏感指令缺 OTP 直接回 `2001`，不执行。
- **本项目证据**：topic `safe/cmd` / `safe/log` / `safe/status`；九类指令；错误码分段；手机 MQTTX 可验证最小闭环。

### 11.7 可靠性工程

- **一句话定位**：把「掉电不坏、断网不丢、挂了能起、日志不撑爆」做成底线能力。
- **会被追问**：写 JSON 写到一半掉电怎么办？板子存储小，日志一直追加怎么办？
- **回答要点**：原子写（临时文件 → `fsync` → `rename`）保证配置文件要么旧要么新；JSONL 追加配容量上限与轮转；进程守护 + 硬件看门狗兜底异常退出。
- **本项目证据**：Sprint4 落地项，当前 PIN 已用 PBKDF2-SHA256 加盐哈希。
