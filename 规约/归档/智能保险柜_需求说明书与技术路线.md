## 1. 项目概述

### 1.1 项目定位

基于 i.MX6ULL Pro 的**多用户共享保险柜系统**。

面向**多人共用同一保险柜**的场景：民宿/短租（房客流动）、
小型办公室（员工离职交接）、家庭成员多且需要权限分级的家庭。

核心是 **FM225 双目人脸识别 + TOTP 动态密码**双因子认证，
配套 LVGL 本地界面、MQTT 远程监控与 RPC 远程指令，
以及**限时/限次的临时授权**（房客退房自动失效）。

系统在开发板上**离线运行**（认证链路不依赖外网）；
局域网内可通过 MQTT 客户端（手机 MQTTX）查看状态、下发开锁与管理指令。

> **为什么不是"家庭保险柜"**：见 1.5 场景适配性分析。
> 这是本项目最重要的定位判断，直接影响后续所有功能的合理性。

### 1.2 当前基线

| 能力 | 状态 | 说明 |
|---|---|---|
| LVGL UI 框架 | ✅ 已有 | Ubuntu Simulator 跑通，板子已验证触摸/显示 |
| 静态密码解锁 | ✅ 已有 | 4–8 位 PIN |
| 用户管理 | ✅ 已有 | 管理员可设置"谁的密码有效/无效" |
| 板子部署 | ✅ 已有 | 交叉编译、ADB 部署、开机自启全链路已通 |
| FM225 双目模组 | ❌ 未购 | 所有真实人脸数据缺失 |
| DS3231 外部 RTC | ❌ 未购 | TOTP 时间基准存在风险，见 7.1 |

### 1.3 本次策略

> **所有能在 Ubuntu 上验证的纯软件逻辑全部前置，FM225 到货后只做硬件对接。**

这一条是整个路线的组织原则。它的直接推论是：

- 人脸数据必须抽象成"分数 + face_id"的接口，模拟器注入和真实模组解析**产出同一种数据结构**
- 业务逻辑不得感知数据来源，否则硬件到货时要改业务代码
- 阶段 1 结束时，除"真实人脸采集"外，整条链路应可完整演示

### 1.4 明确不做的范围

| 不做项 | 理由 |
|---|---|
| 公网穿透 / 云服务器 / 域名备案 | 面试非必需，投入产出比低 |
| 微信小程序 | P2。MQTTX 已足够演示远程闭环 |
| 统一电源管理、电池备份 | 后期 |
| 指纹 / NFC / 4G / CAN 等扩展外设 | 分散精力 |

### 1.5 场景适配性分析

**这一段是本项目最重要的设计判断，建议在面试时主动讲出来。**

最初的需求是"家庭保险柜"。按这个定位推演，会发现几个功能在家庭场景下站不住：

| 功能 | 家庭场景的问题 |
|---|---|
| 人脸识别 | 家庭保险柜**低频使用**（一周甚至一月一次）。人脸的价值在"高频无感通行"，低频下相对密码优势接近于零 |
| TOTP 二次验证 | 掏手机 + 开 App + 输 6 位码，比直接输密码还慢。老人小孩基本用不了 |
| 中分区要求 TOTP | 出现在"识别不顺利"时，等于把两个糟糕体验叠加。手机人脸解锁的做法是**不确定就降级到 PIN**，不会升级到更麻烦的方式 |
| 远程开锁 | 保险柜卖的是**物理防护**。远程开锁等于多了一条不接触实体就能打开的路径。而且人在家为什么要远程开锁？ |
| 局域网 MQTT | 局域网意味着人必须在家。那"远程"功能的价值在哪？真正在外的需求（柜子被撬了吗）恰恰需要公网 |

**结论**：这套设计的骨架其实是**企业门禁/考勤系统**的逻辑——
高频、多用户、需要审计、需要远程管理。
把它套在"家庭保险柜"上是错配。

**解法**：定位改为**多用户共享保险柜**。一词之差，所有功能立刻自洽：

| 功能 | 家庭保险柜 | 共享保险柜（民宿/办公室） |
|---|---|---|
| 多用户 + 权限开关 | 三五口人，有点重 | 房客流动、员工离职，**必需** |
| TOTP 二次验证 | 老人小孩用不了 | 管理员是成年人，**合理** |
| MQTT 远程管理 | 人在家要它干嘛 | 房东不在现场，**必需** |
| 审计日志 | 家里人，查谁？ | 多用户交接追溯，**必需** |
| 限时/临时权限 | 偶尔 | 房客退房自动失效，**核心** |

**一个额外证据**：第一期的用户表已经实现了 `admin` / `user` / `temp` 三级角色，
且 `temp` 支持**限次 + 限时**。这个设计在家庭场景下几乎用不上
（家里哪来的临时用户），但在民宿/短租场景下是核心能力。
说明这套数据模型从一开始就更贴合共享场景。

**面试话术**：

> "这个系统的定位是**多用户共享场景下的保险柜**，
> 比如民宿短租、小型办公室，或者家庭成员多且需要权限分级的家庭。
> 所以它必须解决的是：多通道认证、权限分级、临时授权、操作审计和远程管理。
> 我也考虑过纯家庭场景，但那样人脸识别、TOTP、远程管理这些都会变成过度设计。"

## 2. 需求规格

### 2.1 用户角色与权限

对齐共享场景，采用三级角色：

| 角色 | 典型身份 | 权限 |
|---|---|---|
| **管理员** | 房东、老板、户主 | 全部权限：开锁三通道 + 用户增删改 + 切换各通道有效性 + 修改置信度阈值 + 查看/导出日志 + 发放临时授权 |
| **长期用户** | 家庭成员、员工、长租客 | 开锁三通道（人脸/静态密码/动态密码）、查看自己的开锁记录 |
| **临时用户** | 短租客、访客、家政 | 开锁（按管理员指定的通道）+ **限时**（到期自动失效）+ **限次**（次数用尽失效） |

**与第一期的关系**：第一期的用户表已实现 `admin` / `user` / `temp` 三级，
且 `temp` 支持限次 + 限时。本角色体系**直接沿用，不重做**，
只需在用户管理页增加临时授权的有效期/次数设置（见 FR-9）。

**权限实现方式**：管理员操作前需输入管理员 PIN 或 TOTP（见 FR-3 的二次确认机制）。

**硬约束**（沿用第一期，不得破坏）：

- 删除用户后必须仍保留至少 1 个 enabled 管理员，防止系统被锁死
- 临时用户到期/次数用尽后自动置为 disabled，**不删除记录**（保留审计线索）

### 2.2 功能需求

需求编号规则 `FR-xx`，便于测试与追溯。

#### FR-1 开锁认证（三通道，共用一张用户表）

| 通道 | 校验逻辑 | 状态 |
|---|---|---|
| 静态密码 | 输入密码 → 匹配 `password` → 检查 `password_enable` | 已有 |
| 人脸识别 | FM225 返回 face_id + 置信度 → 映射用户 → 检查 `face_enable` → 按置信度分级 | 新增（先模拟） |
| 动态密码 | 输入 6 位码 → 用该用户 `totp_secret` 本地 TOTP 验证 → 检查 `totp_enable` | 新增 |
| 远程 RPC 开锁 | MQTT 发 `remote_unlock`，携带合法 otp 或触发本地动态码弹窗 | 新增 |

三个通道共用同一张用户表，统一走 `core/unlock_backend.c` 编排。

#### FR-2 人脸置信度分级状态机（核心）

```
注入/真实置信度 score (0~100)
  │
  ├── score ≥ 85          → 直接开锁（发 GPIO，记日志，MQTT 上报）
  ├── 60 ≤ score < 85     → 弹【动态密码页】→ TOTP 验证通过才开锁
  └── score < 60          → 直接拒绝，记失败日志
```

完整状态机定义见 2.3。

#### FR-3 敏感操作二次确认

修改核心规则时**不直接执行**，先强制 TOTP 动态码二次确认：

- 增删用户
- 切换人脸 / 密码 / 动态密码开关
- 修改置信度阈值

#### FR-4 失败锁定

连续 5 次失败（识别失败或动态码错误）→ 锁定 30 秒，UI 显示倒计时。

**锁定粒度决策**（见 ADR-3）：按**用户维度**计数锁定，同时维护全局失败计数。

#### FR-5 远程监控与 RPC

通过 MQTT 实现，手机端用 MQTTX 代替小程序。Topic 与指令集见 2.5、2.6。

#### FR-6 时间基准

TOTP 强依赖时间，需要外部 RTC（DS3231，I2C，带电池）。

代码抽象为 `hal_time()`：

- 未买 RTC 前：返回 `time(NULL)`（Ubuntu 系统时间），TOTP 逻辑可在 Ubuntu 完整验证
- 买到 RTC 后：改为读 DS3231，断电不丢时间；支持 MQTT `sync_time` 校时

#### FR-7 视频预览（阶段 4）

内核开 UVC/V4L2，抓 FM225 的 MJPEG 流，libjpeg 解码 → RGB565 → LVGL Canvas。
分辨率锁 320×240 保证流畅。

#### FR-8 执行器控制

GPIO 驱动继电器 → 电磁锁。**先 LED 模拟，确认逻辑后再接真实电磁锁**。
动作时长必须有上限保护（参考：继电器高脉冲硬性上限 500ms）。

#### FR-9 临时授权（共享场景核心）

管理员可为临时用户指定：

| 参数 | 说明 |
|---|---|
| 有效期 | 起止时间戳，到期自动 disabled |
| 次数上限 | 允许开锁次数，用尽自动 disabled |
| 可用通道 | 该临时用户能用哪几个通道（人脸/密码/动态码） |

**这是共享场景（民宿/短租）区别于家庭场景的关键能力**，
且第一期的 `temp` 角色已支持限次 + 限时，本次主要是把设置界面补齐。

#### FR-10 物理安全告警（P2，有余力再做）

| 功能 | 说明 | 成本 |
|---|---|---|
| 防撬/震动报警 | 震动传感器接 GPIO 中断，触发本地声光 + MQTT 告警 | 低（一个 GPIO） |
| 胁迫密码 | 输入特定密码时表面开锁，实际静默上报告警 | 低（纯软件） |
| 异常时段告警 | 非授权时段开锁，MQTT 推送 WARN | 低（纯软件） |

> 家庭场景下"防撬报警"才是用户最怕的事（比"谁开了锁"重要得多）。
> 虽然共享场景的定位已经让现有功能自洽，但这三项成本低、
> 故事性强，有余力建议补上，面试时是很好的加分点。

### 2.3 状态机定义

```
                    ┌──────────────────────────────────┐
                    │                                  │
                    ▼                                  │
   ┌───────────── IDLE ◄─────────────┐                 │
   │                │                 │                │
   │          detect 事件             │                │
   │                ▼                 │                │
   │          DETECTING               │                │
   │                │                 │                │
   │     ┌──────────┼──────────┐      │                │
   │     │          │          │      │                │
   │  score≥85  60≤s<85     s<60      │                │
   │  & enable  & enable   或禁用      │                │
   │     ▼          ▼          ▼      │                │
   │  UNLOCKED  WAIT_OTP     DENY ────┘                │
   │     │          │                                  │
   │     │     ┌────┴────┐                             │
   │     │   TOTP OK   TOTP失败/超时(60s)              │
   │     │     │          │                            │
   │     │     ▼          ▼                            │
   │     │  UNLOCKED    DENY ──fail_cnt++──┐           │
   │     │     │                            │           │
   │     └─────┼────────────────────────────┤           │
   │           │ 3s 后回 IDLE               │           │
   │           └───────────────────────────►│           │
   │                                        ▼           │
   │                              cnt≥5 ? LOCKOUT : IDLE│
   │                                        │           │
   └─────────────── 30s 后 ─────────────────┘           │
                          └─► IDLE ─────────────────────┘
```

| 状态 | 含义 | UI 表现 | 超时 |
|---|---|---|---|
| `IDLE` | 待机 | 显示时间、状态区 | — |
| `DETECTING` | 识别中 | 显示实时分数 | 5s 无结果回 IDLE |
| `UNLOCKED` | 已开锁 | 绿色提示 + 开锁动画 | 3s 后回 IDLE |
| `WAIT_OTP` | 等待动态码 | 弹出动态密码页 | 60s 超时算失败 |
| `DENY` | 拒绝 | 红色提示 + 原因 | 2s 后回 IDLE |
| `LOCKOUT` | 锁定 | 倒计时 30s | 30s 后回 IDLE，清零计数 |

### 2.4 数据模型

在现有用户结构上扩展，**改动点很小**：

```c
typedef struct {
    int  uid;
    char name[32];

    /* —— 已有 —— */
    char password[32];
    bool password_enable;   // 管理员开关：密码是否有效

    /* —— 新增：人脸 —— */
    int  face_id;           // 该用户在 FM225 内注册的人脸 ID
    bool face_enable;       // 管理员开关：是否允许人脸开锁

    /* —— 新增：动态密码 —— */
    char totp_secret[64];   // 该用户绑定的 TOTP 密钥（Base32）
    bool totp_enable;       // 管理员开关：是否允许动态密码

    /* —— 新增：安全计数（FR-4）—— */
    uint8_t  fail_count;    // 连续失败次数
    uint32_t lock_until;    // 锁定截止时间（Unix 时间戳）
    uint32_t last_otp_counter;  // 防重放：上次使用过的时间片
} user_t;
```

**字段说明**：

| 字段 | 说明 |
|---|---|
| `face_id` | FM225 模组内部的人脸注册 ID，`-1` 表示未录入 |
| `totp_secret` | Base32 编码，RFC 4648 字符集（A-Z, 2-7），建议 16 字节 |
| `last_otp_counter` | TOTP 防重放。记录上次成功使用的时间片序号，同一时间片内不能重复用 |

**迁移策略**：老 JSON 数据缺新字段时，反序列化给默认值
（`face_id = -1`，`face_enable = false`，`totp_enable = false`，`fail_count = 0`），
保证升级不丢数据。

### 2.5 MQTT Topic 定义

| Topic | 方向 | 说明 | QoS |
|---|---|---|---|
| `safe/status` | 设备 → 手机 | 周期上报（5s）+ 状态变化时立即发 | 0 |
| `safe/log` | 设备 → 手机 | 操作/告警日志，指令回执 | 1 |
| `safe/cmd` | 手机 → 设备 | RPC 指令 | 1 |
| `safe/config` | 手机 → 设备 | 阈值、用户信息等配置下发 | 1 |

**消息格式**：

```json
// safe/status
{
  "ts": 1756462800,
  "state": "LOCKED",           // LOCKED|UNLOCKED|WAIT_OTP|LOCKOUT
  "lockout_remain": 0,         // 剩余锁定秒数
  "last_score": 92,
  "last_user": "zhangsan",
  "user_count": 3,
  "time_src": "rtc",           // sys|rtc
  "mqtt_online": true,
  "fw": "1.0.0"
}

// safe/log（含指令回执）
{
  "ts": 1756462800,
  "level": "INFO",             // INFO|WARN|ALARM
  "event": "UNLOCK",           // UNLOCK|DENY|LOCKOUT|ADD_USER|...
  "user": "zhangsan",
  "detail": "face score=92",
  "req_id": "a1b2c3"          // 回执关联，指令触发时带
}

// safe/cmd
{
  "req_id": "a1b2c3",
  "cmd": "remote_unlock",
  "params": { "otp": "123456" },
  "ts": 1756462800
}
```

### 2.6 RPC 指令集

| 指令 | 参数 | 强制动态码 | 说明 |
|---|---|---|---|
| `query_status` | 无 | 否 | 立即回状态 + 日志 |
| `remote_unlock` | `otp`（可选） | 是 | 远程开锁。带合法 otp 直接开；不带则触发本地动态码弹窗 |
| `add_user` | `uid`, `name` | 是 | 新增用户 |
| `del_user` | `uid` | 是 | 删除用户 |
| `set_face_enable` | `uid`, `enable` | 是 | 切换人脸开关 |
| `set_threshold` | `value` | 是 | 修改置信度阈值 |
| `sync_time` | `ts` | 否 | 校时（写入 RTC） |
| `inject_score` | `score` | 否 | **仅调试用**。注入模拟置信度，测试状态机 |

**回执错误码**：

| code | 含义 |
|---|---|
| 0 | 成功 |
| 1001 | 参数缺失 |
| 1002 | JSON 解析失败 |
| 1003 | 未知指令 |
| 2001 | 需要动态码 |
| 2002 | 动态码错误或已使用 |
| 2003 | 用户不存在 |
| 2004 | 用户已锁定 |
| 2005 | 该功能未启用（face_enable / totp_enable 为 false） |
| 3001 | 系统处于锁定状态 |

### 2.7 非功能需求

| 编号 | 项目 | 指标 |
|---|---|---|
| NFR-1 | 离线可用 | 人脸识别 + 动态码 + 开锁完全不依赖外网 |
| NFR-2 | MQTT 延迟 | 局域网内指令到执行 < 500ms |
| NFR-3 | 动态密码 | RFC 6238，30s 窗口，±1 窗口容忍，**一码一用**（防重放） |
| NFR-4 | 失败锁定 | 连续 5 次失败锁定 30s |
| NFR-5 | 可移植性 | Ubuntu Simulator 与 i.MX6ULL 共用同一套业务代码，仅 HAL 层不同 |
| NFR-6 | 稳定性 | MQTT 断线自动重连；后期可选看门狗 / 开机自启 |
| NFR-7 | 执行器安全 | 继电器动作时长上限 500ms，超时强制关闭 |

### 3.3 并发模型

```
主线程（LVGL 主循环 16ms）
  ├── 输入轮询、重绘、flush
  ├── 状态机 tick（auth_fsm）          100ms
  ├── 顶栏时钟 / 倒计时刷新            500ms
  └── worker_poll（取异步结果）        20ms

MQTT 线程（pthread）
  ├── Paho 事件循环（连接/订阅/收发/重连）
  ├── 收 safe/cmd → 投入指令队列
  └── 发 safe/status（周期）、safe/log（事件）

worker 线程（pthread，已有）
  └── 异步存储落盘
```

**线程安全约定**：

- MQTT 线程**不得直接操作 LVGL 对象**，指令投入队列，主线程消费
- 用户表的读写加互斥锁（业务线程与 MQTT 线程都会访问）
- `hal_face` 的 poll 在主线程以非阻塞方式调用，或在独立线程但结果走队列

## 4. HAL 接口定义

阶段 1 就要把这些接口定死，后面换实现只改 .c 文件。

```c
/* hal_time.h —— 时间基准 */
uint32_t    hal_time(void);                 // Unix 时间戳
int         hal_time_set(uint32_t t);       // 校时，写入 RTC
typedef enum { TIME_SRC_SYS, TIME_SRC_RTC } time_src_t;
time_src_t  hal_time_source(void);

/* hal_face.h —— 人脸识别数据源 */
typedef struct {
    int  face_id;      // -1 表示未识别到
    int  score;        // 0~100
} face_result_t;

int  hal_face_init(void);
int  hal_face_poll(face_result_t * out);    // 非阻塞，无结果返回 0
int  hal_face_enroll(int * out_face_id);    // 注册人脸，返回 ID
int  hal_face_delete(int face_id);
// 调试接口：仅在 fake 实现下有效
int  hal_face_inject_score(int score);

/* hal_actuator.h —— 执行器 */
int  hal_lock_init(void);
int  hal_lock_open(uint32_t duration_ms);   // 内部强制 <= 500ms
int  hal_lock_state(void);
```

**阶段 1 与阶段 3 的实现对照**：

| 接口 | 阶段 1（Ubuntu） | 阶段 3（板子 + FM225） |
|---|---|---|
| `hal_time` | `time(NULL)` | I2C 读 DS3231 |
| `hal_face_poll` | 从队列取 UI 滑块 / RPC 注入的分数 | UART 解析 FM225 帧 |
| `hal_face_enroll` | 返回递增的假 ID | 下发 FM225 注册命令 |
| `hal_lock_open` | 打印日志 | GPIO 拉高继电器（≤500ms） |

## 5. 开发路线

共 7 个阶段。每阶段给出**目标 / 任务 / 验收标准**。
阶段 0–2 是主线（Ubuntu 纯软件），阶段 3–6 依赖硬件或部署。

### 阶段 0：环境准备（0.5 天）

**目标**：打通 MQTT 通路。

| 任务 | 说明 |
|---|---|
| 安装 Mosquitto Broker | PC（Windows 或 Ubuntu）局域网监听 1883 |
| 工程集成 Paho MQTT C + cJSON | Ubuntu 本地 gcc 编译通过 |
| 手机装 MQTTX | 连同一 Broker，订阅 `safe/status`、`safe/log` |

**验收**：`mosquitto_pub/sub` 或 MQTTX 能互相收发 `test/topic`。

---

### 阶段 1：Ubuntu 纯软件核心闭环（5~7 天，重点）

**目标**：无 FM225 也能完整演示"注入分数 → 分级 → 动态码 → 开锁 → MQTT 回传"。

#### 1.1 用户表扩展（0.5 天）

- `user_t` 增加 `face_id` / `face_enable` / `totp_secret` / `totp_enable`
- 增加 `fail_count` / `lock_until` / `last_otp_counter`（FR-4、NFR-3）
- 用户管理页增加"人脸开关"、"动态密码开关"
- 保存/切换开关的回调里**预留 TOTP 验证钩子**
- 老数据兼容：缺字段给默认值

#### 1.2 MQTT 客户端（1~2 天）

- `mqtt_client.c`：连接 Broker、订阅 `safe/cmd`、发布 `safe/status` / `safe/log`
- 独立 pthread + 线程安全队列
- 断线自动重连（指数退避）
- UI 在线指示灯

#### 1.3 RPC 指令框架（1 天）

- cJSON 解析 `safe/cmd`
- 实现 `query_status` / `remote_unlock` / `add_user` / `del_user` /
  `set_face_enable` / `set_threshold` / `sync_time` / `inject_score`
- 涉及改规则 / 远程开锁的**强制走 TOTP**（FR-3）
- 回执统一发 `safe/log`，带 `req_id`

#### 1.4 TOTP 动态密码（1~2 天）

- 纯 C 实现 RFC 6238（HMAC-SHA1，可用 OpenSSL `HMAC()`）
- `totp_generate()` / `totp_verify()`，±1 窗口容忍
- **防重放**：`last_otp_counter` 记录已用时间片
- `hal_time()` 现阶段返回 `time(NULL)`
- UI 动态密码页：6 位输入框 + 30s 倒计时

#### 1.5 模拟 FM225 + 状态机（1 天）

- `fake_fm225.c`：UI 调试滑块 / RPC `inject_score` 注入置信度
- 状态机：`IDLE → DETECTING → (≥85)UNLOCK / (60~85)WAIT_OTP / (<60)DENY`
- 关联 `face_id` 查 `face_enable`
- 失败 5 次锁 30s，UI 倒计时

#### 1.6 UI 整合 + 日志（1 天）

- 主界面加状态区（锁定/解锁/置信度/MQTT 在线）+ 视频预览占位区
- 新增动态密码页、日志页、设置页
- 保留静态密码入口

**阶段 1 验收标准**：

| # | 操作 | 期望 |
|---|---|---|
| 1 | MQTTX 发 `query_status` | `safe/log` 收到状态回执 |
| 2 | 注入 score=90 | 直接开锁，`safe/log` 有 UNLOCK 事件 |
| 3 | 注入 score=75 | 弹动态密码页，输入正确 TOTP 后开锁 |
| 4 | 注入 score=50 | 直接拒绝，`safe/log` 有 DENY 事件 |
| 5 | 连续 5 次失败 | 进入 LOCKOUT，UI 倒计时 30s |
| 6 | MQTTX 订阅 `safe/log` | 完整事件流可见 |

## 6. 关键决策记录（ADR）

### ADR-1：MQTT Broker 部署位置

**决策**：开发阶段跑在 PC；**演示阶段改为跑在开发板上**。

**理由**：

- 开发时 PC 上已有 Mosquitto，调试方便
- 演示时若 Broker 在 PC，需要额外带一台电脑，便携性差
- 板子跑 Mosquitto 后，演示只需：手机热点 + 开发板 + 手机 MQTTX

**影响**：阶段 5 部署时要在板子的 rootfs 里集成 mosquitto（Buildroot 需开启对应包）。
**待确认**：Buildroot 是否方便集成 mosquitto；若不便，退化为 PC 跑 Broker。

### ADR-2：TOTP 密钥分发方式

**决策**：管理员在用户管理页生成 Base32 密钥，**以文本形式显示在 UI 上**，
用户用手机 TOTP App（Google Authenticator / 微软 Authenticator）**手动输入**。

**理由**：

- 二维码需要引入 QR 编码库（如 qrencode），增加交叉编译依赖
- 演示场景下手动输入 16 位 Base32 可接受（一次性操作）
- 省掉一个依赖，符合"不分散精力"原则

**待确认**：如果后续觉得手动输入体验差，再加 qrencode。

### ADR-3：失败锁定粒度

**决策**：**按用户维度**计数与锁定。

**理由**：

- 全局锁定会让无关用户也开不了锁，多用户场景下不合理
- 暴力破解通常针对单个用户，按用户锁定已能防住
- 实现上每个用户存 `fail_count` + `lock_until`

**补充**：同时维护一个全局失败计数用于**告警**（连续多用户失败可能是攻击），
但**不触发全局锁定**。

### ADR-4：远程开锁的 TOTP 策略

**决策**：`remote_unlock` 支持两种模式：

- 带合法 `otp` 参数 → 直接开锁
- 不带 `otp` → **触发板子本地弹出动态密码页**，由现场用户输入

**理由**：兼顾"手机远程一键开锁"和"现场有人时的二次确认"两种场景。
演示时后者更有说服力（能看到板子 UI 联动）。

### ADR-5：视频预览分辨率

**决策**：锁 320×240。

**理由**：i.MX6ULL 单核 A7 软解 MJPEG 能力有限；
320×240 在 LVGL Canvas 上叠加显示，能保证 ≥15fps。
追求更高分辨率会拖垮主线程。

### ADR-6：执行器先 LED 后电磁锁

**决策**：阶段 3 先用 LED 验证逻辑，确认后再接真实电磁锁。

**理由**：电磁锁误动作有实物风险（锁死/发热）；
逻辑验证与硬件验证分开，出问题容易定位。
沿用已有经验：继电器高脉冲**硬性上限 500ms**。

### ADR-7：项目定位从"家庭保险柜"改为"多用户共享保险柜"

**决策**：定位调整为**多用户共享保险柜**，目标场景是
民宿/短租、小型办公室、成员多且需权限分级的家庭。

**理由**：按"家庭保险柜"推演，四个核心功能在低频家庭场景下站不住：

| 功能 | 家庭场景的问题 |
|---|---|
| 人脸识别 | 家庭保险柜低频使用，人脸"高频无感通行"的价值发挥不出来 |
| TOTP | 掏手机+开 App+输码，比输密码还慢，老人小孩用不了 |
| 远程开锁 | 削弱物理防护（保险柜的核心价值），且人在家时无意义 |
| 局域网 MQTT | 人在家才能用，那远程功能价值存疑 |

这套设计的骨架其实是**企业门禁/考勤系统**的逻辑。
改定位后，多用户权限、TOTP、远程管理、审计日志、限时授权全部成为必需项。

**额外证据**：第一期的用户表已实现 `admin`/`user`/`temp` 三级角色，
`temp` 支持限次+限时。这个在家庭场景几乎用不上，在民宿场景是核心能力，
说明数据模型本就更贴合共享场景。

**成本**：零。技术栈、模块清单、开发路线全部不变，只改叙事与角色描述。

**影响**：新增 FR-9（临时授权，把已有的 temp 能力补齐 UI）、
FR-10（物理安全告警，P2）；角色从二级改为三级。

## 7. 风险与依赖

### 7.1 DS3231 缺失对上板的阻塞（高优先级）

**风险**：TOTP 依赖准确时间。i.MX6ULL 板载 RTC 若无备份电池，
**断电后时间归零**，上板后所有 TOTP 验证必然失败。

**影响阶段**：阶段 5（上板部署）。阶段 1–4 不受影响（Ubuntu 有系统时间）。

**应对**：

| 方案 | 说明 |
|---|---|
| **推荐**：尽快采购 DS3231 | 几块钱的模块，彻底解决 |
| 备选 1：上板后通过 `sync_time` 校时 | 每次上电都要校，演示麻烦 |
| 备选 2：检查板载 RTC 是否可用 | 若 i.MX6ULL Pro 板载 RTC 有电池则可直接用 |

**建议阶段 1 结束后就下单**，避免卡在阶段 5。

### 7.2 FM225 协议依赖厂家（中）

**风险**：UART 协议文档需向厂家索取，若文档不全或响应慢，阶段 3 会卡住。

**应对**：

- 阶段 1 结束时提前联系厂家要协议
- 若协议难产，考虑先用 USB 视频 + 软件人脸检测（OpenCV）替代，
  但这会增加依赖，非首选

### 7.3 Paho MQTT C 交叉编译（中）

**风险**：Paho 依赖 OpenSSL（若启用 TLS）和 pthread，交叉编译可能有坑。

**应对**：

- 局域网演示**不需要 TLS**，编译时关掉 SSL 支持，减少依赖
- Buildroot 若有 paho-mqtt 包，优先用 Buildroot 构建

### 7.4 单核性能（中）

**风险**：同时跑 LVGL + MQTT + MJPEG 解码，单核 A7 可能吃不住。

**应对**：

- 视频预览锁 320×240（ADR-5）
- MQTT 周期上报 5s，不用更短
- 按第 8 章做性能验证

### 7.5 依赖清单

| 依赖 | 用途 | 状态 |
|---|---|---|
| Paho MQTT C | MQTT 客户端 | 待集成 |
| cJSON | JSON 解析 | 待集成 |
| OpenSSL（HMAC） | TOTP 计算 | 待确认（或用轻量实现） |
| libjpeg | MJPEG 解码（阶段 4） | 待集成 |
| mosquitto | Broker | 待安装 |
| DS3231 | RTC | ❌ 未购 |
| FM225 双目模组 | 人脸识别 | ❌ 未购 |

| 边界值 | score = 85 | UNLOCK 直接开锁 |
| 上边界 | score = 100 | UNLOCK |
| 非法值 | score = -1 / 101 | 视为无效，不触发状态迁移 |

### 8.2 TOTP 测试

| 用例 | 期望 |
|---|---|
| 当前窗口的码 | 验证通过 |
| 上一个窗口的码（−30s） | 验证通过（±1 容忍） |
| 下一个窗口的码（+30s） | 验证通过（±1 容忍） |
| 上上个窗口的码（−60s） | 拒绝 |
| 同一窗口内重复使用 | **第二次拒绝**（防重放） |
| 错误的码 | 拒绝，失败计数 +1 |

### 8.3 失败锁定测试

| 用例 | 期望 |
|---|---|
| 连续 4 次失败 | 未锁定，可继续尝试 |
| 第 5 次失败 | 进入 LOCKOUT，倒计时 30s |
| 锁定期间尝试开锁 | 立即拒绝，返回 3001 |
| 倒计时结束 | 回 IDLE，失败计数清零 |
| 成功一次后 | 该用户失败计数清零 |

### 8.4 MQTT 闭环测试

| 用例 | 期望 |
|---|---|
| 发 `query_status` | 收到状态回执 |
| 发 `remote_unlock`（无 otp） | 板子弹动态码页，回 2001 |
| 发 `remote_unlock`（正确 otp） | 直接开锁，回 0 |
| 发 `set_face_enable`（无 otp） | 拒绝，回 2001 |
| 断网后恢复 | 自动重连，UI 指示灯恢复 |
| 指令到执行耗时 | < 500ms（NFR-2） |

## 9. 面试演示脚本

**目标**：做到阶段 1 + 3 + 5 即完全足够。

### 9.1 现场组网

```
手机开热点
   ├── PC（跑 Mosquitto Broker，或按 ADR-1 改成板子跑）
   ├── i.MX6ULL 开发板（跑保险柜程序）
   └── 手机 MQTTX（连同一 Broker）
```

### 9.2 演示流程（建议顺序）

| 步骤 | 操作 | 展示点 |
|---|---|---|
| 1 | 人脸对准 FM225，置信度 ≥85 | 直接开锁，电磁锁动作，MQTT 上报 |
| 2 | 换个角度，置信度落入 60–85 | 弹动态密码页 → 手机 MQTTX 取码 → 输入 → 开锁 |
| 3 | 用陌生人/低分，score < 60 | 直接拒绝，日志记 DENY |
| 4 | 连续 5 次失败 | 锁定 30s，UI 倒计时 |
| 5 | MQTTX 发 `remote_unlock` | 板子响应 → 日志回传手机 |
| 6 | MQTTX 发 `set_threshold` | 触发 TOTP 二次确认（FR-3） |
| 7 | 拔网线再插回 | 自动重连，指示灯恢复 |

### 9.3 讲解要点

| 话题 | 一句话切入 |
|---|---|
| **定位判断**（先说这个） | "我最初按家庭保险柜做，推演后发现人脸、TOTP、远程开锁在低频家庭场景下都是过度设计。所以定位改成多用户共享保险柜——民宿、小型办公室——这样多用户权限、TOTP、远程管理、审计日志全部成为必需项" |
| 双因子分级 | "不是简单的通过/拒绝，而是按置信度分三档，中分区用 TOTP 补强" |
| TOTP 防重放 | "RFC 6238，±1 窗口容忍，但同一时间片的码用一次就作废" |
| MQTT 指令闭环 | "指令带 req_id，回执能关联，失败有错误码" |
| 用户表设计 | "三通道共用一张表，每个通道独立开关，管理员可单独控制；三级角色，临时用户支持限时+限次" |
| HAL 可移植 | "Ubuntu 和板子共用业务代码，只换 HAL 实现。人脸从模拟器切到真实模组，业务代码零改动" |
| 单核优化 | "板子 nproc=1，所以视频锁 320×240，绘制单元设 1，色深对齐帧缓冲" |

**如果面试官追问"家庭场景为什么要这些"**，按 1.5 的表逐条答：
低频使用下人脸价值低、TOTP 对老人小孩不友好、远程开锁削弱物理防护、
局域网 MQTT 人不在家就没用——所以改定位。
**能主动讲出这个推演过程，比功能本身更有说服力**，
因为这说明你是先想清楚需求再动手，而不是堆技术。
