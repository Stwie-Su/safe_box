## 1. 架构总览

### 1.1 分层与依赖方向

```
ui/          表现层：页面、主题、控件、字体
   ↓ 单向依赖
core/        业务层：auth（认证） / store（存储） / remote（远程） / support（支撑）
   ↓ 单向依赖
hal/         硬件抽象层：face / actuator / camera / time
   ↓
platform/    平台适配：SDL(PC) / FBDEV(目标板)
```

硬约束：

- 依赖**严格单向向下**。`ui` 不得直接调 `hal`；`core` 不得感知具体后端实现；`hal` 不得引用上层。
- `core` 不出现平台头文件（不含 LVGL、不含 SDL/fbdev），保证可移植与可单测。
- 硬件差异全部收敛在 `hal` 的后端注册机制内。

### 1.2 设计原则

| 原则 | 落地方式 |
|---|---|
| 后端可替换 | HAL 以函数指针表/vtable 注册，构建期选后端，业务零改动 |
| 配置集中 | 阈值与地址集中在 `app/core/config.c`，支持环境变量覆盖，禁止散落魔法数 |
| 错误码统一 | 除认证域语义外统一 `safe_err_t`，禁止各模块自造返回码 |
| 主题 token 化 | UI 取色走 `theme_color()` 与全局样式，禁止硬编码颜色值 |
| 异步不阻塞 | 阻塞任务（PBKDF2、文件 IO）下沉后台线程，主线程只做渲染与分发 |
| 事件解耦 | 跨模块通知走 `event_bus`，发布方与订阅方互不知情 |

## 3. 线程与并发模型

### 3.1 现状（Sprint1 已实现）

| 线程 | 职责 | 节拍 |
|---|---|---|
| 主线程（LVGL） | 渲染、状态机心跳、结果泵、事件派发、指令分发 | 20ms / 100ms / 5s 三级节拍 |
| worker 后台线程 ×1 | PBKDF2 校验、文件 IO、网络凭据读写 | 由 `worker_post` 投递 |
| MQTT 网络线程 | 自研客户端的 poll 循环：连接 / 收发 / 重连退避；消息只入线程安全队列，不触碰 UI | 由 `rpc` 层启动 |

主线程节拍分工：

| 函数 | 周期 | 内容 |
|---|---|---|
| `app_tick_fast()` | 20ms | `worker_poll()` → `event_bus_pump()` → `rpc_poll()` → `face_service_tick()` |
| `app_tick_slow()` | 100ms | `auth_fsm_tick()`（轮询人脸结果、状态超时推进） |
| `app_tick_periodic()` | 5s | `rpc_publish_status_now()` |

并发约定（**必须遵守**）：

- LVGL **非线程安全**，所有 UI 操作只能在主线程。
- 后台线程完成回调通过 `worker_post(fn, arg, done)` 的 `done` 在主线程 `worker_poll()` 执行。
- 跨线程事件用 `event_bus_post()`，主线程 `event_bus_pump()` 派发；主线程可直接 `event_bus_publish()` 同步派发。
- MQTT 线程只入队，主线程 `rpc_poll()` 消费，网络线程不得触碰 UI 对象。

### 3.2 Sprint3 目标模型

在现有基础上扩展为**采集线程 + 识别线程 + 主线程**（worker 与 Paho 线程保留）：

| 线程 | 职责 | 交接方式 |
|---|---|---|
| 采集线程 | V4L2 阻塞取帧、格式转换，写入环形/双帧缓冲 | 生产者；缓冲满丢弃最旧帧，绝不阻塞采集 |
| 识别线程 | 串口协议解析 / 帧处理，产出识别结果（含失败原因码）与事件 | 结果经队列交业务层，不直接操作 UI |
| 主线程 | LVGL 渲染 + 既有节拍 | 消费者 |

约束：

- 临界区内不做格式转换等重计算。
- 识别结果只能通过队列/`event_bus_post` 交给主线程，禁止跨线程操作 LVGL 对象。
- 单核上绘制仍为单绘制单元（多线程绘制为负优化）。

## 4. 技术路线与里程碑

```
Sprint1（已完成）  PC/SDL：状态机 · TOTP · 存储 · UI · MQTT/RPC
      ↓

      ↓
Sprint4            收尾：可靠性四项 + 文档 + 简历材料
```

### 4.1 Sprint2：上板打通

| 要点 | 方案 |
|---|---|
| 工具链 | Buildroot `arm-linux-gnueabihf`，经 `cmake/user_cross_compile_setup.cmake` |
| 构建目录 | `build_board`，defconfig 复用 `configs/get_started.defconfig` |
| 显示 | FBDEV，色深对齐 fb0 实际 32bpp |
| 绘制单元 | 单绘制单元（单核多线程为负优化） |
| 触摸 | Goodix 上报已是屏幕像素，标定用恒等 `(0,0,1023,599)`，支持 `LV_TOUCH_CAL_*` 覆盖 |
| 中文 | 启用 FreeType + Noto Sans CJK |
| 防息屏 | 内核 `consoleblank` 只读，应用层用 `KDSETMODE` + `FBIOBLANK` 轮询保活 |
| 部署 | ADB 推送替换目标路径，`killall` 重启（板上无 `pkill`） |
| RTC 接入（v1.6 新增硬件） | I2C RTC 模块（PCF8563 / DS3231 类）经设备树 + Linux RTC 子系统（`/dev/rtc`）接入；`hal_time` 切 `TIME_SRC_RTC`，开机从 RTC 同步系统时钟，掉电不丢时间 |
| broker 两阶段（R-7） | 开发期：Ubuntu 常驻 mosquitto（便于 mosquitto_sub 抓包与自动验收）；目标板阶段：mosquitto 随设备运行（Buildroot 2020.02 自带 mosquitto 包，上板前先验证，受阻则退回 Ubuntu broker 演示） |

部署验证四查：PID 已变、`/proc/<pid>/exe` 非 `(deleted)`、日志有新输出、配置打印核对。

### 4.2 Sprint3：FM225 视频与多线程

**对接方式**：UVC 取流做预览 + 串口拿识别结果，**双通道**。识别算法在模块内完成，主控只消费结果（单核 A7 不具备本地跑检测/活体的算力）。

**分辨率标准（临时统一，2026-08-31 定）**：**采集 = 显示 = 320×240（QVGA，1:1 直通）**，目标 ≥20fps。

先厘清两个此前被混为一谈的概念：

| 概念 | 取值 | 说明 |
|---|---|---|
| 采集分辨率 | 320×240 | 传给 `hal_camera_start(w, h)` 的期望值，后端可协商 |
| 显示窗口尺寸 | 320×240 | LVGL 预览控件大小，与采集 1:1，**零缩放开销** |

选 320×240 的理由：单核 A7 上 1:1 直通无插值开销，最易达成 20fps；与 `hal_camera.h` 现有约定一致，改动最小。

**后续调整规则**：FM225 到货后以其协商结果为准。若原生为 VGA(640×480)，改为采集 640×480 + 显示 320×240（1/2 整数降采样），仍保持整数倍缩放；届时同步更新本表与 `hal_camera.h` 注释。

**性能预算（每帧 50ms）**：

| 环节 | 优化手段 |
|---|---|
| V4L2 采集 | `mmap` 零拷贝，避免 `read()` 复制 |
| 格式转换（YUYV→RGB565） | 查表 / NEON，杜绝逐像素浮点 |
| 缩放 | 整数倍优先，必要时最近邻 |
| LVGL 渲染 | 只刷脏区域，双缓冲防撕裂 |

**先测量后优化**：用 `perf` / `gprof` 定位热点后再改，禁止凭猜测优化。

**先在 Ubuntu 验证再上板**：

1. 用普通 UVC 摄像头或 `v4l2loopback` 虚拟设备构造可控视频源；
2. 串口侧用 `socat` 建立虚拟串口对，模拟 FM225 协议报文；
3. 验证帧率、CPU 占用与线程同步后，再接真机。

以此把「线程 bug / 性能瓶颈 / 硬件协议」三类风险分离，上板阶段只面对硬件差异。

### 4.3 Sprint4：可靠性四项

| 项目 | 方案 |
|---|---|
| 掉电保护 | 临时文件 → `fsync` → `rename` 原子替换 |
| MQTT 可靠性 | 断线指数退避重连 + 离线事件缓存，恢复后补传 |

| 日志滚动 | JSONL 追加 + 条数上限与轮转 |

## 5. 接口规约

> 格式：签名 → 参数 → 返回值 → 功能 → 调用关系（谁调它 / 它调谁）

### 5.1 应用编排 `app/app.h`

```c
void app_main(void);
void app_tick_fast(void);    /* 20ms  */
void app_tick_slow(void);    /* 100ms */
void app_tick_periodic(void);/* 5s    */
void app_shutdown(void);
```

- **参数**：无。
- **返回值**：无。
- **功能**：`app_main` 按依赖顺序初始化存储 → worker → 执行器 → 配置 → 界面 → 状态机 → 远程通道；三个 tick 分别为异步结果泵 / 状态机心跳 / 周期上报。
- **调用关系**：`main.c` 调 `app_main`，并用 LVGL 定时器挂三个 tick；`app_main` 内调 `store_init` → `worker_init` → `hal_actuator_init` → `app_config_init` → UI 初始化 → `auth_fsm_init` → `rpc_init`。

### 5.2 认证状态机 `app/core/auth/auth_fsm.h`

```c
typedef enum { FSM_IDLE, FSM_DETECTING, FSM_UNLOCKED,
               FSM_WAIT_OTP, FSM_DENY, FSM_LOCKOUT } fsm_state_t;

typedef void (*auth_ui_hook_t)(fsm_state_t st, const char *user, const char *detail);
typedef void (*auth_event_cb_t)(const char *evt, const char *user, const char *detail, int res);

void auth_fsm_init(void);
void auth_fsm_set_ui_hook(auth_ui_hook_t hook);
void auth_fsm_set_event_cb(auth_event_cb_t cb);
void auth_fsm_tick(void);

fsm_state_t   auth_fsm_state(void);
const char *  auth_fsm_state_name(fsm_state_t s);
face_reason_t auth_fsm_last_reason(void);      /* 取代 last_score（FM225 无分数） */
const char *  auth_fsm_pending_user(void);
int           auth_fsm_lock_remaining(void);   /* 0 = 未锁定 */

void auth_fsm_submit_face(int32_t face_id, face_reason_t reason);  /* 取代 submit_detect(id, score) */
void auth_fsm_submit_pin(const char *pin);
void auth_fsm_submit_otp(const char *code);
void auth_fsm_cancel_otp(void);
void auth_fsm_note_unlock(const char *user);
void auth_fsm_note_failure(const char *detail);
```

- **参数**：`submit_face(face_id, reason)` 为一次人脸结果（**无分数**，按失败原因分流；`face_reason_t` 定义见 §5.11 `hal_face.h`，core 依赖 hal 为架构允许方向）；`submit_pin`/`submit_otp` 为凭据字符串；`note_unlock(user)` 为成功用户名；`note_failure(detail)` 为失败描述。
- **返回值**：状态查询类返回状态 / 最近失败原因 / 剩余秒数；其余无返回值，结果通过 UI 钩子和事件回调通知。
- **功能**：**按失败原因分流**（成功→开锁；未匹配→计数，连续达 `face_otp_after` 强制转动态码，再达 `max_failed` 锁定；活体失败→拒绝 + 防伪告警并入 FR-10；超时 / 无人脸→不计数）、失败计数与设备级锁定、动态码等待与超时、状态展示时长控制。本模块不 `#include` LVGL，与 UI 通过钩子解耦。
- **调用关系**：
  - 被调：`app_tick_slow` → `auth_fsm_tick`；人脸事件订阅者 → `auth_fsm_submit_face`；PIN 键盘 → `submit_pin`；动态码页与 RPC `submit_otp` → `submit_otp`；RPC `remote_unlock` → `note_unlock`。
  - 它调：`backend_verify_totp` / `backend_verify_pin`（判定），`hal_actuator_pulse`（开锁脉冲），`log_append` 与 `event_bus_publish`（记录与通知），UI 钩子与事件回调。

### 5.3 解锁后端 `app/core/auth/unlock_backend.h`

```c
typedef enum { AUTH_OK=0, AUTH_FAIL, AUTH_LOCKED, AUTH_DISABLED,
               AUTH_NOUSER, AUTH_EXPIRED, AUTH_CHANNEL_OFF, AUTH_REPLAY } auth_result_t;

typedef enum { UNLOCK_OK=0, UNLOCK_FAIL, UNLOCK_LOCKED } unlock_result_t;

unlock_result_t backend_verify_pin(const char *pin, char *out_user, size_t user_cap);
auth_result_t   backend_verify_totp(const char *user, const char *code);
auth_result_t   backend_admin_verify_totp(const char *code);
bool            backend_is_locked(void);
int             backend_lock_remaining(void);
```

### 5.17 虚位密码实现方案（FR-18）

虚位匹配在 PIN 校验层实现，对调用方透明：

```c
/* exact = true  精确匹配（管理员二次确认）
 * exact = false 虚位匹配（开锁 PIN） */
int pin_check_virtual(const char *input, const char *salt_hex,
                      const char *hash_hex, bool exact);
```

实现要点：

- **滑动窗口**：对输入串的每个起始位置取 `pin_len` 长度子串做定值比对。输入上限 20 位、PIN 4–8 位，最多 17 次比对，开销可忽略。
- **不解密、不反推**：虚位是对**输入**做切分后逐段走 PBKDF2 校验，不是把存储的哈希还原成明文——存储侧仍是 PBKDF2 加盐哈希，**安全性不变**。
- **适用边界**：开锁 PIN 走 `exact=false`；管理员二次确认与动态码走 `exact=true`（依据需求规约 5.5）。
- **开关**：由策略项 `virtual_pin_enable` 控制，默认开启，纳入 `safe_policy_t` 与配置快照。

> 安全权衡：虚位会削弱暴力破解难度（一次 20 位输入相当于同时试多个候选）。对冲手段是 FR-4 的失败锁定，以及禁止在管理员二次确认中使用虚位。这是该特性的固有代价，须在设计与面试表述中明确承认，而非回避。

## 7. 通信协议

### 7.1 主题

| 方向 | 主题 | QoS | 内容 |
|---|---|---|---|
| 下行 | `safe/cmd` | 1 | 远程指令（**统一命名**：需求讨论稿中的 `safe/control` 并入本主题） |
| 上行 | `safe/log` | 1 | 指令回执 + 事件 |
| 上行 | `safe/status` | 0 | 状态快照（含 **LWT 遗嘱**：设备异常掉线时由 broker 代发离线状态，支撑 R-1 在线状态） |

主题级 ACL：客户端证书 CN → 可发布/订阅主题映射（如 CN=admin → 可发布 `safe/cmd`），见 §7.5。

### 7.2 报文结构

```json
{ "cmd": "指令名", "req_id": "请求标识", "params": { "otp": "123456" } }
```

回执：

```json
{ "code": 0, "msg": "ok", "req_id": "请求标识" }
```

### 7.3 指令集

| 指令 | 动态码要求 | 行为 |
|---|---|---|
| `query_status` | 无 | 立即回状态快照（含锁定剩余、用户数、连接状态、固件版本） |
| `remote_unlock` | 带 `params.otp` 直接开；不带则回 2001 并在设备端弹码 | 锁定态返回 3001 |
| `add_user` | 需管理员动态码 | `params.uid` / `params.name` |
| `del_user` | 需管理员动态码 | `params.uid` |
| `set_face_enable` | 需管理员动态码 | `params.uid` / `params.enable` |
| `set_face_policy` | 需管理员动态码 | `params.otp_after`（1~5）/ `params.timeout_s`（5~255）——v1.2 取代 `set_threshold`（置信度阈值已随三档判定废弃） |
| `sync_time` | 无 | `params.ts` 为 Unix 秒 |
| `submit_otp` | 无（调试） | 受动态码等待态门控，非该态被忽略 |
| `inject_face` | 无（调试） | `params.reason` / `params.face_id`，仅 fake 后端有效（v1.2 取代 `inject_score`） |

### 7.4 本地验证闭环（不依赖专用 App）

1. 启动应用（无头环境用虚拟显示）；
2. 手机 MQTT 客户端持设备本地授权下发的**接入凭据**连接 broker（同网段；broker **禁止匿名**——FR-24。开发期可经环境变量放宽便于快速联调，但**验收必须以凭据模式跑通**）；
3. 订阅 `safe/#`；
4. 向 `safe/cmd` 发 `{"cmd":"query_status","req_id":"t1"}`；
5. 约 20ms 内 `safe/log` 收到回执，其中连接在线字段为 1 即端到端通。

### 7.5 加密与身份层（FR-25 双向 TLS，需求 v1.6 定案）

**可插拔加密层 `tls_stream`（明文进 / 明文出，上层无感知）**：

```c
/* tls_stream.h —— 接口恒定，后端构建期二选一 */
int  tls_stream_connect(const char *host, int port, const tls_conf_t *cfg); /* cfg=NULL 走明文恒等后端 */
int  tls_stream_write(const uint8_t *buf, size_t len);                      /* 明文进 */
int  tls_stream_read(uint8_t *buf, size_t cap, int timeout_ms);             /* 明文出 */
void tls_stream_close(void);
```

- **后端 A（默认，恒等）**：直接透传 socket，行为与明文完全一致——加密关闭即此态，业务代码与数据零改动。
- **后端 B（mbedTLS）**：双向 TLS。校验 broker 证书（自签 CA + ECDSA + SAN 含 broker IP），同时出示设备客户端证书；任一校验失败**拒绝连接**。

**证书体系与生命周期（自签 CA，全流程项目内完成）**：

| 环节 | 方案 |
|---|---|
| 签发 | 离线生成自签 CA；broker 与手机各持 CA 签发的 **ECDSA** 证书（broker 证书 SAN 必须含 broker IP；不用 RSA2048——A7 握手慢一个量级） |
| 预置 | 设备与手机预置同一信任根 CA；客户端证书经本地管理员授权下发（安全预置流程） |
| 续期 | 证书带有效期，到期前重签并预置（演示期可配长有效期降低频次） |
| 吊销 | 移出 broker 信任列表即吊销，**立即生效**；已吊销证书的连入必须被拒（§10 验收） |

**与 FR-24 的关系（互补不互替）**：双向 TLS 解决「链路加密 + 端点身份」（**谁可以连**）；FR-24 应用层凭据 + 主题 ACL + 动态码分级解决「用户授权」（**连上后能干什么、接管操作要不要动态码**）。两者均保留，缺一不可。

**防重放**：req_id 去重 + 接收序号窗口为主；RTC 就位后叠加时间戳 ±5s 辅助校验（不单独依赖绝对时钟）。

**构建**：mbedTLS 交叉编译进 `third_party/`；`SAFE_FEATURE_TLS` 开关（关 = 恒等后端，业务与既有数据无感，§10 验收「加密开关与业务无感」）。

## 9. 扩展规范

**新增一个硬件后端**（以人脸为例）：

1. 在 `app/hal/face/` 下新增 `backend_xxx.c`，实现后端头文件中的 vtable；
2. 在构建配置中登记新后端名，由 `SAFE_FACE_BACKEND` 选择；
3. 业务层与 `hal_face.h` **零改动**（`face_service_init(backend_name)` 可按名字绑定）。

**新增一条远程指令**：

1. 在 `rpc.c` 的分发函数中添加分支，判定是否需要管理员动态码；
2. 复用统一回执函数，返回分段错误码；
3. 在测试目录中补一条无头验收用例。

**新增一项配置**：集中在 `config.c` 的快照结构中登记，并支持环境变量覆盖，禁止在业务代码写死。
