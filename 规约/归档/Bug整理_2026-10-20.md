## 二、本次上板遇到的 6 个问题

这 6 条的共性：**在 PC 上全绿，一上板就现形**。按依赖的"板上条件"分三类：

| 编号 | 依赖什么才暴露 | 一句话 |
|---|---|---|

| D47 | 真实 fork 语义 | 双 fork 后父进程先退出，抢锁失败的返回码传不回来 |
| D48 | 真实卡死（`kill -STOP`） | 启动宽限无条件生效，跑起来之后卡死也要等 30s 才报 |

### 2.1 D46 停机宽限：基准点选错，不是时间给少了

- **现象**：`kill -TERM supervisor` 后应用 0~1 秒就被 `SIGKILL`，日志却写"宽限 5s 超时"。
- **怎么发现的**：第一次以为是"应用优雅退出太慢"，但日志时间戳显示 TERM 与 SIGKILL 只差 1 秒——
  **日志里的 5s 是阈值，不是实测值**，这是判断"基准错了"的关键线索。
- **根因**：判据用 `waited_ms`（子进程已运行了多久）。应用跑了 8 秒，`waited_ms >= grace*1000` 恒成立，
  信号一到立刻判超时。宽限期实际等于 0。
- **修法**：单独记 `stop_start_ms`，只在第一次看到停机标志时打戳；加 `stop_killed` 锁存避免每轮重复 SIGKILL。
- **回归**：`test_supervisor.sh` 用例 12——应用先跑 6 秒（> grace 3 秒），再发 TERM，
  要求「必须等它自己收尾退出、日志里不能出现 SIGKILL」。修复前这条必挂。

### 2.2 D47 双 fork 之后，父进程返回码与子进程成败无关

- **现象**：`--daemon` 模式下重复启动返回 0（文档写的是 3），init 脚本以为"又起了一份"。
- **怎么发现的**：同一段命令在非 daemon 模式返回 3，daemon 模式返回 0——差异只在 `daemonize()`，
  顺着执行顺序一看，抢锁排在它后面。
- **根因**：`daemonize()` 的父进程 `_exit(0)`，调用方拿到的是**父进程**的成功码；
  真正抢锁失败的是已经转后台的孙进程，它的退出码没人收。
- **修法**：`single_instance()` 提到 `daemonize()` 之前；转后台后用 `pwrite` 把真实 pid 覆盖写回锁文件
  （`flock` 挂在打开文件描述上，随 fork 继承，父进程退出不影响持有）。
- **教训**：凡是要把结果告诉调用方的检查，必须放在 fork 之前。

### 2.3 D48 宽限是给"还没准备好"的，不是给"已经跑起来"的

- **现象**：`kill -STOP` 冻住主循环，本该 5 秒报警，实际等到 30 秒才判死。
- **怎么发现的**：日志里 `心跳超时：22971ms 未更新` —— 年龄都 23 秒了才报，
  说明不是"判得太慢"，而是"前面一直在放行"。对上 `--heartbeat-startup 30`，正好卡在启动宽限结束点。
- **根因**：`hb_check` 无条件给启动宽限，只要子进程启动不满 30s，心跳过期也返回"再等等"。
- **修法**：加 `s_hb_seen`，读到过一次有效心跳就置位，此后宽限立即失效；每个子进程复位。
- **教训**：一个布尔量就能把"初始化慢"和"跑起来后卡死"分开，不需要把宽限调小。

### 2.4 D49 改名不算禁用（BusyBox `rcS` 遍历 `S??*`）

- **现象**：装好新启动脚本、断电重上电后出现**两个 lvglsim**，一个由 supervisor 拉起、一个 `./lvglsim`。
- **怎么发现的**：`ps` 里多出来的进程 cmdline 是相对路径 `./lvglsim`，而 supervisor 拉起的是绝对路径；
  `/proc/170/stat` 的 ppid 是 1（孤儿），说明它来自另一个启动脚本。
- **根因**：备份时把旧脚本复制成了 `/etc/init.d/S05lvgl.bak_20261019`。
  `rcS` 的循环是 `for i in /etc/init.d/S??*`，带 `.bak` **照样匹配照样执行**。
- **修法**：移到 `/root/rollback_20261019/`。
- **教训**："禁用"init 脚本只有两种做法——移出目录，或去掉可执行位；改名不是禁用。
- **附带风险**：两个实例同时抢 `/dev/fb0` 与 `/dev/watchdog`，后者只有一个能打开成功，
  另一个会静默降级到软狗——**现象会变成"看门狗时灵时不灵"，极难查**。

### 2.5 D50 文档写"两层"，代码是"二选一"

- **现象**：supervisor 每 10 秒报一次"未检测到心跳文件"；`kill -STOP` 也不会被软狗处理，
  只能等 60 秒真狗复位整机。
- **怎么发现的**：应用启动日志只有 `后端=linux`，没有软狗初始化那一行；
  再看 `/var/run/safe_heartbeat` 根本不存在——说明 kick 从来没写到文件。
- **根因**：`pick_backend()` 是"多选一"，选中 linux 后 file 后端压根不 `init`，
  而 `kick()` 只转发给当前后端 → 心跳文件永远不写。
- **修法**：主后端是 linux 且显式设置 `SAFE_WATCHDOG_FILE` 时，额外 `init` 一份 file 作为**伴随层**，
  与主后端一起 `start` / `kick` / `stop`；`stop` 时先停伴随层写 `stopped`。
- **验证**：板上日志变成 `后端=linux timeout=60000ms 节流=1000ms 伴随层=file`；
  `kill -STOP` → 5.8s 判死、10s 完成重启，整机未复位。
- **教训**：文档里的"分层"必须落到代码结构上（这里是两个后端同时存活），
  否则只是把两句不相干的话写在一起。降级链管的是"选哪个"，管不了"要不要两个都用"。

### 2.6 OTA 回滚入口：回滚成功了，但生效的是旧版本

- **现象**（推演 + 脚本审阅发现，未端到端跑）：`ota_watchdog.sh` 回滚后执行
  `killall lvglsim` + `/etc/init.d/S05lvgl start`。
- **问题**：在 supervisor 模式下，①`killall` 会被判成一次崩溃、占用重启配额；
  ②supervisor 立刻用 `ExecStart` 里那个路径**把旧二进制重新拉起来**，刚回滚的版本反而没生效。
- **修法**：优先 `/etc/init.d/S05safe restart`（先转发 TERM 优雅停，再重新拉起新文件），
  旧路径保留给没有 supervisor 的部署。
- **教训**：**换掉"谁管进程"之后，所有"重启应用"的地方都要跟着改**。
  这类残留不会报错，只会在最不该出错的时候（回滚）让回滚失效。

### 2.7 D52 两个前台抢屏：屏幕"花了"不是渲染 bug

- **现象**：左侧导航栏整块消失、卡片背后多出一条深色带、左上角出现不属于本应用的红色图标。
  把可疑进程杀掉后**画面依旧不恢复**。
- **怎么发现的**：`fuser /dev/fb0` 输出两个 pid；其中一个 `readlink /proc/<pid>/exe` 是
  `/usr/bin/mxapp2`（MYIR 出厂 HMI demo），`/proc/<pid>/fd` 里同时开着 `/dev/fb0` 与
  `/dev/input/event1`——连触摸都被两个进程分着读。
- **根因（两层）**：
  1. `S99myirhmi2` 的互斥条件写的是 `[ -f /etc/init.d/S05lvgl ]`：有 lvgl 启动脚本就不起 demo。
     我们把入口换成 `S05safe` 后这个文件不存在 → 判断翻到 else → demo 被拉起。
  2. fbdev 没有独占语义，两个写者各画各的，**没有任何报错**。
- **修法**（三层）：
  1. `S99myirhmi2` 移出 `/etc/init.d`；
  2. psplash 的 `QUIT` 原本由那个脚本发，改由 `safe_boot.sh` 自己发——否则开机画面会一直占着 fb0；
  3. 应用启动时扫 `/proc/<pid>/fd`，报告 fb0 的其他写者：
     `fbdev: /dev/fb0 只有本进程在写` / `另一个进程也在写 …，画面会互相覆盖`。
- **验证**：重启后 `fuser /dev/fb0` 只剩本进程，根目录侧栏完整，自检日志报"只有本进程在写"。
- **教训**：
  - 「文件名存在与否」当互斥开关，等于把互斥绑在别人的命名上，改名即失效，且失效方向是"多启动一个"；
  - 杀掉写者不会清屏，残留像素要等本进程重绘才覆盖，**别据此判断修没修好**；
  - 第二个写者可能潜伏很久才画第一笔，故障会"突然出现"。

## 三、按失效模式重排（全量）

同样的坑换个模块还会再踩，所以按"错在哪一类判断"归，而不是按"错在哪个文件"归。

### 模式 A：基准点 / 初值选错（4 条）

| 编号 | 错在哪 |
|---|---|
| D46 | 宽限计时起点用"对象存在时长"，不是"事件发生时刻" |
| D27a | 布尔初值 `true` 让"首次调用"被相等判断吞掉 |
| D20 | 复制预览管线漏了 `s_scale_max` 初值 → 放大判据恒假 |
| D44 | 软狗拿 mtime（墙上时钟）判过期，被校时/远程 `sync_time` 绕过 |

**检查项**：凡是"等 N 秒""第一次""是否已初始化"，先写清基准点和初值方向。

### 模式 B：两件事被一条 `if` 合并（3 条）

| 编号 | 被合并的两件事 | 后果 |
|---|---|---|
| D34 | "没下完" vs "下完了但是坏的" | 用"删除坏包"的处理方式干掉了可续传的残片 |
| D48 | "还在初始化" vs "跑起来后卡死" | 卡死检测被启动宽限吃掉 30 秒 |
| D30 | "迁状态" vs "迁日志"（下沉 worker 时只迁了一半） | 审计少一条，功能正常、不报错 |

**检查项**：写 `if` 时问一句——这个分支里其实混着几种失败态？

| 编号 | 几套规则 |
|---|---|

**检查项**：同一件事有几个写入口/几个副本？能不能收敛到一处？

## 四、下次动手前的 8 个问题

写涉及下面这些东西的代码时，先自问一遍：

1. **「等 N 秒」**——计时起点是"事件发生"还是"对象存在"？（D46）
2. **`if` 分支**——里面混了几种失败态？能不能分开？（D34、D48）
3. **双 fork / daemon**——需要告诉调用方的结果，是不是放在 fork 之前了？（D47）
4. **禁用一个启动脚本**——是移出目录还是去掉 `+x`？改名不算。（D49）
5. **超时判定**——用的时钟会被谁改？RTC 校时、NTP、远程指令。（D44）
6. **跨进程文件**——谁写、谁读、谁清？残留值会不会被当成新状态？（D45）
7. **文档说"两层"**——代码里真有两条路径同时在跑，还是只选了一个？（D50）
8. **换了"谁管进程"**——所有"重启应用"的地方都跟着改了吗？（OTA 回滚）
9. **改了文件名/入口名**——有没有哪个判断是拿这个名字当开关的？失效方向是"多做"还是"少做"？（D49、D52）
