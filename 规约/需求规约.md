> 变更（v1.9，2026-09-16）：**虚位密码性能治理（FR-18，§5.2）**——**① 最大输入长度 20 位 → 12 位**。理由：虚位匹配是「一次输入尝试多个候选子串」，候选数随输入长度增长（单用户最坏候选数由 75 降到 35），20 位不命中在 PC Debug、3 用户下实测约 9.5s，单核 A7 上更慢，构成可感知的算力放大（§5.5 早把该代价登记为已知项，本次加以收紧）。代价：可在正确 PIN 前后附加的干扰位减少（前后合计最多 4 位）——对「防旁人窥视」的实用目的仍足够。**② 开锁 PIN 校验改为异步（实现方式，非判定规则）**：判定下沉到后台线程，界面在校验期间显示「校验中」，不再随 PBKDF2 阻塞；登记于此仅为说明动机，判定口径不变（仍为「连续子串匹配」且受开关控制）。**本次未新增 / 删除任何判定规则，仅收紧长度上限并登记异步化动机。**

## 1. 项目定位与场景

基于 i.MX6ULL 的**多用户共享保险柜系统**，面向民宿/短租、小型办公室、多成员家庭等「多人共用同一柜体」场景。

核心认证链路为 **人脸识别（FM225 双目活体模组）或 PIN 开锁**；**TOTP 动态密码**承担敏感操作二次确认与暴力破解应对，并作为人脸 / PIN 不可用时的备用认证通道。配套本地界面、远程监控与远程指令，以及**限时/限次的临时授权**（房客退房到期自动删除用户）。

基本约束：

- **离线优先**：认证链路不依赖外网，断网仍可正常开锁。
- **局域网远程**：仅局域网内可查看状态、下发开锁与管理指令。
- **硬件受限**：imx6ull,单核 Cortex-A7，一切性能设计以此为前提。
- **人脸模组约束**：FM225 识别距离 30~120cm、识别角度约 ±20°、人脸容量 100 人；录入与验证交互、结构安装均按此约束设计。

## 2. 术语与优先级定义

| 术语 | 含义 |
|---|---|
| 活体检测 | 由人脸模组执行，判断镜头前是真人而非照片 / 视频的防伪检测 |
| 未匹配 | 活体通过，但未命中任何已注册人脸 |
| 防伪告警 | 活体检测失败（疑似照片 / 视频攻击）触发的事件 |
| 链路加密 | 对通信链路上的数据加密并校验对端身份，使第三方无法读取内容、冒充对端或伪造消息 |
| 动态码 OTP | 基于时间的一次性密码（TOTP），6 位 |
| 临时授权 | 限时（有效期）与限次（次数上限）的授权，到期或用量耗尽自动**删除用户** |
| 接入凭据 | 远程客户端连接消息代理时出示的身份凭据，由管理员在设备本地授权下发，可吊销 |
| 接管级操作 | 一旦被滥用即可永久夺取设备控制权的操作：改管理员密码 / 删除管理员 / 恢复出厂 / 改安全策略 |
| 敏感操作 | 增删改用户、人脸录入与删除、修改阈值、切换认证通道、远程开锁 |

优先级定义：

| 级别 | 含义 |
|---|---|
| P0 | 不做则项目不成立 |
| P1 | 核心亮点，直接影响项目价值与简历含金量 |
| P2 | 有则加分，无则不影响主线 |

## 3. 角色与权限模型

| 角色 | 说明 | 权限 |
|---|---|---|
| 管理员 admin | 柜体 owner / 运维 | 用户增删改、人脸录入与删除、策略与阈值调整、敏感操作二次验证、远程开锁 |
| 长期用户 user | 家庭成员 / 员工 | 人脸 / PIN 正常开锁 |
| 临时用户 temp | 房客 / 访客 | 限时限次开锁，到期或用量耗尽自动删除用户（FR-9） |

认证方式：4–8 位数字 PIN（可配置，见 5.2），或人脸验证（含活体检测）；`auth_method` 字段预留 `"otp"`（后续可接手机动态码，P2）。

| FR-26 | 模组链路加密与身份鉴别：人脸模组与主控制器之间的通信应支持加密，并支持校验模组唯一标识（防止以伪造模组替换后伪造「验证成功」）。**当前版本为明文**，风险登记于 §9.3。加密须为配置开关，切换不改变业务行为与既有数据；若模组厂商不提供加密所需算法或授权，则维持明文并保留该风险 | P2 |
| FR-28 | 用户列表按角色分区显示：用户管理页的用户列表按**管理员 / 普通用户 / 临时用户**分为三组，每组带各自的分组标题（见 5.8）。（注：FR-27 编号已被《开发进度》登记为待拍板的「热管理」候选，本次不占用） | P1 |
| FR-29 | 远程固件升级（OTA）：经远程通道接收固件包并升级本机固件。**安全前提**：固件包须通过完整性校验（SHA-256 摘要）与来源签名验证（复用 FR-25 信任根），任一校验失败立即丢弃已下载数据并拒绝升级；**掉电安全不变式**：升级过程任一时刻断电，设备要么继续运行旧固件、要么以新固件正常启动，**绝不出现无法启动的中间态（不变砖）**；新固件首次启动须**自确认**（上报新版本号且健康自检通过），超时未确认**自动回滚**旧固件，回滚动作记入审计日志（FR-5）；升级属**接管级操作**，须管理员动态码确认（§5.7）；升级全程本地开锁、认证、日志不受影响（NFR-1）。**分两期实现**：①固件包接收 / 校验 / 落盘（远程通道侧，PC 无头环境即可验收）；②分区切换 / 自确认 / 回滚（bootloader 侧，依赖 FR-15 目标板）。**明确不做**：云端 OTA 服务器、差分升级、多设备灰度调度、自研 bootloader（理由见版本头 v1.10）。分区布局、传输方式与签名算法由《技术路线规约》规定 | P1 |

> 说明一：要实现优雅的多线程架构，对性能的利用要极致
> 说明二：重新架构整个项目，保留可用部分，重构冗余和不易扩展维护的部分，从需求开始到技术路线，要遵循规约，开发者是一位新人，有建议要及时沟通，修改规约。

## 5. 业务流程需求

### 5.1 人脸开锁判定（FR-2、FR-19、FR-20）

人脸模组仅返回「成功 / 失败（含原因码）」，**不输出比对分数**，系统按失败原因分流：

| 模组结果 | 系统行为 |
|---|---|
| 验证成功（活体通过且命中注册人脸） | 核对本地凭据与用户状态：启用且未锁定 → 直接开锁；已停用 / 已锁定 / 凭据失效 → 拒绝 |
| 验证失败·未匹配（活体通过但非注册用户） | 拒绝并计入失败；**连续未匹配达 `face_otp_after`（默认 3）→ 强制动态码验证身份**；继续失败达 `max_failed` → 设备级锁定（FR-4） |
| 验证失败·活体检测失败 | 拒绝并计入失败，同时触发防伪告警（FR-10，即时上报 R-2） |
| 超时 / 未检出人脸 | 回到待机并提示，**不计入失败** |

附加行为需求：

- 人脸验证超时默认 10s，管理员可配置（上限 255s）。
- 人脸验证进行中允许切换为 PIN 输入（打断当前验证）。
- 已处于动态码验证态时，同一用户人脸验证成功应直接开锁（升级路径），不强制走动态码。
- 开锁成功后展示结果若干秒（默认 3s）再回到待机；拒绝展示约 2s。
- **职责边界**：模组只承担认证，开锁动作统一由系统执行器执行（受 NFR-3 脉冲上限约束）。

### 5.2 PIN 开锁（FR-1）

- 输入 PIN 后匹配任一**启用且未锁定**的用户，成功即开锁。
- PIN 长度 4–8 位，可配置最短/最长。
- **虚位密码（FR-18）**：允许在正确 PIN 的前后附加任意数字，只要输入串中**连续包含**正确 PIN 即判定通过，用于防止旁人窥视。
  - 最大输入长度 12 位（v1.9 由 20 收紧，理由见版本变更记录）；**超过 12 位的输入不受理**（不参与比对，直接判失败），键盘亦不接收第 13 位。
  - 「连续包含」的含义（v1.8 澄清，非新规则）：正确 PIN 必须作为**一段连续子串**出现在输入串中。干扰位加在 PIN 前后不影响连续性，
    故判通过；把干扰位插进 PIN 中间会使其不再连续出现，故判不通过。
  - 仅适用于**开锁 PIN 通道**；管理员二次确认与动态码不适用（见 5.5）。
  - 该功能可由管理员开关控制；**关闭时按精确匹配处理**，输入长度受 PIN 长度范围约束。

### 5.3 防暴力锁定（FR-4）

- PIN 失败与人脸未匹配**合并计入同一失败计数**，成功开锁清零。
- 连续失败达 `max_failed`（默认 5）次进入设备级锁定，持续 `lock_seconds`（默认 30s）。
- **锁定期间拒绝一切开锁请求**，包括管理员的远程开锁指令（返回「系统锁定」错误）。
- 锁定判定优先于任何凭据校验：不得出现「锁定期间仅凭动态码即可开锁」的路径。

### 5.4 动态码（FR-3）

- 6 位数字，基于时间片（默认 30s）生成。
- 容忍前后各一个时间片的时钟偏差。
- **一码一用**：同一时间片内同一码只能成功使用一次，重复提交判为重放并拒绝。
- 动态码通道可由管理员选择是否启用。
- 如果检测到暴力破解：需要动态码验证身份（触发条件见 5.1 分流）。

### 5.5 敏感操作二次确认（FR-14、FR-1）

| 操作 | 二次确认方式 |
|---|---|
| 修改**管理员**密码 | 强制动态码 |
| 修改普通用户密码 | 校验旧 PIN 即可 |
| 删除用户 | 管理员 PIN |
| **人脸录入 / 删除人脸** | 管理员 PIN |
| 查看开发者选项（只读诊断） | 无需鉴权 |
| 远程开锁 / 增删用户 / 改阈值 | 强制管理员动态码 |

**虚位密码的适用边界**：虚位为防窥视而设计，代价是削弱暴力破解难度（一次长输入相当于同时试多个候选；v1.9 把最大输入由 20 位收紧到 12 位，正是为压缩这一放大倍数，理由见版本变更记录）。因此：

- 开锁 PIN：**支持**虚位，依赖失败锁定（FR-4）对冲破解成本。
- 管理员二次确认：**不支持**虚位，必须精确匹配——敏感操作不允许以降低精度换取便利。
- 动态码：不适用，动态码为定长 6 位且一码一用。
- 如果检测到暴力破解：需要动态码验证身份。
- 本表适用于**本地（触摸屏）**操作；**远程**通道的二次确认规则见 5.7。

### 5.6 临时授权（FR-9）

- 管理员可设置有效期截止时间与开锁次数上限。
- **创建入口（v1.8 补）**：上述两项在**创建用户时**随角色一并设置（选临时角色时给出有效期与次数上限的输入项），
  而不是先建成普通用户再补；未填写即视为不限。
- **到期或次数耗尽后，系统自动删除该用户信息（含其人脸凭据等全部数据），无需人工回收**；删除动作记入审计日志。
- 删除后该用户全部凭据自然失效；对模组侧人脸按 FR-21 联动删除，模组删除失败时以本地凭据失效标记兜底。

### 5.7 远程指令的凭据与二次确认（FR-12、FR-24）

**前提认知**：局域网不等于可信通道。同一网络内的任何设备都可能接入消息代理并发布指令——民宿场景下房客就在同一网络里。「手机在管理员手里」只保证**持有者**是管理员，网络上看不出消息是谁发的，因此远程通道不得以「无凭据」方式开放。

分三层保证「只有管理员能发控制指令」：

1. **通道准入（你是不是我授权的那台设备）**：消息代理禁止匿名接入；客户端连接时须出示凭据，凭据由管理员在**设备本地界面**授权下发（配对），一机一凭据；手机丢失或更换时可吊销旧凭据，吊销后立即失效。
2. **指令可信（这条指令是不是新的、有没有被改过）**：每条控制指令携带客户端身份、请求标识与时间有效性；设备端校验「身份已授权 + 请求标识未使用过 + 指令仍在有效期内」，重复或过期指令一律拒绝（防嗅探与重放，见 R-5）。
3. **权限分级（你能做什么）**：凭据只决定「能不能连上并发布」，不等于「能执行所有操作」；消息代理与设备端按主题与操作分级授权。

**二次确认分级**（替代原「远程一律动态码」）：

| 远程操作 | 确认方式 |
|---|---|
| 增删普通用户 / 开关用户通道 / 修改普通用户密码 | 客户端凭据 + 防重放即可，**无需动态码** |
| 修改**管理员**密码 / 删除管理员 / 恢复出厂 / 修改安全策略 | **强制管理员动态码，任何通道不豁免**（接管级操作） |
| 远程开锁 | 维持 R-3：需管理员动态码（直接开门，不豁免） |

说明：动态码解决「这一步是不是管理员本人在操作」，接入凭据解决「连接者是不是已授权设备」——两者互补、不可相互替代。之所以对**接管级**操作保留动态码，是因为凭据可能随手机一并丢失：仅凭凭据即可改掉管理员密码，等于把柜子永久交给捡到手机的人。

### 5.8 用户列表的角色分区展示（FR-28）

用户管理页的用户列表按角色分区显示：

- 分区为**管理员 / 普通用户 / 临时用户**三组，每组前面显示该组的分组标题。
- 分区顺序与组内顺序须**稳定**：同一份用户数据多次进入页面，展示顺序一致。
- 以下细节本规约不约束，由实现决定：某角色当前无用户时该分区是否显示、分区内采用何种排序键、
  临时用户行是否额外展示剩余有效期与剩余次数。

### 5.9 远程固件升级流程（FR-29）

升级属**接管级操作**，全程受控、可中断、可回滚：

1. **授权**：发起升级须管理员动态码确认（§5.7 接管级）；升级会话与普通远程指令共用同一套
   凭据与防重放机制（FR-24），不另开旁路通道。
2. **版本预检**：下载前先查设备当前固件版本与型号，**版本不符 / 型号不符的固件包在下载前即拒绝**，
   不消耗传输。
3. **下载（分块 + 断点续传）**：固件包分块下发，逐块校验；任一块失败只重传该块。
   升级中断电 / 断网，恢复后**从已落盘进度继续**，不重头下载。
4. **校验（两道，顺序不可换）**：收齐后先验整体 **SHA-256 摘要**，再验**来源签名**
   （复用 FR-25 信任根）；**任一失败立即丢弃全部已下载数据**、回执明确错误码，不进入写入阶段。
5. **写入与切换**：校验通过后写入**备用分区**（不覆盖当前运行分区），完成后置「待切换」标记，
   经重启生效。
6. **自确认与回滚**：新固件首次启动上报新版本号且健康自检（存储 / 通道 / 模组）通过后**确认**；
   **超时未确认自动回滚**旧分区。回滚本身记入审计日志（FR-5）并向远端上报。

**掉电安全不变式**：上述任一步骤、任意时刻断电，重启后的设备**要么以旧固件正常运行、
要么以已通过校验的新固件启动——不存在第三种状态**。固件下载数据与用户数据（FR-6）分区隔离，
升级失败不得污染用户数据与审计日志。

### 7.1 用户与人脸凭据模型

| 概念 | 内容 |
|---|---|
| 系统用户档案（唯一身份源） | ID、名称、角色、PIN 哈希与盐、启停状态、失败计数、锁定截止、动态码密钥、通道开关、临时授权字段 |
| 人脸凭据（可选凭据） | 归属用户 ID、模组侧用户 ID（句柄）、已录入方向集合、录入时间、状态（有效 / 失效） |

**「模组侧 ID 会被复用」的含义**：模组用户 ID 是模组内部按槽位分配的编号（容量 100），删除用户后该槽位释放，后续录入的用户可能被分配到**同一个 ID**。也就是说「ID=7」今天是张三、明天可能是李四。因此：

- **模组侧 ID 仅作为访问模组人脸数据的句柄，不参与身份判定**；人脸凭据的有效性以系统侧标记为准。
- 需求按「ID 会复用」这一最坏情况设计（具体复用策略以实测为准）。

规则：

- 用户 : 人脸凭据 = **1 : 0..1**；未录入人脸的用户不存在凭据对象，不占位、不预分配。
- 身份与角色永远以系统档案为准；模组只回答「这张脸对应模组侧几号」，系统再查该号码绑定的用户与状态。
- 用户名冗余写入模组用于对账，用户名长度受模组 32 字节限制。

**防「张冠李戴」的三条防线（FR-21）**：

1. **比对用户名**：验证成功后，核对模组返回的用户名与本地凭据记录是否一致，不一致即判凭据失效并记审计日志。
2. **确认删除结果**：删除用户须确认模组侧删除成功；失败则本地凭据立即标记失效，不得以「已下发删除指令」代替确认。
3. **启动对账**：系统启动或模组就绪后，核对模组用户清单与本地凭据；孤儿凭据（本地有、模组无）标记失效且不用于放行。

- 删除用户 / 到期删除 / 恢复出厂 → 按 FR-21 联动处理人脸凭据。

| R-6 | 手机端验证 | 使用标准 MQTT 客户端即可完成订阅状态与下发指令的验证；不开发专用 App |
| R-7 | 消息代理部署 | **分两阶段，设备端连接方式不变、仅代理地址不同**：PC 验证阶段代理运行于 Ubuntu 本机（便于报文观察与自动化验收，NFR-7）；**目标板阶段代理随设备运行（设备自带）**，手机直连设备，消除外部主机单点。若目标板阶段仍依赖外部常驻主机，则该主机离线期间远程能力不可用，**本地开锁、认证、日志不受影响** |
| R-8 | 接入认证与权限 | 代理禁止匿名接入，客户端须持凭据连接；按主题与操作分级授权；凭据由设备本地管理员授权下发并可吊销（FR-24） |
| R-9 | 固件升级通道 | 经远程通道**分块下发固件包（断点续传）**；升级进度可查询；升级成功 / 回滚结果上报并记入审计日志（FR-5）；升级属接管级操作，须管理员动态码确认；固件包须通过摘要与签名双重校验（FR-29） |

### 8.1 远程通道方案候选与选型结论

**约束前提**（任何候选方案都必须满足）：手机端**无需专用 App** 即可查看状态与下发指令（R-6）；本地开锁与认证链路不得依赖远程通道（NFR-1）；事件需即时送达手机（R-2）；指令需可回执对账（R-5）。

| 候选 | 拓扑与依赖 | 手机端验证 | 事件即时送达 | 单点风险 | 结论 |
|---|---|---|---|---|---|
| ① 标准消息协议 + 消息代理（协议栈自行实现或采用第三方库，属实现差异） | 设备与手机均接入代理（R-7） | 标准客户端可直接验证，**满足 R-6** | 协议自带在线状态通告、最新状态留存、送达保证三项能力，正好覆盖 R-1 / R-2 / R-5 | 代理为单点，随设备部署后消除 | **主选** |
| ② 设备自建服务、手机直连（无代理） | 手机直连设备，不依赖任何常驻主机 | 通用工具可达，但 R-6 的验证方式需相应调整 | 需自行设计长连接推送、回执与防重放 | 无单点 | **后续评估**（§9.1） |
| ③ 近场无线（蓝牙等）点对点 | 手机与设备直连 | 需专用工具或 App，与 R-6 冲突 | 通信距离受限，不满足「远程」语义 | 无单点 | **不采用**（§9.2） |

**选型结论与理由**：

- **主选 ①**：R-6「标准客户端即可验证」直接成立，无需自建验证工具；协议自带的三项能力对应 R-1（状态上报）、R-2（事件上报）、R-5（回执对账），无需自行设计；代价是引入代理组件，通过「目标板阶段代理随设备运行」（R-7）消除单点。
- **后续评估 ②**：待 ① 跑通后评估「去掉常驻代理、手机直连设备」，目标是彻底消除单点、简化拓扑；评估时必须重新覆盖三项需求——事件即时送达方式、指令回执与防重放、无专用 App 的验证方式。
- **实现方式不在本规约约束范围**：协议栈自行实现还是采用第三方库、分层结构与线程模型等由《技术路线规约》规定；本规约只约束**能力、验证方式与取舍边界**。

### 9.2 明确不做（需求边界外）

| 项 | 理由 |
|---|---|
| 演示模式用于生产 | 模组演示模式不做比对、人人可过，仅限开发调试使用 |
| 模组执行开锁 | 开锁统一由系统执行器执行（见 5.1 职责边界） |
| 置信度分数相关功能 | **依赖模组能力**：当前模组不输出相似度分数，暂不做；若后续模组型号 / 固件提供分数，再行评估后重开需求 |
| 近场无线（BLE 等）作为远程通道 | 10m 级通信距离不满足「远程监控」语义；需额外硬件与专用工具，违反 R-6（无需专用 App） |

> 注：v1.6 起「双向证书体系（客户端证书互验）」**已从明确不做改为采纳**（见 FR-25 / §9.1）——设备新增 RTC 模块解决时钟可靠性，且该项目以作品集形式展示嵌入式网络与安全能力，互验 TLS 的证书生命周期成本被接受为 deliberate 投入；FR-24 应用层凭据仍保留，与 FR-25 互补，不互替。

### 9.3 当前版本已知限制（残余风险登记）

| 限制 | 风险与缓解 |
|---|---|
| 与模组通信为明文（FR-26 未启用） | 可物理接触者可介入模组与主控之间的链路窃听或伪造「验证成功」；缓解依赖结构防护（模组与主控同一壳体内）与 FR-10 防拆告警。风险已登记，不因明文链路降低其它防线 |
| 远程通道已加密（FR-25 启用，双向 TLS） | 链路窃听与冒充代理风险已关闭；残余：证书生命周期管理（安全预置、续期、吊销）须可靠，吊销须即时生效；证书校验失败必须拒绝连接（§10 验收） |
| 设备时钟 | 已新增 **RTC 模块**，掉电保持实时时钟，可信时间源成立；时间戳防重放（§5.7）与证书有效期校验可行。残余：RTC 电池耗尽 / 失效时的兜底策略待定（启动后校时或宽松有效期） |
| 远程能力依赖代理主机 | **PC 验证阶段**代理主机离线时远程监控与指令不可用；目标板阶段按 R-7「代理随设备运行」落地后该限制消除。任何情况下本地开锁、认证、日志不受影响 |
| 模组用户 ID 复用 | 按「会复用」设计；ID 仅作句柄，有效性以系统侧标记为准，并靠三条防线兜底（§7.1） |

## 10. 验收标准

分层验收，每层可独立复现。

| 层级 | 范围 | 通过标准 |
|---|---|---|
| 单元 | 认证状态机、动态码、存储 | 全部用例通过 |
| 单元 | 虚位密码匹配 | 前后加扰的长串可通过；**中间插入干扰位的串被拒**；**超过 12 位的输入被拒**；不含正确 PIN 的长串被拒；管理员二次确认不接受虚位；**开关关闭时虚位失效（长串被拒、精确 PIN 仍通过）** |
| 单元 | 人脸凭据模型与一致性 | 未录脸用户不占位；删用户联动删凭据；凭据失效时即使模组返回成功也被拒 |
| 单元 | 临时授权创建入口（FR-9） | 创建时可指定角色为临时用户并设有效期 / 次数上限；到期与次数耗尽的用户在任一认证通道被拒并自动删除，动作入审计 |
| 单元 | 用户列表角色分区（FR-28） | 管理员 / 普通用户 / 临时用户三组标题与成员归属正确；顺序稳定 |
| 单元 | OTA 升级状态机与校验（FR-29） | 摘要错误 / 签名错误 / 版本不符的固件包**全部拒绝且不留残余数据**；断点续传从已落盘进度继续而非重头；升级状态机**任意时刻断电模拟**后，均可恢复到「旧固件运行」或「新固件待确认」两态之一 |
| 集成 | 无头环境端到端（远程指令驱动开锁/拒绝/锁定） | 全部用例通过，锁定期间无误触发 |
| 集成 | 人脸判定分流 | 成功开锁；未匹配连续达阈值转动态码；活体失败触发防伪告警；超时 / 无人脸不计失败 |
| 集成 | 远程通道安全 | 匿名连接被拒；请求标识重复或超时的指令被拒；凭据吊销后立即失效；接管级操作仍要求动态码 |
| 集成 | 加密开关与业务无感 | 明文与加密两种配置下功能用例全部通过；切换加密不改变业务行为、既有数据与配置 |
| 集成 | 对端身份校验 | 双向 TLS 下无有效客户端证书 / broker 证书的连接必须拒绝；已吊销客户端证书立即失效；不得以关闭校验的方式通过验收 |
| 目标板 | 远程链路自包含 | 手机与设备可直接完成订阅状态与下发指令，无需外部常驻主机参与（R-7 目标板阶段） |
| 目标板 | OTA 升级与回滚（FR-29） | 升级后新固件正常启动并**自确认**；升级中断电**不变砖**（旧固件照常运行）；新固件超时未确认**自动回滚**；回滚动作入审计并上报远端 |
| 集成 | 人脸凭据对账 | 模组返回用户名与本地不一致时判失效并拒绝；孤儿凭据不放行；模组侧删除失败时本地立即标失效 |
| 人脸录入 | 多方向交互录入 | 引导与已录方向进度显示正确；取消后录入状态清零；容量满（100）提示明确 |
| 目标板 | 显示、触摸、中文、防息屏、稳定运行 | 交互正常，长时间运行不退出 |
| 目标板 | 人脸模组稳定性 | 模组故障时系统降级不崩溃、告警可见，恢复后自动回归正常认证 |
| 视频预览 | 实时画面小窗 | 画面连续，界面操作不卡顿 |
| 手机端 | 标准 MQTT 客户端订阅与下发 | 状态可见、指令有回执 |

**手机端最小验收闭环**：设备运行 → 手机连接同一局域网 → 订阅全部设备主题 → 下发状态查询指令 → 在超时前收到状态回执，且回执中显示连接在线。
