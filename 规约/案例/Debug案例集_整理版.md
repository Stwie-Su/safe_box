# Part A —— 🟢 真·产品缺陷（面试可讲，人类也会踩）

每个案例统一结构：**现象 → 隐匿点/根因 → 修复 → 考点**。全部来自本工程真实代码缺陷，量化数据均为实测。

---

## A1. 串口重发刷屏——跨模块时钟纪元混用
**现象**：FM225 `VERIFY` 命令重发把日志刷屏（40s 内 671 行日志 489 行是重发），但日志里明明有 `verify 应答` 解析记录。
**根因**：接口契约缺失——`tick(now_ms)` 的「毫秒」没有约定纪元。`backend_fm225.c` 用 `hal_time_ms()`（CLOCK_MONOTONIC 绝对值，≈1.54×10⁶），而 `app.c` 传的 `now_ms` 来自 `s_tick_ms += 20`（进程内计数，从 0 起）。两者相减无符号下溢成巨值 → 超时恒触发 → 重发 → 重置基准 → 循环。注释里写的「800ms 超时/退避」从未生效。
**修复**：`app.c` 改传 `hal_time_ms()`，头文件注释钉死语义；改动前 grep 确认 4 处 `now_ms` 使用方全是差值语义（相对用法不受纪元影响）才动手——零风险依据。**驳回**「再叠指数退避」：这里是空转轮询，指数退避会推迟恢复检测，是负优化。
**考点**：串口协议超时重传设计 / CLOCK_MONOTONIC vs 自维护计数 / 对照实验排除变量 / 「判据必须能从常量推算」（reply 场景重发=0 是硬指标）。

## A2. 日志「最后开启」恒为 `--`——大小写失配被无效单测掩护
**现象**：日志页「最后开启」永远空，但日志列表里明明有开锁记录。
**根因**：双缺陷叠加。①写入侧 `auth_fsm.c` 用全大写 `UNLOCK`，查询侧 `page_logs.c` 用小写 `"unlock"` 做 `strcmp` → 精确匹配失败。②`tests/test_store.c` 的写入与查询**两侧都用了小写**——期望值是从实现抄的，实现错了测试跟着错 → 假通过。
**修复**：查询侧改 `strcmp(e->evt,"UNLOCK")==0`；测试改回真大写串并**反向验证**（故意改错一位确认会红——测试也要被测试）。长期方向：事件字符串收敛为枚举+映射表，消灭裸字符串比较。
**考点**：数据流追踪（写侧真源→读侧消费）/ 单测有效性（期望值必须独立于实现）/ 一次修复要问「测试为什么没拦住」。

## A3. 日志滚动写放大——strace 量出来的 O(cap) 隐患
**现象**：怀疑日志写入在认证路径上同步落盘磨损 flash。
**根因**：行数计数依赖运行时全文件遍历（`fopen(rb)+fgetc` 数行），每条日志都 O(cap) 读；饱和后更每条触发一次全文件重写。strace 量化：未饱和追加 200 条重写 0 次；饱和后追加 158 条 rename 全量重写 259 次、写 10.04MB（应然 12KB）。**好消息**：rename 收尾无 fsync → 认证路径零同步落盘（掉电安全不受影响）；重写只在饱和后发生。
**修复**：①行数改内存维护（init 扫一次 + 增量）消除 O(file) 读；②加迟滞 `lines > cap + SLACK` 才滚动，摊还到 O(1)/次。纪律：D7 落地前 cap 不从 500 调 5000（否则单次重写 38KB→385KB、洪峰 6MB→60MB）。
**考点**：文件 IO 与原子替换 / strace 性能取证（先量后猜）/ 摊还分析 / 嵌入式 flash 寿命意识。

## A4. 远程注入「假成功」——无符号枚举吞掉 -1 哨兵
**现象**：给 `inject_face` 传非法值 -1 想验证错误处理，接口却回 `{"code":0,"injected":true}` 假成功。
**根因**：`face_reason_t` 全部枚举值 ≥0 且无显式底层类型。`-1` 经整型提升再转枚举参与比较，在无符号语境下 `if (reason < 0)` **恒为假**——哨兵值整个被类型系统吞掉，非法值直达注入层。
**修复**：入口先以有符号整型收参、显式范围校验后再转枚举；非法值走统一错误码（1002 类）。不改枚举底层类型（影响面大），校验放在 API 边界。
**考点**：C 类型系统（整数提升/有符号无符号转换）/ API 边界校验原则 / 错误处理路径必须被测试覆盖。

## A5. 配置双默认值 + 假文档出处
**现象**：环境变量 `SAFE_LOG_MAX` 设了不生效。
**根因**：配置层字段 `s_cfg.log_max_entries` 全仓 **0 个读取点**，真正生效的是 `store.c` 编译期常量 `LOG_MAX_ENTRIES 500`——同一语义两套默认值。连带发现代码注释声称出处「DESIGN.md §3.3」根本不存在，翻归档确认 5000 才是有出处的数字（注释引用与原文相反）。
**修复**：让 `SAFE_LOG_MAX` 真正生效（运行期可调），默认保持 500（零回归）；注释从「假引用」改成「解释该值的后果」（决定滚动重写的写入量）。
**防回归**：引用文档出处前必须打开那份文档；「代码里写假出处比没注释更糟」。
**考点**：配置系统设计（env→config→consumer 全链路闭环）/ 单一事实源 / 文档可追溯性。

## A6. A/B 测试跑在已删除的旧二进制上——部署验证铁律
**现象**：板上 A/B 对比「修复无效」。
**根因**：进程跑的是**已被覆盖的旧可执行文件**（`/proc/<pid>/exe` 显示 `(deleted)`）——覆盖文件不等于重启进程。反推：部署只传了文件没重启服务；BusyBox 无 `pkill`（`pkill` 静默失败继续往下跑，「杀进程」是假动作）→ 用 `killall` 或 init 脚本 restart。
**固化为部署铁律**（每次必查，10 秒）：①PID 变了；②`/proc/<pid>/exe` 非 `(deleted)`；③日志有本次新增打印（新代码真的在跑）；④关键配置打印核对，不靠猜。
**考点**：Linux 进程与 inode 关系（覆盖≠重启）/ `/proc` 调试 / BusyBox 精简环境适配 / 「验证部署」与「验证代码」是两件事。

## A7. FM225 单帧/五向命令码用错（0x13 vs 0x1D）
**现象**：录入「总是失败/超时」；偶发「成功」但模组里没有用户。
**根因**：命令码 `0x13` 合法存在（它是五向录入），只是**语义用错了**——单帧场景发了五向命令。编译、协议校验、重发全部正常，所以静默出错。
**怎么发现**：用户实测反馈 + 决定性日志 `enroll 应答 uid=65535`；拿桌面 FM225 测试工具当参考实现，逐字节对比命令表——`0x1D ENROLL_SINGLE`（应答即结果）与 `0x13 ENROLL_5`（应答是进度）语义完全不同。
**修复**：命令码与 `face_dir` 按模式选。
**考点**：协议语义不能只靠「合法即通过」/ 对照参考实现比对。

## A8. uid=0xFFFF 伪成功
**现象**：app 显示录入成功，模组清单 0 个；界面挂「删人脸」却删不掉。
**根因**：模组回 `mr=SUCCESS` 但 uid 是**未分配占位值 0xFFFF**——「成功」里藏着假成功，app 照单全收写下指向不存在用户的假绑定。
**怎么发现**：`enroll 应答：err=0 mr=0x00 uid=65535` + `模组用户清单：0 个` 两行日志并排看。
**修复**：源头拒收（`uid<=0 || ==0xFFFF` 判失败）+ 存量清理（读盘归一化）。
**考点**：三源对账（app 日志 / 模组清单 / users.json）/ 「成功」响应里也可能藏失败。

---

## A9. face_dir 掩码语义误用（0x1F）
**现象**：「还没转头就录成功了」（914ms 完成）。
**根因**：`0x1F` 是**累计掩码语义**（五个方向都已完成），不是「要求采五个方向」。传全 1 掩码，模组直接判成功。
**怎么发现**：物理证据——914ms 就 SUCCESS；整个会话只有 1 条 NOTE（模组根本没采五次）。
**修复**：逐方向分 5 次（正0x01→右0x02→左0x04→下0x08→上0x10），app 按累计掩码主动续发。
**考点**：协议字段语义（请求掩码 vs 累计掩码）/ 用硬指标（耗时、帧计数）证明「模组没采集」比推理可靠。

## A10. 幂等对账的死角：本次运行期新产生的假绑定
**现象**：某用户从没录成功却显示「删人脸」，删除被拒。
**根因**：启动对账只跑一次（幂等设计）——它管不到「本次运行期间新产生的假绑定」。时序还原：对账标失效 admin（旧假值）→ 旧 A8 bug 又给该用户写新假值 → 无人再管。
**修复**：读盘归一化非法 face_id（源头校验 + 存量清理两道闸门）。
**教训**：**幂等的一次性机制不能当唯一兜底**。
**考点**：机制叠加分析（两个各自正确的机制叠出死角）/ 时序还原。

---

## A11. store_init 不填充内存态 policy
**现象**：users.json 里 `enroll_five_way=true`，启动日志却是「录入模式切换 → 单帧」。
**根因**：`store_init` 「看起来做了初始化」（建目录、引导默认 admin），**但没做「读盘填内存」**。`g_policy` 停在编译期默认值（enroll_five_way=false），直到 UI 首次调 `load_users()`。
**怎么发现**：顺数据流逐层排查——盘上数据 ✓ → 解析代码 ✓ → 调用时序 ✗（`user_policy()` 在首次 load 之前被调用）。
**修复**：`store_init` 在「文件已存在」分支补一次 `load_users()`——初始化内存态本来就是它的职责。
**考点**：初始化职责边界 / 调用时序先于「看起来初始化了」的判断。

---

## A12. 主泵里的非幂等调用
**现象**：无（自查发现）。
**根因**：`face_service_set_enroll_five_way(user_policy()->…)` 被放进 20ms 主线程泵——每秒约 50 次加锁 + 整份 policy 拷贝，全是无用功。
**修复**：移到 `app_main` 初始化，只做一次。
**考点**：泵里只放幂等的东西 / 「代码放在哪」比「代码对不对」更影响性能。

---

## A13. 事件广播无人订阅
**现象**：清空模组人脸后用户页不刷新。
**根因**：事件「发出去了」但没人听；`cred_reconcile` 注释甚至写着「属死代码，若将来确有订阅者再恢复」。
**修复**：三处联动（page_users 订阅 + 两处广播）——恰好是注释里预留的那个「将来」。
**考点**：事件总线「发了≠有人处理」/ 死代码注释是逻辑缺口的免费信号。

---

## A14. 回调硬编码导致第二个使用者静默失效
**现象**：第二个使用该行的开关点了没反应。
**根因**：`lv_obj_add_event_cb(sw, vpin_click_cb, …)` 回调**硬编码**——第一个使用者一切正常，第二个静默失效。
**怎么发现**：**编译警告** `mode_click_cb defined but not used`——unused-function 是逻辑 bug 的免费信号。
**修复**：回调改由调用方传入。
**考点**：别忽略编译警告 / 复用组件回调必须参数化。

---

## A15. static 函数声明位置错误
**现象**：`implicit declaration` + `conflicting types`。
**根因**：同一个错一天犯两次（`page_system.c` 的 `clear_face_btn_cb`、`backend_fm225.c` 的 `fm225_next_dir`）——声明放「定义之前」而非「使用点之前」。
**教训**：声明放**使用点之前**。
**考点**：C 声明/定义顺序 / 编译错误定位。

# Part B —— 🔵 环境/运维速查（人类也会遇到，但不是代码 bug）

> 这些不是产品缺陷，是 Linux/嵌入式环境的客观特性。任何人类开发者在同样环境下都会撞，值得记为速查。

| 坑 | 一句话结论 | 排查第一层 |
|---|---|---|
| brltty 抢占 CH340 | Ubuntu 22.04 自带盲文服务经 udev 抢走 CH340 接口，`/dev/ttyUSB0` 消失 | `lsusb -t` 看 `Driver=` 是否为空；`systemctl mask brltty-udev` + 重载 `ch341` |
| 板子息屏 | 根因内核参数 `consoleblank=600`，不是驱动问题 | 改内核 cmdline 或关 consoleblank |
| `/tmp` 写爆 | 板上 `/tmp` 是 tmpfs（~250MB 内存），调试日志写 `/var/log` | `df -h /tmp` |
| ADB 传文件截断 | 两端必 `wc -c` 比对；2457600 变 348160 就是截了 | 传后 `wc -c` 双端核对 |
| 触摸没反应 | LVGL evdev 必须指到 `/dev/input/event1`（Goodix），且需 root | `ls -l /dev/input/event1` |
| 相机冷启动降级 | UVC 枚举 7.43s 晚于 S05lvgl 自启 → 应用层延迟重扫，不在内核层修 | 应用层定时器重扫 `/dev/video*` |
| 相机只出 MJPG | V4L2 格式协商失败就停下回报，不硬解 | 检查 `VIDIOC_ENUM_FMT` 支持列表 |
| LVGL tick 驱动源 | SDL 移植层 `lv_tick_set_cb(SDL_GetTicks)` 注册墙钟；`lv_tick_inc` 对 SDL 端口调度是空操作（但裸板移植仍需它） | `grep lv_tick_set_cb` 确认驱动源 |

> 注：原「案例6 LVGL tick 测量」的**核心知识（tick 驱动源决定 timer 行为）是真的**，但原文把「截图时间漂移」部分归因于「同机并行跑 2 个实例」——那其实是 AI 自己的测试 harness 噪声（见 Part D），并非 SDL 端口的产品缺陷。产品从未因此故障；人类工程师用单调钟打点验证 612ms 与 600ms spec 吻合。

# Part C —— 🟡 调试方法论（普适，无论谁开发都该掌握）

> 从隐匿 Bug 篇与前期案例提炼，每条对应真实案例。

1. **先拿证据，再下结论**（A8）——不是猜「可能同步有问题」，而是先拿 `uid=65535` 铁证。
2. **三源对账**（A8）——app 日志 / 模组清单 / users.json 三方摆一起：「app 说成功、模组说没有」必有一假。
3. **物理证据链**（A9）——914ms + 1 条 NOTE 是硬指标，比语义推理硬。
4. **对照参考实现**（A7）——桌面测试工具是「能跑通的实现」，比读手册猜语义可靠。
5. **时序还原，找机制叠加死角**（A10）——两个各自正确的机制叠加出无人负责的区间；画时间线比反复读代码快。
6. **顺着数据流走**（A2/A11）——现象 → 原始数据 → 解析 → 时序 → 设计职责，每层排除一个嫌疑。
7. **别忽略编译警告**（A14）——`unused-function` 看着无害，实际暴露逻辑 bug。
8. **一次只改一件事**——先让单帧通（0x1D），真机验证后再做五向；一次改两件事出错就不知道是谁引入的。
9. **可复现性是调试前提**——`| tee` 会让 stdout 全缓冲、Ctrl+C 丢日志；启动器常备 `stdbuf -oL -eL`。先保证日志拿得到，再谈调试。
10. **下结论前读原始数据**——日志片段 ≠ 全局状态，读一次 users.json 十秒钟。
11. **量化先于猜测**（A1/A3）——用对照实验和 strace 把「怀疑」变成「数据」，判据要能从常量推算。

# Part D —— 🟠 AI 工具链注记（已从案例剔除，人类不必照搬）

> 以下均**不是产品缺陷**，是 AI 经 SSH/ADB 操作 VM 与自研部署脚本时制造的问题。仅作存档，避免后人误以为是工程 bug。完整记录见 `ssh-ubuntu` 技能 SKILL.md §4。

- **「同机并行跑 2 个实例导致截图时间漂移」**：实为 `ssh_helper.execute()` 连接闪断时自动重连并重跑后台启动命令，把 `setsid ./lvglsim &` 跑了两次 → 双实例同消费串口/MQTT。表现为「同一条命令收到 2 条回执」，极易被误判成「代码重复消费」。规避：后台启动前先 `pkill -f bin/lvglsim`，启动后校验 `pgrep -x lvglsim | wc -l == 1`。
- **「后台进程起不来：adb base64 管道吞行尾 `&`」**：AI 部署脚本把 `setsid ... &` 写进 `echo <b64> | base64 -d | su` 管道，`&` 不生效，进程起不来。正确做法：启动命令写进 .sh 文件再 `setsid`。属 AI 自研部署脚本写法坑。
- **「`su -c` 命令失效」**：adb→板子多层 shell 吃掉 `su -c` 的引号，命令里的 `&&`/`-f` 被 BusyBox ash 错解。AI 改用 base64 管道 `echo <b64> | base64 -d | su` 绕开。人类手工 `adb shell` 一般不踩，但上板自动化脚本可借鉴。
- **行尾被脚本改 / 长文本经 stdout 往返被截断 / RC 探针放错位置**：均为 AI 经 SSH 文本模式读写 VM 文件的副作用（文本模式 universal-newlines 改行尾、stdout/stderr 往返丢长文本）。人类用普通编辑器/终端操作不会遇到；本地写 VM 文档须 `newline='\n'`、长文本走 VM 本地脚本。
