### 1.3 差距清单（按优先级）

1. **P0 · FR-25 TLS 未闭环**——代码 90% 就位，缺的是：自签 CA 签发脚本、broker/客户端证书、mosquitto TLS 监听配置、`g_tls_enable` 打开并过"无证书拒连"验收（§10 已写好验收标准）。**这是规约声称"本期启用"的唯一未兑现 P1 需求，面试被问"你的 TLS 呢"必须有答案**。
2. **P1 · FR-29 签名验证缺失**——当前只有 SHA-256 完整性（防损坏），无来源签名（防投毒）。开发态 HTTP 明文可接受，但应把 `sha256 → HMAC-SHA256` 的升级点写进 ota_apply 注释。
3. **P1 · FR-29 断点续传缺失**——验收标准明写未做；板端 wget 加 `-c` + 服务端支持 Range 即可（自研 ota_http 补 Range 分支）。
4. **P2 · 规约自身滞后三处**——FR-13（底栏页签→rail）、§9.3（RTC"已新增"实为 DS3231 到货前走 sys 后端）、NFR-4 措辞。**规约驱动开发的原则是"代码变更先回改规约"，反向差距同样要修**。

## 二、项目评估（生产级视角）

### 2.1 扩展性 —— 强，方向正确

- **HAL 全面抽象**：face（fm225/null）、net（wpa/none）、camera（v4l2/null）、time（sys/rtc 预留）四个后端接口 + `SAFE_*_BACKEND` 编译期选择，`check_layers` 单测强制"业务不 import 平台头"。换模组/换平台不动业务代码——这是 NFR-5 的落地，也是"新增硬件能力不改动业务代码"的实证。
- **编译开关切特性**：SAFE_FEATURE_MQTT_TLS 等特性开关不改变业务行为（FR-25 的"配置开关"语义已就位）。
- **事件总线解耦**：UI 与业务通过 EV_* 订阅，跨页联动（EV_USER_CHANGED / EV_FACE_EVENT）已有实效。
- **OTA 预留了模型升级通道**：manifest 结构天然支持多产物（lvglsim + 未来的模型文件）。

### 2.2 规范性 —— 强于多数校招项目

三文档规约驱动 + D 系列缺陷台账 + 19 项 ctest + 分层强制检查（check_layers）+ 部署验证铁律 + commit 分类（feat/fix/docs/chore）。"没写进度=没做完"的纪律本身就是差异化亮点。

### 2.3 是否需要重构？—— 不需要大重构，需要局部减脂

架构（hal / core / ui / ports 分层 + 单向依赖 + 事件总线）是健康的，伤筋动骨的重构**弊大于利**。局部问题：

| 问题 | 现状 | 建议 |
|---|---|---|
| **page_users.c 2381 行** | 行渲染 + 4 个弹窗 + 键盘逻辑 + 名称缓存全在一个文件 | 拆 `page_users_rows.c`（列表/行渲染）与 `page_users_dlg.c`（弹窗族），头文件只暴露页面创建函数；**纯搬移零逻辑改动，ctest 全绿即安全** |
| **mqtt_client.c 1200+ 行** | codec 已拆（test_mqtt_codec），但 client 里 TLS 流+重连+统计+业务发布混居 | `tls_stream.c` 已独立——续拆"重连策略"为独立单元即可，优先级低 |
| **事件字符串裸 strcmp** | "UNLOCK"/"unlock" 大小写坑（附录 B 案例）已修但机制仍在 | 收敛为枚举+映射表，一次搞定整类风险；顺手让 test_store 期望值取自规约常量 |
| **ota_apply.sh LOCAL 回退语义** | 回退旧包时用**当前 manifest** 的 SHA 校验 → 必然 ERR_SHA（安全失败但报错误导） | 回退时改用 LOCAL manifest 配套校验；或 ERR 分支区分 `ERR_DOWNLOAD+LOCAL 过期` 与 `ERR_SHA` 两种文案 |
| **两个服务器工程的 git** | ota-server / mqtt-server 无版本管理 | `git init` + 首提交，make_ota_pkg 产物加 .gitignore |

### 2.4 冗余排查结论

- 归档目录（规约/归档/）有 6 个历史版本需求规约——**不冗余**，规约演进的考古价值，且"不维护不改写"已约定；
- store.c 双默认值（SAFE_LOG_MAX 案例）已修；
- 真正可清的：`build_pc`/`build_board` 若未 gitignore 应补（产物目录不应入库）；板上 `/tmp/ota_x/` 解压残留可让 apply 脚本收尾清理（一行 `rm -rf`）。

### 2.5 给秋招的优先级建议

1. **TLS 闭环（1~2 天）**：openssl 签 CA + 设备/手机证书、mosquitto 开 8883 双向互验、`g_tls_enable=true` 过"无证书拒连"验收——把规约里唯一未兑现的"本期启用"变成真话，这是面试含金量最高的一块；
2. **OTA 补断点续传 + HMAC（1 天）**：wget -c + ota_http Range 分支；HMAC 密钥预置方案写进技术路线规约；
3. **规约三处滞后回改（30 分钟）**：FR-13 rail、§9.3 RTC 措辞、NFR-4 有限补传——保持"规约=事实"的信誉；
4. **page_users.c 拆分（半天）**： interview 讲"我如何保持 2000+ 行 UI 文件的可维护性"比拆本身更有价值；
5. 事件枚举化（半天，可后置）。

## 三、结论

- **需求实现率**：P0 22/22 全落地；P1 已落地 9/12（差 TLS 闭环、OTA 签名、断点续传）；P2 差撬动告警（无硬件）与模组加密（厂商依赖）。
- **隐藏 bug 排查（2026-10-02 专项）**：复审了当日全部 UI 改动（表头对齐链 718、refresh_cb 生命周期）无新缺陷；识别 ota_apply.sh LOCAL 回退的报错误导（登记为设计边界，见 §2.3）。
- **总体判断**：这不是"学生 demo"，是一个有规约、有台账、有测试、有部署纪律的工程。**不需要重构**；把 TLS 闭环和 OTA 两项验收补齐后，"生产级"三个字基本站得住。
