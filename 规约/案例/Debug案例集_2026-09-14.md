## 案例 1：FM225 指纹/人脸模组「无退避疯狂重发」——跨模块时钟基准混用

**30 秒版**：串口命令重发把日志刷屏（40 秒内 489 行重发日志、3.95 轮/秒）。先用对照实验排除"应答慢"的假设，再用微基准发现重发发生在超时窗口开启之前，最后代码审计定位到**两个模块对"毫秒"的定义不同**——一个是系统单调钟，一个是进程内计数器，相减恒为巨值，超时永远立刻触发。

**背景**：PC 验证 FM225 链路时，`VERIFY(0x12)` 命令的重发日志刷屏：40s 内 671 行日志中 489 行（73%）是重发；且同一日志里明明有 `verify 应答` 的解析记录。

**排查步骤**：
1. **量化现象**：统计日志——3.95 轮/秒的重发频率；存在应答仍重发 → 直觉假设"超时窗口过短"存疑。
2. **对照实验（单变量）**：让模拟模组完全不回帧（silent）vs 秒回（reply）各跑 40s——重发量 1438 vs 1933，同一量级 ⇒ **重发与应答快慢无关，"超时过短"假设作废**。
3. **微基准定位时间点**：UART open @953ms，首条重发 @1021ms——只隔 68ms（3~4 个 tick），**远早于 800ms 超时窗**；且 reply 模式下重发与应答几乎同刻 ⇒ 重发决策根本不读应答。
4. **代码审计对时钟源**：
   - `backend_fm225.c` 记 pending 时间用 `hal_time_ms()`——**CLOCK_MONOTONIC 绝对值**（开机起算，当时 ≈1.54×10⁶）
   - 而传进来的 `now_ms` 来自 `app.c: s_tick_ms += 20`——**进程内计数，从 0 起算**
   - 超时判断 `(now_ms - s_pending_at_ms) > 阈值`：两个不同纪元的数相减，无符号下溢成巨值 ⇒ **恒超时 → 重发 → 重置基准 → 循环**。注释里写的"800ms 超时/退避"从未生效过。

**根因**：接口契约缺失——`tick(now_ms)` 的"毫秒"没有约定纪元，两个模块各自用了合法但不同源的时钟。

**修复与取舍**：Path A（契约修）`app.c` 改传 `hal_time_ms()`，头文件注释钉死语义。改前先 grep 全仓确认 4 处 `now_ms` 使用方**全部是差值语义**（自洽的相对用法不受纪元影响）才动手——这是零风险的依据。**驳回**了"再叠指数退避"的提案：这里是空转轮询（要持续探测模组恢复），指数退避会把恢复检测推迟，是负优化；`VERIFY_REARM_MS=2000` 本身已是重开节奏。

**验证与防回归**：复测判据从代码常量推算（reply 场景重发=0 硬指标；silent 场景 40s≈24 次 = 800ms×3 重试 + 2s REARM），不拍脑袋；重发日志降频到每轮 ≤1 行。

**考点**：串口协议超时重传设计 / 时钟与定时器（CLOCK_MONOTONIC vs 自维护计数）/ 对照实验排除变量 / "判据必须能从常量推算"。

## 案例 2：USB 串口设备"插上就消失"——brltty 抢占 CH340

**30 秒版**：FM225 模组插上 Ubuntu 虚拟机，CH340 驱动加载了、`ttyUSB0` 也出现了，但一会儿就没了。从设备层往驱动层逐层排查，最后在内核日志里发现是系统自带的盲文服务 brltty 通过 udev 把接口配置抢走了——mask 掉它并重载驱动，节点稳定。

**排查步骤**：
1. `ls /dev/ttyUSB*` → **不存在**，但之前明明出现过。
2. `lsusb` → `1a86:7523 CH340` 在 ⇒ USB 枚举正常，物理层和供电没问题。
3. `lsmod | grep ch341` → 驱动已加载 ⇒ 不是驱动缺失。
4. `lsusb -t` → 该接口 **`Driver=` 为空** ⇒ 设备在、驱动在，但**没绑定**——锁定"绑定被抢"。
5. `dmesg` 找到铁证：`usbfs: interface 0 claimed by ch341 while 'brltty' sets config #1` + `ch341-uart converter now disconnected` ⇒ brltty（盲文终端守护进程，Ubuntu 22.04 自带）按 udev 规则抢先 claim 了接口。
6. 修复：`systemctl mask brltty-udev.service`（彻底禁用 udev 触发）+ `stop/disable brltty`；再 `modprobe -r ch341 usbserial && modprobe ch341` 重新探测绑定。
7. 验证：`lsusb -t` 显示 `Driver=ch341`、`/dev/ttyUSB0` 稳定存在、自检脚本双向通帧。

**根因**：发行版的服务策略与开发场景冲突（brltty 支持部分 CH340 设备的盲文点字显示器）。

**防回归**：mask 而非仅 stop（stop 在下次插拔还会被 udev 拉起）；把"`lsusb -t` 查 Driver 绑定"固化进串口排查第一层。

**考点**：USB 枚举与驱动绑定模型（device→driver→/dev 节点三层）/ udev / 内核日志定位法——**从现象层逐层下钻，每层排除一个假设**。

## 案例 3：「最后开启」恒为 `--`——大小写失配被自测用例掩护

**30 秒版**：日志页的"最后开启"永远是空。顺着数据流从写入侧全量 grep 真源，发现写入是大写 `UNLOCK`、查询是小写 `unlock`；再深挖为什么单测没拦住——**测试文件里写入和查询用了同一个错误的小写字符串**，两侧一起错，单测全绿。

**排查步骤**：
1. 现象锁定：UI 查询"最后开启"恒空，但日志列表里明明有开锁记录。
2. **数据流追踪**：找到写入侧真源，全量 grep 各模块的 `log_append` 事件字符串并列表——`auth_fsm.c` 全大写（`UNLOCK/DENY/ALARM/LOCKOUT`）、`page_users.c`（`user_add/...`）、`store.c`（`setting_change`）、`page_system.c`（`factory_reset`）。
3. 对照查询侧：`page_logs.c` 用小写 `"unlock"` 做 `strcmp` ⇒ 精确匹配失败。
4. **追问为什么测试没拦住**：`tests/test_store.c` 的写入与查询**两侧都用了小写**——期望值是从实现抄的，实现错了测试跟着错 ⇒ 假通过。之前同类 bug 只修了 HOME 页的显示侧，根子（测试无效）一直没动。

**根因**：双缺陷叠加——①字符串 magic value 无单一定义点；②单测期望值来源是"实现"而非"规约"。

**修复与取舍**：UI 侧改 `strcmp(e->evt,"UNLOCK")==0`；测试改用真大写串并**验证改后单测真的能捕获大小写失配**（把测试改错一位确认会红——测试也要被测试）。长期方向：事件字符串收敛为枚举+映射表，消灭裸字符串比较。

**考点**：数据流追踪（写侧真源→读侧消费）/ 单元测试有效性（期望值必须独立于实现）/ 一次修复要问"测试为什么没拦住"。

## 案例 4：日志滚动写放大——strace 量出来的 O(cap) 隐患

**30 秒版**：怀疑日志写入在认证路径上有同步落盘磨损 flash。用 strace 按四种场景量化：发现**未饱和时零重写、日志路径零 fsync**（原怀疑不成立），但真问题藏在更普遍的地方——**每次追加都无条件全文件遍历计数**，饱和后更是每条日志触发一次全文件重写，洪峰期写放大 ~500×。

**排查步骤**：
1. 提出怀疑：`log_append` 可能每次全量重写 + fsync，cap=500 时认证洪峰（158 次 DENY）会磨 flash。
2. **strace 量化**（不读代码先量）：四场景对照——未饱和追加 200 条：重写 **0** 次；饱和后追加 158 条：rename 全量重写 **259** 次、写 10.04MB（应然 12KB）。
3. 结论修正两次：①`rename` 收尾**无 fsync** ⇒ 未违反"认证路径零同步落盘"（掉电安全不受影响）；②重写只在饱和后发生。
4. **读完整函数找普遍成本**：每次 append 都 `fopen(rb)+fgetc` 遍历全文数行数——O(cap) 读，**每条日志都发生**，528MHz 单核 A7 上 cap=5000 时一次 ~385KB。

**根因**：行数计数依赖运行时全文件遍历；滚动无迟滞，每追加一条都越过上限一次。

**修复与取舍**：①行数改内存维护（init 扫一次 + 增量）消除 O(file) 读；②加迟滞 `lines > cap + SLACK` 才滚动，把重写摊还到 O(1)/次。**先立一条纪律：D7 落地前 cap 不从 500 调 5000**（否则单次重写 38KB→385KB、洪峰 6MB→60MB，放大现有伤害）。

**考点**：文件 IO 与原子替换 / strace 性能取证（先量后猜）/ 摊还分析 / 嵌入式 flash 寿命意识。

## 案例 5：远程注入"假成功"——无符号枚举吞掉 -1 哨兵

**30 秒版**：给 `inject_face` 传非法值 -1 想验证错误处理，接口却回"注入成功"。原因是枚举全为非负值，而 C 的枚举传参后按无符号参与比较，`if (reason < 0)` **恒为假**——哨兵值整个被类型系统吞掉。

**排查步骤**：
1. 黑盒探测：`inject_face reason=-1` → 返回 `{"code":0, "injected":true}` 假成功。
2. 读签名：`face_reason_t` 全部枚举值 ≥0，无显式底层类型。
3. 类型推演：`-1` 经整型提升再转枚举类型参与比较；实现在无符号语境下 `<0` 恒假 ⇒ 校验分支形同虚设，非法值直达注入层。

**根因**：错误哨兵走"魔法数值"而非类型系统；无显式底层类型的枚举在比较语境下的符号性依赖实现。

**修复与取舍**：入口先以有符号整型收参、显式范围校验后再转枚举；非法值走统一错误码（1002 类）。取舍：不改枚举底层类型（影响面大），在边界处收敛——**校验放在 API 边界，类型修复放长期**。

**考点**：C 类型系统（整数提升/有符号无符号转换）/ API 边界校验原则 / 错误处理路径必须被测试覆盖。

## 案例 6：一次被实测推翻的结论——LVGL tick 驱动源与测量口径

**30 秒版**：我用三个采样点断言"UI 动画时长被压缩了一半"，工程师仪表化实测后推翻：真实时长 612ms 与常量 600ms 吻合。深挖发现 SDL 移植层用 `lv_tick_set_cb(SDL_GetTicks)` 注册了**墙钟**驱动，手动 `lv_tick_inc` 对调度是空操作；我看到的"压缩"是**渲染开销让快照时间漂移 30~280ms**。

**排查步骤**：
1. 我的错误方法：SHOT_MS∈{40,200,400} 三点红像素计数 160/160/0 ⇒ 推断"FAIL 态 ~300ms 回退，spec 600ms 被压缩 2×"。
2. 被证伪：工程师用 `hal_time_ms()` 单调钟打点，回退实测 **612ms** —— spec 没被压缩。
3. 找真机制：`grep lv_tick_set_cb` → `lv_sdl_window.c:70` 注册 `SDL_GetTicks` ⇒ LVGL timer 全跑真实墙钟，`lv_tick_inc()` 对调度空操作（但**不能删**——未注册 tick cb 的裸移植板子还需要它）。
4. 解释漂移：快照墙钟 ≈ SHOT_MS + 30~280ms 渲染开销，且**随机器负载漂移**——当时同机并行跑了 2 个实例。

**教训（比结论更值钱）**：①只扫 3 个点就下普遍结论必翻车；②**两个实测值打架，先怀疑自己的测量口径**；③时间敏感的验收判**日志时间戳/单调钟打点**，不信"拍摄时刻"；④让协作者**证伪**自己而不是确认自己——这条后来抓出了我连续 6 次误判。

**考点**：LVGL tick 机制（tick 驱动源决定 timer 行为）/ 测量方法论（口径先于结论）/ 单变量对照与仪器化。

## 案例 7：`SAFE_LOG_MAX` 形同虚设——配置双默认值与"假出处"

**30 秒版**：环境变量 `SAFE_LOG_MAX` 设了不生效。全仓 grep 发现配置层写的字段**没有任何读取点**，真正生效的是存储层编译期常量 500——同一语义两套默认值；连带发现代码注释声称的文档出处（DESIGN.md §3.3）根本不存在，翻归档后确认 5000 才是有出处的数字。

**排查步骤**：
1. 复现：`SAFE_LOG_MAX=3` + 种子 5 条 → 滚动上限仍是 500。
2. `grep` 读取点：`s_cfg.log_max_entries` 全仓 **0 个消费方** ⇒ 配置链断在半路。
3. 找真源：生效值是 `store.c` 编译期 `LOG_MAX_ENTRIES 500`。
4. **核验注释出处**：注释说"500 有 DESIGN.md §3.3 依据"→ 打开归档原文：§3.3 写的是"N 条"、另一处写"待用户拍板"、需求文档写"5000 条且需确认 flash 容量" ⇒ **注释引用与原文相反**（5000 才有出处）。

**修复与取舍**：让 `SAFE_LOG_MAX` 真正生效（运行期可调），默认保持 500（零回归 + 现行规约只要求"有上限"）；注释从"假引用"改成"解释该值的后果"（决定滚动重写的写入量）。

**防回归**：立规——引用文档出处前必须打开那份文档；"代码里写假出处比没注释更糟"。

**考点**：配置系统设计（env→config→consumer 全链路闭环）/ 单一事实源 / 文档可追溯性。

## 案例 8：A/B 测试跑在旧二进制上——部署验证四条铁律

**30 秒版**：板上 A/B 对比测试"修复无效"，排查后发现进程跑的是**已被覆盖的旧可执行文件**（`/proc/<pid>/exe` 显示 `(deleted)`）——覆盖文件不等于重启进程。由此固化了每次部署必查的四条 10 秒铁律。

**排查步骤**：
1. A/B 结论反常 → 先不信代码，查"跑的到底是不是新代码"。
2. `ps` 比对 PID：与上次相同 ⇒ 进程没重启。
3. `ls -l /proc/<pid>/exe` → `(deleted)` ⇒ 铁证：二进制已被覆盖，但进程还挂在旧文件的 inode 上。
4. 反推机制：部署流程只传了文件没重启服务；BusyBox 环境还没有 `pkill`（`pkill` 静默失败继续往下跑，"杀进程"是假动作）⇒ 用 `killall`，或走 init 脚本 restart。

**固化为部署铁律**（每次必查，10 秒）：①PID 变了；②`/proc/<pid>/exe` 非 `(deleted)`；③日志有本次新增的打印（新代码真的在跑）；④关键配置打印出来核对，不靠猜。

**考点**：Linux 进程与文件 inode 的关系（覆盖≠重启）/ `/proc` 调试 / BusyBox 精简环境适配 / "验证部署"与"验证代码"是两件事。

## 使用建议（面试怎么讲）

1. **先讲排查路径，再讲答案**——面试官考的是过程：现象量化 → 假设 → 用什么手段验证 → 证据链 → 结论修正。每个案例的"排查步骤"就是现成的脚本。
2. **主动讲被推翻的经历**（案例 6）：对照实验推翻自己假设、被队友实测打脸后修正口径——这比"我一眼看出根因"可信十倍。
3. **把判据数字化**：24 次重发是常量推算、10.04MB 是 strace 量出来、612ms 是单调钟打点——全程有仪表，这是嵌入式工程师的基本功展示。
4. 每个案例结尾都能落到**防回归制度**（部署四条铁律、mock 三条铁律、契约注释、期望值取自规约）——体现从"修 bug"到"让 bug 不再发生"的层级。
