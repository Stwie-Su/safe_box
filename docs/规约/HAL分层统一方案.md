# HAL 分层统一方案（评审修订版）

- 版本：v1.1（2026-10-22 修订）；v1.0 的问题：事实过期（"目录不是 git 仓"、"face 还没改名"）、漏了看门狗模块、术语太密。本版按仓库现状逐条重核。
- 维护位置：仓库 `docs/规约/HAL分层统一方案.md`（本文）；下载目录那份是同步镜像。
- 范围：`app/hal/` 七个设备模块 + `app.c` 启动装配 + `core/config.c` + `tools/check_layers.sh`
- 一句话目标：让"换硬件只改一个目录，业务代码不用动"从口号变成脚本能检查的规矩。
- 总原则：**不重写架构，只把 HAL 内部的写法统一到同一个模板；程序跑起来的行为一概不变。**

## 0. 现在乱在哪（先看清治什么病）

| 现状 | 具体位置 | 会出什么事 |
|---|---|---|
| 界面和启动代码直接引用实现层的内部头文件 | `page_face.c`、`page_enroll.c`、`app.c` 引 `face/face_thread.h`；`app.c` 还引 `time/time_backend.h` | 实现层一改内部结构，界面跟着改；换实现时改一处漏一处 |
| "用哪个实现、设备文件在哪"散在多处各自读环境变量 | `app/hal` 里共 19 处 `getenv`，分布在 12 个文件（含 watchdog 5 处、actuator 3 处） | 同一份配置有多个读法，改配置方式要全仓找；脚本也查不出谁在读 |
| 内部结构写进了对外头文件 | `hal_net.h:92` 的 `net_backend_t`、`:94` 的 `hal_net_set_backend()` | 业务本来看不到内部，现在能看到，边界名存实亡 |
| 名字与实物不符 | `face_thread.c` 实际是"一条线程同时管摄像头和串口"的并发设施 | 名字像"人脸线程"，新人会找错文件 |

> 已经解决、不用再做的：`face_service_* → hal_face_*` 已于 2026-10-15 完成（`d2feae0`，现全仓 0 处旧名 / 165 处新名）；后端实现文件已于同日统一成 `backend_<实现>.c`（`53fd7ea`）。

## 1. 目标分层（还是五层，只把 HAL 内部理顺）

```
┌──────────────────────────────────────────────────────┐
│ 界面层   ui/          LVGL 页面，只管画和收触摸          │
│ 业务层   core/        状态机 / 存盘 / MQTT，不碰硬件     │
│          （两层之间只靠事件通知，不互相引用）             │
├──────────────────────────────────────────────────────┤
│ 启动装配  app.c + core/config.c                      │
│   全程序只有 core/config.c 读环境变量                    │
│   启动时决定每台设备用哪个实现，当参数传给各 init()       │
├──────────────────────────────────────────────────────┤
│ 对外接口  app/hal/hal_<dev>.h                        │
│   每台设备一个头文件，业务只能看见这些函数                │
├──────────────────────────────────────────────────────┤
│ 实现      app/hal/<dev>/                             │
│   <dev>_service.c         实现对外头里的函数；开机选实现、 │
│                          选不到就降级；把调用转给选中的实现│
│   <dev>_backend.h         函数表类型（内部头，只本目录和测试用）│
│   backend_<实现>.c        真干活的文件：ioctl / 串口 / 协议 / 假实现│
├──────────────────────────────────────────────────────┤
│ platform/  换平台（电脑 SDL ↔ 板子 fbdev）不动上面任何一层 │
└──────────────────────────────────────────────────────┘
```

**为什么是五层，不是三层**（面试常问，答案要有因果）：

- 界面和业务分开：LVGL 只能在主线程碰。混在一起，后台线程一更新数据就会去改界面，表现为随机花屏或崩溃。
- 业务和 HAL 分开：业务不该知道用的是 V4L2 还是串口。分开之后，电脑上没有相机也能开发（用空实现顶上），换硬件不用改业务。
- platform 单独一层：同一份界面代码在电脑和板子上跑，差别只在显示和输入怎么来。

## 2. 走一条真实调用链（面试就讲这个）

点一下"人脸解锁"按钮，代码依次经过：

```
page_face.c        hal_face_verify(...)        ← 界面只认这个函数名
face_service.c     转给开机时选好的实现          ← 选谁、失败怎么降级，只在这一层
backend_fm225.c    组串口帧 → 发出去 → 等回应    ← 换硬件只改这个文件
event_bus          结果回主线程 → 界面更新
```

换硬件时改动范围：**实现层一个文件 + 启动配置一行，界面和业务零改动。**

三个能直接举例的收益（说给面试官听）：

1. 同一个程序，电脑（SDL）和板子（fbdev）跑，界面代码一行没改——平台差别被 platform 层吃掉了。
2. 相机没插也能开发：空实现会顶替，界面显示占位，日志写"后端=none"。
3. 人脸识别链路可以自动测：假实现按脚本返回"通过/失败"，不用真模组也能跑完整流程。

## 3. 统一规则（5 条）

| # | 规则 | 为什么 | 怎么检查 |
|---|------|--------|----------|
| R1 | 每台设备对外**只有一个头文件** `hal_<dev>.h`；线程、函数表等内部文件不对业务层开放 | 判断"这台设备能干什么"只看一个文件；边界能被脚本检查 | `grep -rn '#include "hal/' app/ui app/core` 只允许命中 `hal_*.h` |
| R2 | **用哪个实现、设备路径是什么，启动时定一次**，全程序只有 `core/config.c` 读环境变量 | 配置只有一个来路；改配置方式不用全仓找 | `grep -rn getenv app/hal` 应为 0（两个调试开关除外） |
| R3 | **函数表类型只放内部头**，对外头文件里不得出现 `_backend_t` | 业务只是调函数，看不到内部结构 | `grep -n _backend_t app/hal/hal_*.h` 应为 0（注释里的提及一并清掉） |
| R4 | **重试、降级、探测这类策略只写在 `<dev>_service.c`**；`backend_*.c` 只负责和硬件打交道 | 换实现时策略不跟着搬家 | 评审时看文件职责 |
| R5 | **测试专用函数一律 `test_` 前缀**，只声明在内部头或测试目录；生产代码不得调用 | 看名字就知道"只能测试用"；`grep test_` 能列出全部测试入口 | `check_layers.sh` 新增规则 (i) |

### 文件命名：本轮**不改**（原方案这一条撤销）

现状是 `hal/camera/backend_v4l2.c` 这种，符合《技术路线规约》§1.3 的 `backend_<实现>.c`。原方案想再加设备前缀（`camera_backend_v4l2.c`），评审结论是撤销，理由三条：

1. 目录名已经说明了设备，`hal/camera/backend_v4l2.c` 读起来没有歧义；
2. 7 天内第二次全仓改名，git 记录和文档引用会再失效一次，换来的只是名字长一点；
3. 与现行规约 §1.3 冲突——要改就得先改规约，为审美付两次代价，不划算。

**唯一保留的小改名**：`face_thread.{c,h} → face_worker.{c,h}`（名字与实物对齐：它是一条并发线程，负责同时收摄像头和串口；不是"人脸能力"本身）。只动 2 个文件 + 3 处 include + CMake。

## 5. 不能破坏的行为（每条写清"违反会出什么现象"）

1. **启动顺序不变**（先存盘模块 → 后台线程 → 执行器 → 配置 → 界面 → 状态机 → 远程通道）。违反：界面会拿到还没准备好的设备，表现为启动白屏或随机崩。
2. **相机开机竞态最多重试 3 次**。违反：USB 相机枚举比应用启动晚时，预览永远黑屏，只能重启机器。
3. **网络探测失败不记住失败**。违反：Wi-Fi 比应用起得晚，第一次扫描失败被记住，之后永远连不上，现场表现是"重启才好"。
4. **时间默认用系统时间，没 RTC 就打印降级再回系统时间**。违反：没装 RTC 的板子起不来。
5. **降级日志的原句逐字保留**。违反：现场排障靠 grep 这些句子，改了就对不上文档。
6. **LVGL 只在主线程碰；全程序线程数 4 个不变**（主线程 + worker + MQTT + face）。
7. **关机顺序**：先请求停 → 停止采集 → 关设备 → 等线程退出。违反：线程卡在等帧的调用里，关机要等满超时。
8. **人脸结果共享要有锁**（`face_service.c` 里 `s_last` / `s_seq` 的读写）。违反：偶发读到半截数据。
9. **已登记的 hal→core 反向依赖本轮不动**（`face_service.c` 引 `core/event_bus.h`）。以后改成 core 注册回调再拆，别顺手"修"。

## 7. 本轮不做（写下来防止顺手改）

| 项 | 现状 | 为什么不动 |
|----|------|------------|
| 文件名再加设备前缀 | 已是 `backend_<实现>.c`，符合规约 §1.3 | 见 §3 文件命名（二次改名不值得） |
| storage 不建函数表 | 单文件直连 `statvfs` | 只有一个实现，建表是空仪式感 |
| actuator 保留函数表 | 函数表 + GPIO/mock 两个实现 | 已经换来真实好处：GPIO 后端接入时业务零改动 |
| 相机 fd/frame 是否并入 face 接口 | 现在只有 face 线程在用 | 等"摄像头是否还有第二用途"有产品答案再说 |
| hal→core 反向依赖 | 已登记（规约 §10） | 单独处理，本轮不碰 |
| event_bus / worker / platform | 本来就是干净实现 | 不在收敛范围 |

## 8. 写代码和写文档时的用词约定

这份项目面向"半年后接手的人"和"面试官"，一律用日常说法：

| 别用 | 用 |
|------|----|
| 适配器 | 具体实现（v4l2 版 / 假数据版） |
| 内部契约 | 内部约定（只有本目录和测试能用的头文件） |
| 转发 | 转手交给当前选中的实现 |
| 测试接缝 / 测试替身 | 测试专用接口 / 假实现 |
| 机械约束 / 机械检查 / 开闸 / 判红 | 脚本自动检查 / 打开严格模式 / 报错 |
| 签注 | 加前缀标记 |
| 冒烟 | 起机跑一遍看功能 |
| 负缓存焊死 | 记住失败结果、以后不再重试 |
| 收敛 / 收口 | 统一 / 收尾 |
| 基线 | 改动前的对照存档 |
| 治理路径 | 以后怎么改的计划 |

源码里引用位置**用函数名和符号名，不用行号**——行号一改文件就漂了（本版评审已发现旧文档的行号全部对不上）。
