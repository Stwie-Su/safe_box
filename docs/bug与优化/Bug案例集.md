### 0.2 讲法四条

1. **讲路径不讲答案**。面试官考的是「现象量化 → 假设 → 验证手段 → 证据 → 结论修正」。每个案例的"排查"一节就是脚本。
2. **主动讲被推翻的假设**（案例 1 的解析层假设、案例 6 的"再加一层反转"、案例 8 的"包坏了"）。修正过程的可信度远高于"一眼看穿"。
3. **判据数字化**：489 行重发、10.04MB 放大、914ms、0 字节、404、130px。全程有仪表是嵌入式基本功。
4. **落到防回归**：部署四查铁律、IPC 解析进 ctest、把约定写进注释钉死语义——从"修好一个 bug"上升到"这类 bug 不再发生"。

## 一、定位方法论：断言链二分 + 分层地图

> **定位原则只有一句**：不要在"可能的原因"里挑一个改，要在"可判定的断言"上切一刀。
> 每一次观察都应把嫌疑空间砍掉一半，而不是把希望押在最像的那个原因上。

### 1.1 二分模板：断言链

对每个怀疑层写一条 **yes/no 可判定**的断言，从上到下逐条验证。**第一条失败的断言就是分界点**，下层的东西在它修好之前都不必看。

| 层 | 断言（可判定） | 探针 |
|---|---|---|
| 物理/链路 | 对端 IP 能 ping 通？ | `ping -c 2 <ip>` |
| 传输 | TCP 能握手？ | 板端 `python3 nettest.py <ip> <port>` / `nc` |
| 加密 | TLS 能握手？ | `nettest.py <ip> <port> tls`；看日志「握手完成」行 |
| 应用协议 | 有 CONNACK / 回执？ | broker 日志、应用日志 `connected (connack=0)` |
| 业务 | 请求-响应能关联？ | 下发带 `req_id`，看回执是否同 id |
| 呈现 | UI 显示与实际状态一致？ | 截图 / 几何打印 |

**关键**：断言要能**单独**判定。"MQTT 连不上"不是断言，"ping 通但 TCP refused"才是——它把问题从应用协议切到了防火墙/端口。

### 1.2 本项目的分层地图（自外向内）

```
呈现层   UI（LVGL）          ← 截图 / 几何打印 lv_obj 的 y/h/w
业务层   core（auth/store/rpc/mqtt）
抽象层   hal（camera/net/time/storage/face）
系统层   OS / 驱动 / 网络     ← ping / TCP / TLS / 防火墙 / 端口转发
对端     broker / OTA 服务器  ← 对端日志（必须先拿到对端视角）
中间     转发器 / 热点 / 网桥  ← 一等公民，不是"背景"
```

**跨机问题必须同时拿两端日志**：只看一端会得到"对方关的"这种互相甩锅的结论（案例 9：板端"读 EOF" vs broker"Client closed"，真凶是中间转发器）。

### 1.3 三条铁律（本项目踩出来的）

1. **先取证，再动手**。改两次没效果就停手，插桩量数据（几何 / 计数 / errno）。案例 10 就是靠 `printf` 出 `child2 h=130` 一次锁定的——之前猜了三轮。
2. **一次只改一处并验证**。同时改两处会让"哪个起效了"变成新的谜题。
3. **跨进程约定必须纯函数化进 ctest**。脚本写状态 / UI 读状态这种 IPC，手动 `cat` 看全量会掩盖"读方解析逻辑"的错误（案例 7）。

### 1.4 反模式清单

| 反模式 | 为什么错 | 替代 |
|---|---|---|
| "大概是 X，先改了试试" | 猜错成本高于插桩成本 | 先写一条能证伪 X 的断言 |
| 只查一端日志 | 会得到互相甩锅的结论 | 两端日志 + 中间链路（抓包 / 转发器日志） |
| 手动 cat 全量验证解析 | 掩盖读方逻辑错误 | 用读方同样的解析路径跑一遍（进 ctest） |
| 看瞬时值下结论 | 忙循环/重连风暴在瞬时值是"好转"的 | 取**稳态**（≥60s 计数差） |
| 改完不跑 ctest | 回归在别处炸开 | ctest 全绿才算完（本项目两次靠它抓回归） |
| PC 通过就认为板端通过 | 2x 缩放会掩盖绝对像素类 bug（案例 10） | 上板后重验布局 / 性能 |
| 把"我加了修复但没变"当成运气 | 它说明变换链上有抵消 | 列出链路上全部变换点逐个打点（案例 6） |

## 二、案例

### 案例 1：串口重发风暴——一次无符号下溢，让"超时重传"从未生效

**背景**：FM225 人脸模组走串口协议，`VERIFY` 命令 800ms 无应答就重发。某次联调日志被刷屏：40 秒 671 行日志里 489 行是重发。

**现象**：日志里明明有 `verify 应答` 的解析记录——应答到了，重发却停不下来。这两件事放一起是矛盾的：要么应答解析是假的，要么超时判定是假的。

**排查**：我先怀疑应答没送达解析层，加日志跟了一遍串口读路径，应答确实被解析了（假设被推翻）。于是反过来读超时判定的代码：

```c
if (now_ms - last_send_ms > 800) resend();   // 伪代码
```

`now_ms` 由 `app.c` 主循环传入，来源是 `s_tick_ms += 20`（进程内计数，从 0 起步）；`last_send_ms` 由串口后端记录，来源是 `hal_time_ms()`（`CLOCK_MONOTONIC`，开机后已是百万级毫秒）。两者相减，无符号下溢，差值瞬间变成 ≈4×10⁹ 的巨值，`> 800` 恒成立——**每一次 tick 都判定超时，重发、重置基准、再判超时，死循环**。注释里写的"800ms 超时 + 退避"从未生效过一天。

**根因**：接口约定缺失。`tick(now_ms)` 的参数只写了"毫秒"，没约定纪元（进程计数 vs 系统单调钟）。两个模块各自用了"自己以为的"时间源。

**修复**：`app.c` 改传 `hal_time_ms()`，并在头文件注释里钉死语义。动手前先 grep 了全部 4 处 `now_ms` 使用方，确认都是差值语义（差值对纪元不敏感），改动零风险。我还主动否决了"再加一层指数退避"的提议——这里是空转轮询，指数退避只会推迟恢复检测，是负优化。

**反思**：跨模块传"时间"必须约定纪元与单位；判据要能从常量推算——"应答场景重发次数 = 0"就是硬指标，达不到就是没修好。

**考点**：C 无符号运算下溢 / `CLOCK_MONOTONIC` 语义 / 串口协议超时重传设计 / 改动前先审计使用方。

### 案例 2：FM225 协议逆向三部曲——"成功"响应里藏着三个假成功

**背景**：人脸录入联调，三种症状先后出现：录入秒成功但模组里没有用户；录入永远超时；还没转头就提示成功。

**第一部（命令码用错）**：录入总是超时，偶尔"成功"但模组清单是空的。日志里 `enroll 应答 uid=65535` 是决定性证据。我拿桌面 FM225 测试工具当参考实现，逐字节对比命令表，发现我用的 `0x13` 是**五向录入**（应答是进度回调），单帧场景该用 `0x1D ENROLL_SINGLE`（应答即最终结果）。命令码本身合法、协议校验全过——**合法但语义错**，所以静默出错。

**第二部（伪成功应答）**：改成 `0x1D` 后，app 显示录入成功、`err=0 mr=0x00`，但模组用户清单 0 个、uid 仍是 65535。翻手册：`0xFFFF` 是"未分配占位值"——模组回了成功、实际没分配用户，app 照单全收，写下一条指向不存在用户的假绑定。修复是源头拒收（`uid<=0 || ==0xFFFF` 判失败）+ 读盘归一化清存量。

**第三部（掩码语义误用）**：五向录入"还没转头就成功"，914ms 完成——物理上不可能。整个会话只有 1 条方向 NOTE，证明模组根本没采五次。根因：我给模组传了 `0x1F`（全方向掩码），但 `0x1F` 的语义是"**已累计完成**五个方向"（状态值），不是"请采五个方向"（请求值）。模组一看"都完成了"，直接判成功。改成逐方向分 5 次下发（正 0x01 → 右 0x02 → 左 0x04 → 下 0x08 → 上 0x10），app 按累计掩码续发。

**排查方法论**（三部曲共用的招）：
- **三源对账**：app 日志 / 模组用户清单 / users.json 三方摆一起，"app 说成功、模组说没有"，必有一假；
- **硬指标**：914ms、1 条 NOTE、uid=65535——物理证据比语义推理硬；
- **对照参考实现**：桌面测试工具是"能跑通的实现"，比读手册猜语义可靠。

**反思**：跟外部黑盒子打交道，"成功"两个字不可信，字段级语义要逐个核对；固件 bug 往往长得像"功能正常"。

**考点**：嵌入式外部协议对接 / 状态机语义（请求 vs 累计）/ 三源对账取证。

### 案例 3：日志滚动写放大——strace 量出来的 O(cap) 隐患

**背景**：审计日志要求掉电安全、限额滚动。code review 时我怀疑认证路径上有同步落盘和全文件重写，会磨损 flash、拖慢开锁。

**排查**：不猜，直接 strace 跟系统调用，量化取证：
- 未饱和时追加 200 条日志：rename 0 次，纯追加，我的怀疑"每条都重写"不成立；
- **饱和后**追加 158 条：触发 rename 全量重写 **259 次**、写入 10.04MB——理论应然 12KB，放大 800 倍。

顺藤摸瓜读代码：行数计数是运行时 `fopen+fgetc` 全文件数行（每条日志 O(cap) 读一遍）；饱和后每条都触发"全量重写"。

**一个好消息藏在坏消息里**：strace 显示 rename 收尾路径**没有 fsync**——认证路径实际是零同步落盘的，掉电安全不受影响；重写只在饱和后发生。这决定了修复优先级是性能而非安全。

**修复**：①行数改内存维护（init 扫一次 + 增量），消除 O(file) 读；②滚动加迟滞（`lines > cap + SLACK` 才触发），单次重写摊还到 O(1)/次。

**反思**：先量后猜——strace 十分钟把"我怀疑"变成"我知道"；改容量参数前先算放大倍数（cap 从 500 调 5000，单次重写 38KB→385KB，洪峰 6MB→60MB，不做迟滞就是把地雷调大）。

**考点**：文件 IO 原子性 / strace 性能取证 / 摊还分析 / flash 寿命意识。

### 案例 4：ch341.ko 内核外编——跟工具链和内核版本同时斗智

**背景**：板载内核 4.9.88 没编 CH341 串口驱动（FM225 经 CH340 USB 转串接入），rootfs 里也没有现成 ko。要在 VM 上用内核源码外编一个 `ch341.ko`。

**坑一（MODVERSIONS）**：第一次编出来 insmod 报 `Invalid module format`。`modinfo` 看 vermagic 一致，卡了一阵才想到 CRC：内核开了 `CONFIG_MODVERSIONS=y`，符号 CRC 必须和目标内核的 `Module.symvers` 对齐，而我的源码树没有板子内核的 symvers。解法是拉板子的 `/proc/config.gz` 做**全量精确配置**重编内核生成匹配的 `Module.symvers`，再编模块——一次过。

**坑二（dtc 编不过）**：`scripts/dtc` 报 `yylloc` 重复定义。这是 4.9 内核遇上新 GCC 的 `-fno-common`（旧内核多个 .c 里 yylloc 是"侥幸通过"的公共符号，新编译器不再合并重复定义）。修法：sed 改成 `extern YYLTYPE yylloc` 声明 + HOSTCFLAGS 加 `-fcommon` + 删掉陈旧的 dtc 对象重编。

**验证**：insmod 后 `/dev/ttyUSB0` 出现，FM225 自检 `RESET→REPLY result=0x00`，模组清单 2 模板 201 字节应答——链路通。

**反思**：内核模块版本兼容是三层：vermagic（内核版本串）、CRC（MODVERSIONS）、配置（`.config` 必须来自目标机的 `/proc/config.gz`，不能"差不多配一个"）。

**考点**：内核模块构建体系（Kbuild / Module.symvers）/ GCC `-fno-common` 与老代码兼容 / `Invalid module format` 的分层排查。

### 案例 5：相机 0 帧——快速恢复路径在非标 UVC 上是无效路径

**背景**：FM225 的 UVC 相机（`ffff:ffff`，非标）只出 MJPG。预览链路调好后出现两个时序问题。

**问题一（离开页面回来 0 帧）**：为提速我做了"快速恢复"（STREAMOFF 后直接把旧 buffer QBUF 重新挂上，省去格式协商）。真机上这条路返回 EINVAL——**非标 UVC 不接受这种非标准的恢复顺序**。修法不是继续猜它接受什么，而是把"快速恢复失败"接回"完整重开"路径：QBUF 一失败就自动退回 STREAMOFF→重新 MMAP→STREAMON 全流程，errno 记日志。**优雅降级，比赌硬件行为可靠**。

**问题二（开机扑空）**：开机进人脸页没画面。日志显示应用启动（S05lvgl）早于 USB 相机枚举（dmesg 里相机 7.43s 才就绪）——**init 时序竞争**，不是相机代码的问题。在内核层修（改启动顺序）侵入太大；在应用层加**竞态重试**：人脸页打开时若相机未就绪自动重扫，最多 3 次——覆盖 USB 枚举窗口，代码零侵入。

**反思**：嵌入式的外设不总遵守标准；"更快"的路径必须给"更慢但确定"的路径当备胎。开机竞态类问题先画时间线（init 脚本顺序 vs 内核事件时间戳），再决定在哪一层修。

**考点**：V4L2 buffer 管理（QBUF / STREAMOFF 语义）/ USB 枚举时序 / 优雅降级设计 / 按层选修复点。

### 案例 6：触摸点不准——双重镜像相互抵消的"恒等假象"

**背景**：屏幕要 180° 旋转（面板物理倒装）。设置 `lv_display_set_rotation(180)` 后画面正了，但触摸"点哪错哪"，错得很有规律——点左上响应在右下，**正好镜像**。

**排查**：我的第一反应：旋转了画面但没旋转输入坐标。于是到 evdev 触摸后端加了坐标反转（`x' = max - x, y' = max - y`）。改完更奇怪了——**触摸完全正确了，但和加这段代码之前的表现一模一样**。也就是说：这段代码改不改，行为相同。代码没有起作用，或者起了两次作用。

读 LVGL v9 的 indev 核心：`lv_indev` 在把坐标送给控件前，会**根据 display 的 rotation 自动做同样的旋转变换**。我加的手动反转，恰好和核心的自动变换**相互抵消，等于恒等**。而"没加之前点哪错哪"是因为——那时我同时开了标定反转（TOUCH_CAL 里反向），两个变换叠加又构成另一个错误组合。打开 CALIB_DEBUG 全链路打点，把 raw → 标定 → indev 核心每一层变换后的坐标打出来，对齐之后才看清：**整条链上有几处在转、各转了多少，一目了然**。

**修复**：删掉 evdev 里的手动反转，标定恒等（raw 坐标本身就是面板像素坐标 0..1023 / 0..599），只留 `lv_display_set_rotation(180)` 一处变换。

**反思**：变换类 bug 最怕"看起来对了"——两个 bug 相互抵消时，现象会精确掩盖根因。对这类问题要**列出链路上所有变换点**逐个打点，而不是在某一层试错。"我加的修复没有改变行为"本身就是重要线索。

**考点**：输入坐标变换链 / 显示旋转与触摸映射的关系 / "无效修复"的诊断价值 / 用日志链对齐替代试错。

### 案例 7：OTA"检查中…"卡死——跨进程 IPC 的读方解析没人验收

**背景**：OTA 分两侧：shell 脚本管流程（wget / sha256 / tar），UI 轮询状态文件渲染进度。板端点"检查更新"后永远停在"检查中…"。

**排查**：先手动 `cat /var/ota/status`——里面明明有 `STATE=CHECKED`！文件是对的、UI 是错的。但为什么我在 PC 上怎么测都过？因为我手动验证时用的是 `cat` / `grep`——**全量查看**，而我 UI 里写的是"取第一个匹配"。脚本写状态是**追加式**：每次阶段推进 `echo "STATE=xxx" >> 文件`，于是 `CHECKING` 永远是第一行，UI 取首个匹配永远拿到旧的 CHECKING。**我验收读方的方式，和读方真正的行为不一致**——手动 cat 掩盖了根因。

**修复三件套**：
1. 解析逻辑抽成纯函数 `ota_status_query()`：取**最后**一条匹配、容忍 CRLF——单独建 `test_ota_status`，9 组用例进 ctest；
2. 脚本改**重写式**（`: > file` 先清空再写）；
3. UI 加 30s 超时兜底，防任何未预见的状态滞留。

**反思**：这次修完后我把一条纪律写进了规约：**跨进程 IPC 的解析必须按读方的真实语义写成纯函数并进 ctest**。验收协议时必须模拟读方行为，不能拿人肉 cat 代替。后续又踩了同族问题：脚本在板端 BusyBox 上 `tar -z` 不存在（`invalid option -- z`）——**两端工具能力要对齐为最小集**；包格式改纯 tar 后，自研 HTTP 服务器的白名单还匹配 `.tar.gz`，对新包一律 404（见案例 8）。

**考点**：跨进程约定设计 / 测试与真实读方的等价性 / 增量协议 vs 全量协议 / BusyBox 能力裁剪。

### 案例 8：ERR_SHA 伪装的下载失败——离根因最远的一次排查

**背景**：OTA 服务器发布 1.0.3 后，板端升级失败，状态停在 `STATE=ERR_SHA`——sha256 校验不通过。

**排查链**（这次每一步都被上一步推翻）：
1. **第一反应：包坏了。** 服务器上 `sha256sum safe_ota_1.0.3.tar` 和 manifest 完全一致——包没坏；
2. **第二反应：传输截断。** 板上手动前台 wget 全量下载——`exit=8`（服务器错误响应）、**0 字节**。不是截断，是根本没下下来；
3. **缩小范围：哪一段拒绝的？** VM 本机 `curl 127.0.0.1:8080/safe_ota_1.0.3.tar` → **404**！服务器进程活着（manifest.json 返回 200）、文件就在工作目录里，却 404；
4. **读源码**：自研 `mini_ota_http.c` 的 GET 白名单写着 `strstr(name, ".tar.gz")`——**只放行 .tar.gz**。而前几轮为了适配板端 BusyBox（无 -z），包格式改成了纯 `.tar`。改包格式时改了打包脚本、改了板端解压，唯独漏了服务器白名单；
5. **为什么表现成 ERR_SHA 而不是下载失败？** 板端 apply 脚本的逻辑：wget 失败 → 自动回退"预推送兜底包"（`/var/ota/ota_pkg_local`，还是 1.0.2 旧包）→ 用 manifest 里 1.0.3 的 sha 去校验 1.0.2 的旧包 → 必然不匹配 → ERR_SHA。**下载失败被兜底机制伪装成了校验失败**。

**修复**：白名单 `.tar.gz` → `.tar`（前缀匹配同时涵盖两种）；重建重启后 tar 返回 200 全量，板端 OTA 走 HTTP 直连通道一次性升到 1.0.3。

**反思**：错误码会撒谎——离根因最远的表象往往来自**多个机制的串联**（404 → 兜底回退 → 校验必然失败）。排查这种问题要分段归责：先证明"服务器上文件正确"，再证明"服务器愿意发"，再证明"传输完整"，最后才是"校验逻辑对"。另外，**改一个约定（包格式）必须全链路排查一遍它的消费方**：打包、分发、白名单、解压、校验——只改一端就是埋雷。

**考点**：分段归责排查法 / HTTP 状态码语义 / 兜底机制的"伪装效应" / 约定变更的全链路影响分析。

### 案例 9：MQTT 每 30 秒断一次——真凶在"实验用的转发器"里

**背景**：板端通过 PC 端口转发连到 VM 上的 mosquitto（8883 双向 TLS）。现象是每 30 秒断链重连一次，断得很规整。

**现象**：板端日志只有一句 `读 EOF（对端关闭）`，FSM 的 ping / suback 超时计数**全是 0**——说明不是超时路径。broker 日志则写着 `Client safe-xxx closed its connection`，看起来像"客户端自己关的"。**两端日志互相甩锅**，这就是典型的中间链路故障特征。

**排查**（逐层断言，每层一个 yes/no）：
1. `ping 10.218.148.51` → 通（链路 OK）
2. TCP 8883 → `Connection refused`（不是超时！说明有主机响应但端口没开）
3. 从 VM 连 Windows 的 8883 → 也 refused，但连 `127.0.0.1:8883` → **OK**

第 3 步是分界点：同一台机器上环回通、外部地址拒 → **防火墙按接口拦截**。而"工具本身的 bug"这一假设，是在看到 `socket.create_connection(timeout=30)` 的 timeout 被继承成 socket 超时后才成立的。

**根因**：临时转发器用 `create_connection(TARGET, timeout=30)` 建连，这个 timeout 会被继承为**已连接 socket 的超时**，于是 30 秒后 `recv` 抛 `TimeoutError`，转发器关掉两侧——板端看到 EOF，broker 看到客户端关闭。**两端日志都"正确"，但都指向错误的方向。**

**修复**：建连后 `up.settimeout(None)`（长连接回到阻塞）。

**反思**：跨机问题，中间链路（转发器 / 防火墙 / 热点）是**一等公民**，必须能自证：转发器自己要打日志，否则它的故障会被归咎到两端之一。

**考点**：分层断言（ping → TCP → TLS）/ socket timeout 的继承语义 / 中间链路取证 / 防火墙按接口拦截的判别（环回通 + 外部拒）。

### 案例 10：板端布局大面积塌陷——PC 通过，板端崩

**背景**：用户页在 PC 模拟器上一切正常，板端却"表头与列表之间一大片空白、普通用户组看不到"。

**排查**：
1. PC 用截图专用入口截同页 → 正常 → **排除拆分代码**（新旧 `page_users_create` 逐行 diff 完全一致）；

**考点**：图形栈取证（几何插桩）/ 平台差异意识 / 交叉验证（PC vs 板端）/ flex 主轴与交叉轴。

### 案例 13：IP 漂移——环境变化比代码更容易"背锅"

**背景**：MQTT 断线反复出现，用户第一反应是"上次配的防火墙规则重启后失效了"。

**结论**：`netsh interface portproxy` 与 `netsh advfirewall` 规则**都是持久配置，重启不丢**。真正变化的是 **Windows WLAN 的 DHCP 地址**（10.218.148.51 → 10.163.32.202 → 10.163.32.51），而板端连接字符串写死了 IP。

**反思**：把会变的地址写成常量，就是把环境变化伪装成代码缺陷。凡跨机依赖，设备侧都要能自愈。同理，证书 SAN 与"板端连接字符串"是同一份约定，网段变化必须同时改两处。

### 案例 14：动态码连点两次，码被吃掉门没开——世代号撤不了已发生的副作用

**背景**：认证路径下沉 worker 后（主线程零同步落盘改造），做了两处异步化：动态码校验、PIN 校验。改造本身达成目标，但引入两条**静默回归**——不报编译错、不影响主流程，功能自测全过。

**回归一（漏迁日志，D30）**：凭据失效路径原本在主线程会落**两条**日志，下沉时只迁了状态改写那一条，第二条「已标记失效」审计日志漏了。表现：功能正常、`safe.log` 少一条审计。**这类回归只能靠"审计可追溯"这条需求兜**——它不是 bug，是需求没满足。

**回归二（码被吃掉，D31）**：连点两次动态码 → 第一次作业跑完 `auth_verify_totp` 并写回 `last_otp_counter`（码被消耗），但结果因世代号过期被丢弃 → 不开锁；第二次作业判 `AUTH_REPLAY`（防重放）→ 也不开锁。**码没了，门没开。**

**根因**：世代号（generation）的语义被我理解错了——它**只能丢弃"结果"，撤销不了 worker 已经执行的副作用**。防重放计数器是不可逆写，一旦worker 跑过就生效了，主线程丢不丢结果无所谓。

**修复**：带不可逆副作用的通道改**单飞**（在途期间不再受理新请求）；并且把在途标志的复位**统一收进 `set_state`**（离开 WAIT_OTP 即复位），而不是散在每条离开路径——漏一条就永久卡死。

**反思（两条）**：
1. **凡下沉到 worker 的分支，回头核一遍原分支落了几条日志**。状态改写迁走、日志漏掉，是最典型的异步化回归；
2. **世代号不是万能的**。凡作业带不可逆副作用（写防重放计数器、消耗一次性凭据、硬件动作）的通道都要单飞。

**考点**：异步化改造的代价 / generation 计数的语义边界 / 幂等与单飞 / 复位逻辑收敛到唯一出口。

### 案例 15：门禁看不见的同步落盘——扫描范围被"想当然"缩小了

**背景**：项目有一道 ctest 门禁 `check_main_thread_store.sh`：扫 UI 层是否直连 store 读写接口（UI 主线程同步落盘会卡住界面、磨损 flash）。改管理员密码的动态码二次确认这条路径一直"合规"。

**现象**：静态复查时发现 `page_users_dlg` 直调 `auth_admin_verify_totp()`，而这个函数内部**全表读盘 + 整表写盘**——标准的同步落盘，但门禁的正则只匹配 store 接口名，看不见 `backend_*`。

**根因**：**门禁的扫描范围会被"想当然"缩小**。当初写门禁时认为"backend_ 是后台用的封装"，就把它排除在扫描外；结果它正是主线程同步落盘的藏身处。

**反思**：自动化门禁的价值不在"它能拦什么"，而在"它拦不到什么"要被显式承认。每加一条规则就问一句：有没有一类调用是我默认排除的？

**考点**：架构约束的机械化（门禁进 ctest）/ 间接调用 vs 正则扫描 / 用"另一条规则"覆盖漏网路径。

### 案例 16：预览一片空白——复制的预览管线漏了一个初值

**背景**：人脸录入页预览全白，识别页正常。

**排查**：两页共用一套"预览管线"（缩放 + 旋转 + 映射表），录入页是复制过去的。打印映射表尺寸 → **1×1**。往上追：`scale` 算出来是 0，被 `if(scale < 1) scale = 1` 夹成 1，于是画布 1×1。再往上：`s_scale_max` 是 0——**漏了初值**，放大上限判据恒假，`scale` 归零。

**反思**：**复制代码必漏初始化；设备固定的几何常量必须单源**，不能散在启动器 env 和各页里。

**考点**：复制粘贴型缺陷 / 常量的单一来源 / 设备固有属性不进环境变量。

### 案例 17：屏幕全黑、串口零输出——RTC 电池把上电时序打崩了

**背景**：板子接上 RTC 后备电池（供 CPU 的 SNVS 常电域）后出现**间歇性无法开机**——插上 12V 后屏幕全黑、背光灭，串口有时一个字符都没有。拔掉电池则一切正常。而 RTC 时间保持是好的，这个"电池没问题"的假象把排查带偏了很久。

**排查**：

2. **软件侧证明芯片没坏**：`hwclock -w` 写入成功、`hwclock -r` 读回正确、`snvs-powerkey` 中断在册 → 排除"插反把芯片烧了"的焦虑
3. **查 NXP 官方规格**：`VDD_SNVS_IN` 工作范围 **min 2.40 / typ 3.0 / max 3.60 V**——实测电池 3.5V **合规**，于是**撤回我自己"3.5V 破坏上电时序"的误判**；但在同一页顺手捡到两条关键条文：*"VDD_SNVS_IN 必须先于其它电源上电"*、*"必须确保没有任何电源向 3.3V 域 back-voltage"*
4. **串口连续记录（转折点）**：写 pyserial 脚本后台跑，每行打毫秒时间戳，覆盖用户的多次上下电。抓到 5 次上电，其中一次是——

```
23:03:36.9  U-Boot #1  Reset cause: POR   ← 按 POWER 键触发开机
23:03:41.0  Starting kernel...
23:03:42.5  U-Boot #2  Reset cause: POR   ← 内核刚起 1.5 秒，整板掉电
23:03:44.3  U-Boot #3  Reset cause: POR   ← 又崩，1.7 秒后再次上电
23:03:48.5  Starting kernel...            ← 第三次才稳住
23:04:19.3  100ask login                  ✅
```

**1.5 秒间隔的三连复位，肉眼永远抓不到。**

5. **用户 A/B 对比定案**：不插电池多次断电重启全部正常，插电池则间歇失败 → 变量锁定在电池

**关键判据（黑屏必须分两型）**：

| 型 | 串口表现 | 真实状态 |
|---|---|---|
| Ⅰ 真死 | **零输出**，连 U-Boot 一个字符都没有（实测静默 13 分 57 秒） | CPU 未执行，崩在 SPL 之前 |
| Ⅱ 假死 | 全程正常输出（U-Boot → 内核 → `Starting 100ask lvgl: OK` → 网络就绪） | 系统活得好好的，是我等待不足（正常启动需 30~36 秒，当时只等 23 秒）误判 |

`Reset cause: POR`（而非 WDOG）是分水岭：**POR = 硬件掉电复位**，一刀切开"电源崩了"与"软件死机"。

**根因**：插 12V 后主电源逐级建立（12V → 5V → 3.3V），存在几 ms~几十 ms 的窗口，此时主域 3.3V 尚未建立，而电池 3.0V 已加在 SNVS 上 → 芯片内部 ESD 结构导通，**电池向 3.3V 主域倒灌** → CR1220 内阻（10~33Ω）上的压降把 `VDD_SNVS_IN` 拉低 → 跌破 POR 阈值 → 复位 → 电压回升 → 再启动 → 再倒灌…… 崩得早时连 U-Boot 第一行都打不出来。这正是 NXP 明文禁止的 back-voltage；官方 EVK 在此处用 BAT54C **二极管或门**（3.3V 与电池各经一只二极管汇入）隔离，这块板把它省了。

**修复**：

- 硬件 ①：J18 pin1↔pin2 并焊 **100µF** 电解/钽电容——倒灌窗口由电容供电，容量是 C173（100nF）的 1000 倍（最易实施）
- 硬件 ②：电池包正极线内串**肖特基二极管**（SS14/1N5819）——彻底切断倒灌，等同官方 EVK 做法；代价 SNVS 电压 −0.3V（仍在 2.4~3.6V 规格内）
- 硬件 ③：换新电池降低内阻（治标）
- 操作规范：**先插电池、再插 12V**（符合"SNVS 必须先上电"）；上电后若黑屏，按一下 POWER 键（ONOFF，勿超 4 秒否则变关机请求）再等满 40 秒
- 验证闭环：装回电池断电重启 ×5，串口统计——零 POR 循环即成功

**反思**：

- **电路事实优先于现象**：没翻原理图之前所有猜测都是空中楼阁；看到"直连、无二极管"那一刻，答案其实已经埋好了
- **不可复现的问题，只要能连续记录就变成可复现的**：三连 POR 间隔 1.5 秒，靠人盯永远抓不到——这是本次最值钱的经验
- **`Reset cause` 一行定方向**：POR vs WDOG 直接切开两大嫌疑空间
- **假设必须绑定可证伪的判据**：本次推翻 6 个假设（欠压 / 反接 / 3.5V 破坏时序 / SNVS 状态机不自启 / OTA 看门狗 45s / 背光故障），**其中 3 个是我自己公开撤回的**——修正过程的可信度远高于"一眼看穿"
- **用户 A/B 对比是切割变量的最快路径**，不要抢在用户前面做实验

**考点**：i.MX6 上电时序与 SNVS 常电域 / back-voltage 与 ESD 倒灌 / POR 复位源判别（POR vs WDOG）/ 原理图 + datasheet 取证 / 用连续记录把偶发变可复现 / 硬件设计缺陷的软件侧规避。

### 案例 18：屏幕"花了"却不是渲染 bug——两个前台在抢 fb0

**背景**：换掉开机入口脚本大半天之后，界面突然"花了"：左侧整条导航栏消失、卡片背后多出一条深色带、左上角冒出不属于本应用的红色图标。第一反应是渲染或布局回归——但代码那一晚之后没动过。

**排查**：

1. **先确认有几个进程在写屏幕**（不要先看渲染代码）：
   ```sh
   fuser /dev/fb0            # 185 398      ← 两个 pid
   fuser /dev/input/event1   # 185 398      ← 连触摸都是两个
   readlink /proc/398/exe    # /usr/bin/mxapp2
   ```
   398 是 MYIR 出厂 HMI demo，由 `/etc/init.d/S99myirhmi2` 拉起。
2. **读厂家脚本找互斥条件**：
   ```sh
   LVGL="/etc/init.d/S05lvgl"
   if [ -f "$LVGL" ]; then echo "run lvgl"; break; else /usr/bin/mxapp2 ... ; fi
   ```
   它判断的是**「这个文件存不存在」**。我们把启动入口从 `S05lvgl` 换成了 `S05safe`，文件没了 → 判断翻到 else → demo 被拉起。
3. **为什么不是"一换就出现"**：手工按脚本参数启动 mxapp2，按时间抓帧做像素差分：

   | 时刻（相对 mxapp2 启动） | 与干净基线的差异像素 | 说明 |
   |---|---|---|
   | t = 2s | 224（0.04%） | 只有我们自己的时钟在跳 |
   | t = 8s | **121 817（19.83%）** | mxapp2 首帧上屏，就是这幅"花"的样子 |
   | t = 20s | 121 995（19.86%） | 不再变化 ⇒ **它画完不会自己重画** |

4. **反向验证"谁最后画谁赢"**：让 mxapp2 继续跑着，只把我们的应用重启一次（等于一次整屏重绘），再抓帧——
   与干净基线的差异只剩 **624 像素（0.1%，就是时钟数字）**。说明 mxapp2 的像素被完整覆盖，而且它**不会自动重绘回来**。

**根因（两层）**：

1. **用「文件名存在与否」当互斥开关**：等于把互斥绑在别人的命名上。改名即失效，而且失效方向是"多启动一个"——没有报错、没有回滚、没有任何日志。
2. **fbdev 没有独占语义**：第二个进程可以照常 `open` 并绘制，两个写者各画各的，内核不报错、应用也不报错。

**为什么以前没出现**——这个问题要拆成两问，只有第一问有确定答案：

1. **换入口之前为什么没有？** 有确定答案：`[ -f /etc/init.d/S05lvgl ]` 为真，
   脚本走 `echo "run lvgl"` 分支，出厂 demo **从来没被启动过**。
   不是"启动了但没影响"，是根本没跑。
2. **换入口之后为什么过了一阵才看见？** **没有定论，不编。**
   当晚 00:17 的截图是干净的，而按脚本逻辑那时 demo 已经在跑了。试过两个解释，都被自己的实验否掉：

   | 假设 | 验证方式 | 结果 |
   |---|---|---|
   | `psplash-write` 在无读者时阻塞 → 脚本卡在第一行，demo 根本没起 | 无 psplash 时执行 `timeout 3 psplash-write "PROGRESS 75"` | **排除**：立即返回 rc=255，不阻塞 |
   | 遗留脚本 `S05lvgl.bak_*` 起的第二个应用，它的整屏重绘把 demo 盖掉了 | 按 rcS 执行顺序：S99 在最后，demo 的首绘远晚于应用首次重绘 | **不成立**：时间对不上 |

   所以「为什么晚了两小时」留作未解。能确定的是：**只要 demo 起来并画过，画面就会一直是花的**——
   实测它画完不会自己重画，也没有别的进程会盖它。

   ★ 这一段本身就是纪律：一开始我用"被另一个 bug 掩盖"讲得很顺，但一算时间就露馅了。
   **不要把"听起来合理的因果"写成结论**，尤其当它没法被现有证据支持时。

**修复（三层）**：

- `S99myirhmi2` 移出 `/etc/init.d`（到 `/root/rollback_20261020/`）——**不能只改名**，`rcS` 遍历 `S??*` 会把 `.bak` 也捡回来（D49 同源）；
- `psplash` 的 `QUIT` 原本由那个脚本发，改由 `safe_boot.sh` 自己发，否则开机画面会一直占着 fb0；
- 应用启动时扫 `/proc/<pid>/fd`，把结果打进日志：
  `fbdev: /dev/fb0 只有本进程在写` / `fbdev: 警告：另一个进程也在写 …，画面会互相覆盖`。

**验证**：重启后 `fuser /dev/fb0` 与 `/dev/input/event1` 都只剩本进程，导航栏完整，日志报"只有本进程在写"。

**反思**：

- **「以前没问题」不等于「以前没有这个 bug」**：可能只是被另一个现象掩盖了。判断"这次为什么变"之前，先确认"以前到底是什么状态"，而不是"以前看起来是好的"。
- **修掉一个 bug 会让另一个 bug 现形**，这是正常工程现象。修完 A 之后要重新跑一遍曾经"通过"的验收项，而不是假设它们仍然通过。
- **杀掉写者不清屏**：fb 里是它留下的像素，要等本进程重绘到那块区域才被覆盖。我先 `killall mxapp2` 再截图，画面依旧花——差点误判成"没修好"。
- **延迟上屏会让故障看起来是"随机/突然"出现的**：demo 首绘延迟约 8 秒，加上可能几小时才被触发一次，直觉会把它归成"偶发渲染问题"。
- **把"看起来花"变成数字**：像素差分（224 → 121 817 → 624）比"我看着不对"有力得多，也让时间线可以定量复现。

**考点**：Linux framebuffer 多写者语义 / BusyBox init 脚本执行顺序与 `S??*` 通配 / 用 `/proc/<pid>/fd` 做资源归属取证 / 时序竞态（谁最后画谁赢）/ 用像素差分把显示问题量化 / "一个缺陷掩盖另一个缺陷"的排查心态。

## 四、附录 B：未入选缺陷索引（一句话，素材不丢）

- 日志"最后开启"恒为 `--`：写入侧大写 / 查询侧小写，且单测两侧同错假通过——**期望值必须独立于实现**；
- 远程注入传 -1 回假成功：无符号枚举吞掉负哨兵——**API 边界先做有符号校验**；
- `SAFE_LOG_MAX` 不生效：配置双默认值 + 注释假出处——env → config → consumer 要全链路闭环；
- A/B 跑在已删除旧二进制上：`/proc/pid/exe` 出现 `(deleted)`——固化为**部署四查铁律**（PID 变 / exe 非 deleted / 日志有新打印 / 字节数核对）；
- 幂等对账的死角：启动对账只跑一次，管不到运行期新产生的假绑定——一次性机制不能当唯一兜底；
- 版本号 bump 三次 sed 不匹配：CMakeLists 的 `project()` 是多行形式，单行 sed 永不命中——改构建文件先看它的真实排版；
- MQTT 重连后不再 SUBSCRIBE：`pending_subscribe` 只在首连置位——`clean_session=1` 下每次建连都要重订阅（已在 fsm 修复并注释）；
- 主页统计 worker 写 / UI 读竞态：静态 `s_stats` 双方直读直写——改为每次 job 独立堆缓冲、done 时主线程拷回（跨线程共享要么不可变要么拷贝）。

## 五、附录 C：方法论十诫（每条都对应上面的真实案例）

1. 先拿证据再下结论（`uid=65535` 是铁证，不是"可能有 bug"）；
2. 三源对账——两个来源一致不算数，三个才敢下结论；
3. 物理硬指标 > 语义推理（914ms 不可能完成五向采集）；
4. "我的修复没改变行为"是重要线索，不是运气（案例 6）；
5. 分段归责，每段独立证明（案例 8 的四段链）；
6. 顺着数据流逐层走，每层排除一个嫌疑；
7. 量化先于猜测：strace / wc -c / 几何插桩 / 单调钟打点；
8. 跨进程约定要模拟读方验收，进 ctest（案例 7）；
9. 改约定必须全链路过一遍消费方（案例 8）；
10. 一次只改一件事，验证后再改下一件。
