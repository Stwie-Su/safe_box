# 隐匿 Bug 与调试方法（2026-09-20~21 实录）

> 配套：`Debug案例集_2026-09-14.md`（前期案例）。本篇收录 2026-09-20~21 两天的 9 个隐匿 Bug。
>
> **为什么单独立一篇**：这批 Bug 的共同点是——**编译器不报错、测试全绿、界面"看起来在工作"**。
> 全部依靠用户实测反馈 + 证据链才揪出来。记录两件事：每个 Bug 的「隐匿点」在哪；
> 作为工程师当时是怎么调试的（可复用的动作，不是运气）。

## 一、Bug 清单（9 例）

### Bug-1 单帧录入用错命令码（0x13 vs 0x1D）
- **现象**：录入"总是失败/超时"；偶发"成功"但模组里没有用户。
- **隐匿点**：命令码 `0x13` **合法存在**（它是五向录入），只是**语义用错了**——单帧场景发了五向命令。编译、协议校验、重发机制全部正常。
- **怎么发现**：用户实测反馈 + 决定性日志 `enroll 应答 uid=65535`。
- **调试动作**：拿**桌面 FM225 测试工具**当参考实现，逐字节对比它的命令表与应答解析——`0x1D ENROLL_SINGLE`（单脸，应答即结果）与 `0x13 ENROLL_5`（五向，应答是进度）语义完全不同。
- **修复**：命令码与 `face_dir` 都按模式选；配套 Bug-2 的 uid 校验。

### Bug-2 uid=0xFFFF 伪成功
- **现象**：app 显示录入成功，模组清单 0 个；界面挂"删人脸"却删不掉（模组回容量异常）。
- **隐匿点**：模组回 `mr=SUCCESS` 但 uid 是**未分配占位值 0xFFFF**——"成功"里藏着假成功。app 照单全收，写下指向不存在用户的假绑定。
- **怎么发现**：`enroll 应答：err=0 mr=0x00 uid=65535` + `模组用户清单：0 个` 两行日志并排看。
- **调试动作**：**三源对账**——app 日志、模组清单、users.json 三方摆一起，假的那边立刻现形。
- **修复**：源头拒收（`uid<=0 || ==0xFFFF` 判失败）+ 存量清理（读盘归一化）。

### Bug-3 face_dir=0x1F 被模组当成"已完成"
- **现象**："还没转头就录成功了"（914ms 完成）。
- **隐匿点**：`0x1F` 是**累计掩码语义**（五个方向都已完成），不是"要求采五个方向"。传全 1 掩码，模组直接判成功。
- **怎么发现**：两个**物理证据**——914ms 就 SUCCESS；整个会话只有 **1 条 NOTE**（模组根本没采五次）。
- **调试动作**：用硬指标（耗时、帧计数）证明"模组没采集"，而不是靠推理猜语义。
- **修复**：逐方向分 5 次（正0x01→右0x02→左0x04→下0x08→上0x10），app 按累计掩码主动续发。

### Bug-4 假绑定残留（幂等机制的死角）
- **现象**：tyx 从没录成功却显示"删人脸"，删除被拒。
- **隐匿点**：**启动对账只跑一次**（幂等设计）——它管不到"本次运行期间新产生的假绑定"。
- **怎么发现**：时序还原：对账标失效 admin（旧假值）→ 旧 Bug-2 又给 tyx 写新假值 → 无人再管。
- **调试动作**：**机制叠加分析**（两个各自正确的机制叠加出死角）+ 直接读 users.json 原始数据。
- **修复**：读盘归一化非法 face_id（源头校验 + 存量清理两道闸门）。
- **教训**：**幂等的一次性机制不能当唯一兜底**。

### Bug-5 store_init 不填充 policy（09-21）
- **现象**：users.json 里 `enroll_five_way=true`，启动日志却是"录入模式切换 → 单帧"。
- **隐匿点**：`store_init` "看起来做了初始化"（建目录、引导默认 admin），**但没做"读盘填内存"**。`g_policy` 停在编译期默认值（enroll_five_way=false），直到 UI 第一次调 `load_users()`。
- **怎么发现**：顺着数据流逐层排查——盘上数据 ✓ → 解析代码 ✓ → **调用时序** ✗（`user_policy()` 在首次 load 之前被调用）。
- **调试动作**：从现象到设计走完整条链：界面 → 原始数据 → 解析 → **时序** → 初始化职责。
- **修复**：`store_init` 在"文件已存在"分支补一次 `load_users()`——**初始化内存态本来就是它的职责**，任何"启动早期读 policy"的代码都该拿到真值。

### Bug-6 20ms 泵里的非幂等调用
- **现象**：无（自查发现）。
- **隐匿点**：`face_service_set_enroll_five_way(user_policy()->…)` 被放进 20ms 主线程泵——每秒约 50 次加锁 + 整份 policy 拷贝，全是无用功。
- **调试动作**：审视"代码放在哪"——**泵里只放幂等的东西**（`cred_reconcile_tick` 自带 `s_done` 短路所以没事）。
- **修复**：移到 `app_main` 初始化，只做一次。

### Bug-7 EV_USER_CHANGED 定义了但无人订阅
- **现象**：清空模组人脸后用户页不刷新。
- **隐匿点**：事件"发出去了"但没人听；`cred_reconcile` 注释甚至写着"属死代码，若将来确有订阅者再恢复"。
- **修复**：三处联动（page_users 订阅 + 两处广播）——恰好是注释里预留的那个"将来"。

### Bug-8 toggle_row 回调写死
- **现象**：第二个使用该行的开关点了没反应。
- **隐匿点**：`lv_obj_add_event_cb(sw, vpin_click_cb, …)` 回调**硬编码**——第一个使用者一切正常，第二个静默失效。
- **怎么发现**：**编译警告** `mode_click_cb defined but not used` —— unused-function 是逻辑 bug 的免费信号。
- **修复**：回调改由调用方传入。

### Bug-9 static 函数声明不在使用点之前
- **现象**：`implicit declaration` + `conflicting types`。
- **隐匿点**：同一个错一天犯两次（`page_system.c` 的 `clear_face_btn_cb`、`backend_fm225.c` 的 `fm225_next_dir`）。
- **教训**：声明放**使用点之前**，不是"定义之前"。

## 二、调试方法论（10 条，每条对应上面的真实案例）

1. **先拿证据，再下结论**（Bug-2）——不是猜"可能同步有问题"，而是先拿到 `uid=65535` 这个铁证。
2. **三源对账**（Bug-2）——app 日志 / 模组清单 / users.json 三方摆一起："app 说成功、模组说没有"必有一假，假的那边立刻现形。
3. **物理证据链**（Bug-3）——914ms + 1 条 NOTE 是硬指标，比任何语义推理都硬。
4. **对照参考实现**（Bug-1/3）——桌面测试工具是"能跑通的实现"，比读手册猜语义可靠得多。
5. **时序还原，找机制叠加的死角**（Bug-4）——两个各自正确的机制（幂等对账 + 旧 bug 写新数据）叠加出无人负责的区间。画时间线比反复读代码快。
6. **顺着数据流走**（Bug-5）——现象 → 原始数据 → 解析 → 时序 → 设计职责。每一层排除一个嫌疑。
7. **别忽略编译警告**（Bug-8）——`unused-function` 看着无害，实际暴露了回调写死的逻辑 bug。
8. **一次只改一件事**——先让单帧通（0x1D），真机验证后再做五向。一次改两件事，出错就不知道是谁引入的。
9. **可复现性是调试的前提**——`| tee` 会让 stdout 全缓冲、Ctrl+C 丢日志；`run_fm225.sh` 常备 `stdbuf -oL -eL`。**先保证日志拿得到，再谈调试。**
10. **下结论前读原始数据**——我曾据"启动时模组清单 1 个"推断出反向孤儿，被用户一句"app 不是也有两张人脸吗"纠正。**日志片段 ≠ 全局状态**，读一次 users.json 十秒钟。

## 三、调试基础设施（环境要点）

- **日志**：`./run_fm225.sh 2>&1 | tee /tmp/app.log`（启动器内含 `stdbuf -oL -eL` 防缓冲丢日志）
- **诊断日志**：切模式时打印 `[fm225] 录入模式切换 → 五向`（区分"同步链路断了"与"文案没走分支"）
- **数据核验**：`python3 -c "import json; d=json.load(open('data/users.json')); ..."` 直读原始数据
- **参考实现**：`~/桌面/FM225测试工具/fm225_debug_platform/`（命令表 + 应答解析，语义权威来源）
- **线程取证**：`gdb -p <pid> -batch "thread apply all bt"` 逐线程取栈（规约 §3.3 的实测依据）
