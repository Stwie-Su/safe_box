## 1. 分层与依赖方向

```
┌──────────────────────────────────────────────────────────────┐
│  app/platform/     平台引导：命令行、显示后端选择、防息屏、性能探针 │
│  可 #include LVGL 与系统头文件                                  │
├──────────────────────────────────────────────────────────────┤
│  app/ui/           视图层：外壳、主题、组件、页面                │
│  可 #include LVGL + core 公共头                                │
├──────────────────────────────────────────────────────────────┤
│  app/core/         业务层：认证、状态机、存储、RPC、TOTP、配置     │
│  禁止 #include LVGL，禁止 #include 平台头文件                    │
├──────────────────────────────────────────────────────────────┤
│  app/hal/          硬件抽象：接口 + 多种后端实现                  │
│  只有这一层知道硬件怎么访问                                       │
├──────────────────────────────────────────────────────────────┤
│  ports/lv_port/    LVGL 官方 Linux 移植层（显示/输入后端）        │
│  third_party/      aes、sha256 等自包含第三方代码                 │
└──────────────────────────────────────────────────────────────┘
```

依赖只能向下，不能反向。检查方式见 `docs/05-分层检查.md`。

三条硬规则：

1. `app/core` 不出现 `lvgl.h`、`<linux/...>`、`<SDL2/...>`。UI 通知一律走回调或事件总线。
2. `app/hal` 的头文件只放数据类型与函数声明，不放任何平台头文件，避免污染上游。
3. `app/ui` 只做渲染与事件绑定，判定逻辑下沉到 `core`，硬件动作下沉到 `hal`。

## 3. 统一错误码

`app/core/err.h` 收敛现有返回值的混乱（store 用 0 成功、auth 用枚举、部分函数返回 -1）。

```c
typedef enum {
    SAFE_OK          =   0,   /* 成功 */
    SAFE_ERR_FAIL    =  -1,   /* 通用失败 */
    SAFE_ERR_PARAM   =  -2,   /* 参数非法 */
    SAFE_ERR_NOMEM   =  -3,   /* 内存不足 */
    SAFE_ERR_NOENT   =  -4,   /* 记录不存在 */
    SAFE_ERR_EXIST   =  -5,   /* 记录已存在 */
    SAFE_ERR_PERM    =  -6,   /* 权限不足 */
    SAFE_ERR_IO      =  -7,   /* 文件读写失败 */
    SAFE_ERR_LOCKED  =  -8,   /* 处于锁定状态 */
    SAFE_ERR_EXPIRED =  -9,   /* 已过期或次数用尽 */
    SAFE_ERR_BUSY    = -10,   /* 设备忙（如正在录入人脸） */
    SAFE_ERR_UNSUP   = -11,   /* 当前后端不支持该操作 */
    SAFE_ERR_TIMEOUT = -12,   /* 超时 */
} safe_err_t;

const char * safe_err_str(safe_err_t e);
```

认证域保留自己的 `auth_result_t`（语义域不同，映射到 RPC 错误码），
其余模块统一返回 `safe_err_t`。

## 4. 事件总线

现状问题：FSM、RPC、主题、UI 之间用四个独立回调字段互相挂钩，
加一个订阅方就要改一次头文件，main.c 里还要手写桥接。

改为单一事件总线，主题用字符串枚举：

```c
typedef enum {
    EV_AUTH_STATE,      /* 状态机状态变化：arg = fsm_state_t */
    EV_AUTH_RESULT,     /* 开锁成功/拒绝：arg = auth_event_t */
    EV_USER_CHANGED,    /* 用户增删改 */
    EV_POLICY_CHANGED,  /* 安全策略/阈值变化 */
    EV_NET_CHANGED,     /* 网络配置变化 */
    EV_MQTT_STATE,      /* 连接/断开 */
    EV_THEME_CHANGED,   /* 主题切换 */
    EV_ALARM,           /* 告警（FR-10 预留） */
} ev_topic_t;

typedef void (*ev_handler_t)(ev_topic_t topic, const void *payload, void *user);

safe_err_t event_bus_subscribe(ev_topic_t topic, ev_handler_t h, void *user);
safe_err_t event_bus_unsubscribe(ev_topic_t topic, ev_handler_t h);
void       event_bus_publish(ev_topic_t topic, const void *payload);
```

约束：

- 发布一律在主线程（LVGL 线程）进行，订阅回调里可以直接操作控件；
- 跨线程事件（MQTT 线程收到指令）先入队，主线程 `event_bus_pump()` 时再发布；
- 总线不做内存管理，payload 生命周期由发布方保证至少覆盖本次派发。

## 5. 人脸模块接口（本期预留）

### 5.1 设计要点

1. 异步事件驱动，不用调用方轮询。
2. 后端可注册：模拟后端与 FM225 后端实现同一张 vtable，编译期或运行期选一个。
3. 能力查询：调用方先问后端能干什么，再决定要不要调用。
4. 录入与删除是耗时操作，走异步任务 + 进度事件。
5. 业务层只认 `{face_id, score}` 这一个数据契约，不认数据来源。

### 5.2 接口

```c
/* app/hal/hal_face.h —— 业务层唯一可见的人脸头文件，不含任何平台头文件 */

typedef struct {
    int32_t face_id;      /* -1 = 未识别到已注册人脸 */
    int32_t score;        /* 0~100 */
    uint32_t seq;         /* 帧序号，用于去重 */
    uint32_t timestamp;   /* hal_time() 时间戳 */
} face_result_t;

typedef enum {
    FACE_EV_DETECT = 0,   /* 识别结果：payload = const face_result_t * */
    FACE_EV_ENROLL_DONE,  /* 录入完成：payload = const face_enroll_result_t * */
    FACE_EV_DELETE_DONE,  /* 删除完成：payload = const face_delete_result_t * */
    FACE_EV_ERROR,        /* 后端错误：payload = const char * 描述 */
} face_event_t;

typedef struct {
    int32_t face_id;      /* 成功时 >= 0，失败时 -1 */
    safe_err_t err;
} face_enroll_result_t;

typedef struct {
    int32_t face_id;
    safe_err_t err;
} face_delete_result_t;

/* 后端能力位 */
#define FACE_CAP_DETECT    (1u << 0)   /* 能产出识别结果 */
#define FACE_CAP_ENROLL    (1u << 1)   /* 支持录入 */
#define FACE_CAP_DELETE    (1u << 2)   /* 支持删除 */
#define FACE_CAP_INJECT    (1u << 3)   /* 支持注入模拟结果（仅 fake） */
#define FACE_CAP_LIVENESS  (1u << 4)   /* 带活体检测 */

typedef struct {
    const char * name;                 /* "fake" / "fm225" */
    uint32_t     caps;
    int32_t      max_templates;
} face_caps_t;

typedef void (*face_event_cb_t)(face_event_t ev, const void *payload, void *user);

/* 生命周期 */
safe_err_t face_service_init(const char *backend_name);
safe_err_t face_service_deinit(void);
void       face_service_tick(uint32_t now_ms);   /* 主线程周期驱动 */

/* 事件订阅 */
safe_err_t face_service_subscribe(face_event_cb_t cb, void *user);

/* 能力查询 */
const face_caps_t * face_service_caps(void);

/* 控制 */
safe_err_t face_service_start(void);             /* 开始识别 */
safe_err_t face_service_stop(void);
safe_err_t face_service_enroll_async(int32_t *out_job_id);
safe_err_t face_service_delete_async(int32_t face_id);

/* 调试注入：仅 FACE_CAP_INJECT 后端有效，其它后端返回 SAFE_ERR_UNSUP */
safe_err_t face_service_inject(int32_t face_id, int32_t score);
```

### 5.3 后端 vtable

```c
typedef struct face_backend {
    const char * name;
    uint32_t     caps;
    safe_err_t (*init)(void);
    safe_err_t (*deinit)(void);
    safe_err_t (*start)(void);
    safe_err_t (*stop)(void);
    void       (*tick)(uint32_t now_ms);
    safe_err_t (*enroll)(void);       /* 结果通过 face_service 上报 */
    safe_err_t (*delete_tpl)(int32_t face_id);
    safe_err_t (*inject)(int32_t face_id, int32_t score);
} face_backend_t;

const face_backend_t * face_backend_fake(void);
const face_backend_t * face_backend_fm225(void);   /* 本期为 stub */
```

### 5.4 后端选择

| 构建选项 | 效果 |
|---|---|
| `SAFE_FACE_BACKEND=fake`（默认） | 编译 `backend_fake.c`，支持注入分数，PC 与板子都能跑 |
| `SAFE_FACE_BACKEND=fm225` | 编译 `backend_fm225.c`，当前为协议解析空壳，返回 `SAFE_ERR_UNSUP` |
| `SAFE_FACE_BACKEND=none` | 编译空后端，人脸通道整体停用 |

FM225 到货后只需补 `backend_fm225.c` 的 UART 解析，业务代码不动。

## 7. 并发模型

```
主线程（LVGL 循环）
  ├── lv_timer_handler()
  ├── face_service_tick()        20ms
  ├── auth_fsm_tick()           100ms
  ├── event_bus_pump()           20ms   ← 派发跨线程入队的事件
  ├── worker_poll()              20ms   ← 取异步任务结果
  └── 周期状态上报               5s

MQTT 线程（可选特性）
  ├── Paho 事件循环、断线重连
  └── 收 safe/cmd → 入队，由主线程消费

worker 线程
  └── PBKDF2、文件落盘、网络扫描等阻塞任务
```

线程边界：

1. LVGL API 只能在主线程调用。
2. MQTT 线程不碰 LVGL 对象，只入队；指令在主线程分发。
3. 用户表读写加互斥锁，业务线程与 MQTT 线程都会访问。
4. 订阅回调运行在主线程，可以直接更新界面。

## 8. 构建与特性开关

| 选项 | 默认 | 说明 |
|---|---|---|
| `SAFE_FEATURE_MQTT` | 依赖存在时 ON | 关掉后 `remote/` 编译为 no-op 存根 |
| `SAFE_FEATURE_JSON` | 依赖存在时 ON | 关掉后存储层退化为受限模式 |
| `SAFE_FACE_BACKEND` | `fake` | `fake` / `fm225` / `none` |
| `SAFE_BUILD_TESTS` | ON（PC） | 板子交叉编译时默认关闭 |
| `SAFE_DATA_DIR` | 工程内 `data/` | 板子上由 defconfig 覆盖为 `/var/lib/safe` |

特性开关的实现方式：头文件给统一声明，`.c` 选一份实现编译。
调用方代码不出现 `#ifdef`，保证核心链路在有无依赖时都能编译。

目标产物：

| 目标 | 内容 |
|---|---|
| `lvgl_linux` | 官方移植层静态库 |
| `safe_core` | 业务静态库（不含 LVGL 依赖），供单测链接 |
| `lvglsim` | 最终可执行文件 |
| `safe_tests` | 单元测试集合（CTest） |

## 9. 运行时数据

| 文件 | 内容 | 处理 |
|---|---|---|
| `data/users.json` | 用户、角色、PIN 哈希与盐、策略、阈值 | 哈希不可逆，权限 600 |
| `data/network.json` | SSID、加密方式、加密后的 PSK | AES-256-CBC 可逆加密 |
| `data/safe.log` | 审计日志，JSON Lines | 追加写，超过上限滚动 |

数据目录由构建期 `SAFE_DATA_DIR` 决定，运行时可用环境变量 `SAFE_DATA_DIR` 覆盖。
源码目录不再产生任何运行时文件。
